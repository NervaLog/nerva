# v0.7.0 release audit

This audit covers what changed since `v0.6.1` (`2be394b6b6822a6225bc3ebc553aa63d64e7f730`) that a
running cluster, its operator or its client can notice. It also records how the upgrade and the
downgrade were tested by hand. It was written on 2026-11-10 for the release candidate below,
before the adversarial reviews.

**Release candidate:** `main` at `a47d9c7d452c9ae257e18037e3bb7ca3bbdbb71d` (the merge of #259),
327 commits after `v0.6.1`. `src/` and `build.zig` are the same as at `4269b80` (the merge of
#239), where the tests below ran. The three merges after it (#258, #242, #259) change only
`tests/jepsen`, `.github/workflows/jepsen.yml`, `ops/jepsen` and documentation.

## `nerva api` JSON surface

Every change adds a field or a reply where there was none. No field is renamed or removed.
`error` and `status` keep their spellings (P168b, P173c).

| Change | PR | v0.6.1 clients |
| --- | --- | --- |
| `applied` (`false`, `"unknown"`) and `code` on every reply that is not `2xx` | R4 (P168b, P173c) | unaffected: new fields |
| A replayed commit answers `200` with `"replayed":true,"code":"NRV-W0201"` | R4 | unaffected |
| All slots busy: `503 busy` NRV-E0602, sent before reading, where v0.6.1 closed mid-send | #170 (#120) | a client sees a reply instead of a reset |
| A request not whole after 10 s: `408` NRV-E0116 | R4 | new reply |
| A second gateway on one port exits with NRV-E0007 (no `SO_REUSEPORT`) | #170 (#112) | operator-visible |
| `catalog busy`: `503` NRV-E0313 with `applied:"unknown"`, where v0.6.1 answered `cluster unavailable` | #228 (#216) | the spelling of `error` changes for this case only |
| `/v1/documents/commit` takes a `key`; a malformed key is NRV-E0109 on every route | #180 | new optional field |
| The request deadline: NRV-E0606 when less than a sixteenth of it is left | #195, #209, #213 | new reply, `applied:false` |
| Commits and lookups that wait together go to the cluster as one request (at most 16) | #143 | the reply to each request is unchanged |
| An idle gateway probes its cluster every 5 s; `/healthz` turns `503` NRV-E0605 | R4 | `/healthz` is more accurate |

## Upgrade and downgrade, tested by hand

This used three `--development` replicas on loopback. The v0.6.1 binary (`0.0.6+2be394b`) and the
candidate (`0.0.6+4269b80`) were both built here.

1. **v0.6.1 cluster.**
   - Formatted with v0.6.1.
   - Through a v0.6.1 gateway: a layout, a keyed commit (a row and a record), a ledger and a
     document, then 2,500 more commits, so the cluster crosses checkpoints.
2. **Rolling upgrade.**
   - Replica 0 restarted on the candidate.
   - The mixed cluster (one new replica, two old) committed through a v0.6.1 gateway.
   - Replicas 1 and 2 restarted on the candidate.
3. **Candidate cluster, candidate gateway.**
   - Read every v0.6.1 row, record, ledger and document.
   - Resent the v0.6.1 commit key: `200`, `"replayed":true`, `NRV-W0201`.
   - Wrote a keyed commit, a document under a key (new in v0.7.0) and 2,500 more commits.
4. **Downgrade.**
   - Every replica restarted on v0.6.1.
   - A v0.6.1 gateway read what the candidate wrote, the keyed document included.
   - Resending the candidate's commit key applied nothing.
   - 1,500 more commits succeeded.
5. **Results.**
   - No replica log has a panic or an `error[` line.
   - The candidate's `nerva api --listen=0.0.0.0:…` without `--listen-remote` exits 1 with
     NRV-E0009.

The script is not in the tree. Reviewers who want to repeat the test can write their own from
the steps above. `test:release` covers the same paths automatically, with fewer ops.

## Notes for the reviewers' briefs

- Review the diff `v0.6.1..a47d9c7` (`git diff v0.6.1 a47d9c7 -- src build.zig` for code).
- Start with #254 and #255. Both are in `prefetch_members_callback`, so the review should check
  whether `prefetch_operation` can be stale or reused across a prefetch that is still running.
- Check the request combining in the gateway (#143, P143) for lost or swapped replies.
- Check that the `-Dtest-commit-keys=off` build can never be installed (#221, #222).
- `recover` and the view it chooses ("two past the cluster's", P149b) is the one change that
  writes a data file in a new way. `test:release`'s recover script exercises it; check that a
  v0.6.1 binary opens a recovered file too.
- P259g: moving from v0.7.0 to the first R6 release is an export and import, so v0.7.0 is the
  last release on `0.0.6`.
