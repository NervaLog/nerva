# v0.7.1 release audit

This audit covers what changed since `v0.7.0` (`3301aadd60117ec553368ea6040bf6c524c4e45b`) that a
running cluster, its operator or its client can notice. As P275 requires, it lists every new
kind of op, runs the ops a candidate gateway sends against v0.7.0 replicas and the other way
round, and states the upgrade order and rollback condition that follow. It was written on
2026-11-11 (PR #312), before the soak and the adversarial reviews.

**Code audited:** `main` at `36da4ca05f8a7f60ccc2fb753c58a1f001e965c4` (the merge of #309), 14
commits after `v0.7.0`. The release candidate is the `main` commit the soak runs on, which
includes this PR. #311 merged after the audit (`696a890878fefcaeb8476b4ce799a997a778279e`) and
changed four lines of `src` and `build.zig`; the addendum at the end covers them. **This audit
holds for a candidate only while `git diff 696a890 <candidate> -- src build.zig` is empty.** A fix
that merges during the soak and touches either must re-run the checks below (P275), and the
release PR says which.

## Verdict

**No new kind of op, no `Operation` value, no state machine change, no `tree_ids` change, no
on-disk, wire or export format change.** The only changes to the `nerva` binary are a sixth line
in `nerva version`, a longer pre-flight wait for a data file's lock, a help text and a test
helper. A v0.7.1 gateway ran against v0.7.0 replicas, a v0.7.0 gateway against v0.7.1 replicas,
a rolling upgrade and a rollback, with both gateways committing to the mixed cluster; all passed
(below).

So the release notes' **"Upgrading from v0.7.0: replace the binary, one replica at a time, then
gateways in any order"** holds, and **a rollback to v0.7.0 is the same swap the other way**, with
no condition beyond v0.7.0's own. Upgrades from v0.6.1 keep P260's order: v0.7.1 gateways combine
requests exactly as v0.7.0 gateways do.

## Mixed releases, run by hand (P275)

Two real binaries on one host, three `--development` replicas on loopback with a random
`NERVA_CLUSTER_KEY`, and two gateways, one of each release:

- **v0.7.0:** the published `nerva-v0.7.0-x86_64-linux.tar.gz` (SHA-256 checked against the
  release's `SHA256SUMS`), `Nerva version 0.0.6+3301aad`.
- **Candidate:** `./zig/zig build -Drelease` at `36da4ca`, `Nerva version 0.0.6+36da4ca`, the
  same `format` digest.

Each phase writes 1,200 keyed puts into a table under a view with `count`, `min` and `max` per
group (declared before its rows), 20 keyed ledger pairs and a keyed document, sent by 16 threads
at once so that each gateway combines them (P143). Then it sends every key again at once:
combined, resent keyed transactions over `min`/`max` view members, the op shape of #254 and
#255. Every resend must answer `replayed` with its original op. A rotation stops each replica in
turn while the other two commit, so every pair of replicas forms a quorum on the binaries of
that phase.

1. **v0.7.0 cluster, v0.7.0 gateway.** Formatted by v0.7.0. Layouts, the view, a ledger of two
   fields, phase 1 (through op 427).
2. **v0.7.1 gateway on v0.7.0 replicas** (P275's direction that v0.7.0's audit missed). It read
   phase 1 as the v0.7.0 gateway did, wrote phase 2 past the first checkpoint (op 1,194), and
   replayed every phase 1 key. Both gateways read the view's hash and groups alike at op 427 and
   op 1,194. Rotation passed.
3. **Rolling upgrade.** Each replica in turn stopped (SIGTERM) and started on the candidate.
   After each, both gateways committed 400 puts each, 16 at a time, to the mixed cluster. Rotation
   passed on three candidate replicas.
4. **v0.7.0 gateway on v0.7.1 replicas.** Both gateways read phases 1 and 2 the same (every row's
   value and op, the ledger's accounts, the documents), and as before the swap. The view's
   `as_of` answers were unchanged. Every key of phases 1 and 2 replayed at its op. The v0.7.0
   gateway wrote phase 5 and the candidate's phase 6 (through op 4,882).
5. **Rollback.** Each replica in turn back on v0.7.0, 200 commits after each. Rotation passed on
   three v0.7.0 replicas. Both gateways read phases 1, 2, 5 and 6 as in step 4, and the view at
   ops 427, 1,194 and 4,882 as before. Every key of the four phases replayed at its op. A last
   phase committed (latest op 8,052, past several checkpoints).
6. **Logs.** No replica or gateway log has a `panic` or an `error[` line. Their warnings are
   connections closed by the swaps and prepares ignored during view changes.

The script (`mixed_071.py`, about 300 lines of Python) is posted as a comment on PR #312, not
kept in the tree: `test:release` runs two builds of one source, while this needs a published
release. Reviewers can run it with any two binaries: `python3 -I mixed_071.py <v0.7.0 nerva> <candidate
nerva> <empty dir>` (it needs about 3.5 GB of disk).

## Upgrade order and rollback condition

- **From v0.7.0:** replace the binary, one replica at a time, waiting for each to catch up, then
  the gateways in any order. A v0.7.1 gateway may run before every replica is upgraded, and a
  v0.7.0 gateway after: both directions were run.
- **Rollback to v0.7.0:** the same swap the other way, at any time. v0.7.0 opens what v0.7.1
  wrote and replays what it committed.
- **From v0.6.1:** P260's order is unchanged. A v0.6.1 replica panics on combined resent keyed
  transactions over `min`/`max` view members (#254, #255), and v0.7.1 gateways combine as v0.7.0
  gateways do. Every replica first, then gateways; roll back to v0.6.1 only if no v0.7.x gateway
  and no multi-batch client has run since the upgrade began. Not run here against a real v0.6.1
  binary (as for v0.7.0: P260, "What it costs").
