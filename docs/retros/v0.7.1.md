# v0.7.1 retro

Release PR #453 (the `VERSION` commit `f80dcdf`, 2026-11-14 17:41 UTC). The candidate was `c886c9f` (P388).
The draft was created at 17:41. The release was published 11 h 40 min later, at 2026-11-15 05:21:33 UTC,
with 12 assets. Getting there took nine release runs and five fixes to the release automation
(#455, #459, #462, #465, #467). The last fix landed after the release was published. The
run-by-run record is at the end of this file. Facts marked *(lead's account)* come from the
release lead and could not be checked against GitHub. Everything else was read from the GitHub API
on 2026-11-15.

## Assumptions that were wrong

1. **"The finish chain has been rehearsed before the tag."** P343 (4) and P360 (8) required a
   rehearsal on `v0.7.1-rc.2`. The Developer ID chain and the notary profile were to be "tried
   only by the rehearsal", and the automation was to be used for v0.7.1 only if that rehearsal
   passed the whole graph. The rehearsal never ran. No `v0.7.1-rc.2` tag or release exists, and
   `release-finish.yml` and `mac-sign.yml` have no run before 2026-11-14 18:42, an hour after the
   `VERSION` commit. P360 (9) allowed v0.7.1 to be "the first run of the steps the rehearsal
   cannot reach". In the end it was the first run of every step. P389 (7) left the owner's approval
   of `apple-signing` as the only gate, and that approval cannot show whether a rehearsal ran.
   - Cost: the release ran nine times: `release.yml` three times, `release-finish.yml` six times,
     and `mac-sign.yml` once by hand. The owner approved `apple-signing` at least seven times. Five
     fixes merged while the release was half done:
     - the signing secrets did not reach the called workflows (NRV-E1121, #459);
     - Apple's intermediates were missing (#455);
     - the codesign output read wrongly (#462);
     - a relative script path after `cd` (#464, #465);
     - an untrusted Homebrew tap (#466, #467).

     A notary credential refusal (run 43636852450) was an owner-side secret. 11 h 40 min passed from the
     `VERSION` commit to publication. Five of those hours (00:06 to 05:14) the last run waited for
     the signing approval overnight.
   - Change (P474 (a)): the release PR quotes the rehearsal's `release-finish.yml` run, as it quotes
     the fleet line, the Jepsen result and the verdicts. A release with no such run needs the
     owner's written waiver, which names the jobs that were never run. The rule was there. Nobody
     could see that it had not been met.

2. **"If the jobs before `publish` pass, the jobs after it are set up."**
   - `PACKAGES_BASE_URL` was set on the `package-repos` environment. `repos-ready` and `repos` read
     it from there as `https://packages.nerva.pro`. P404 requires a repository variable, and
     `repos-verify`, which has no environment, read it empty: NRV-E1139 in all 16 cells, after the
     release was public.
   - `site-verify` failed with NRV-E1151: nerva.pro did not show 0.7.1 within 15 minutes after the
     site's release PR (NervaLog/nervalog.github.io#19) merged. The nerva-site Worker that replaced
     Pages (P410) was not serving yet. *(lead's account: the Worker was not set up. This session
     could not reach nerva.pro to check.)*
   - Cost: v0.7.1 is public, and the apt repository serves `0.7.1-1` (its `InRelease` is dated
     05:23 UTC). No install from the repositories has been verified on any distribution, and the
     site check is red. A re-run of 43656540690 waits on the owner's setup.
   - Change: proposed in #473, not made here because it is a workflow change. Before `publish`,
     check the repository variables from a job with no environment, and check that nerva.pro
     serves the previous version.

3. **"The runner's Homebrew behaves like the one `mac-verify` was written against."** On
   `macos-15`, Homebrew refused the formula from the untrusted `nervalog/tap`. The step then
   reported "the tap has nerva , not 0.7.1", blaming a stale formula that was not stale (#466).
   `macos-15-intel`, with an older brew, passed.
   - Cost: `verify / macos-15` failed after publication. Users on current Homebrew need
     `brew trust nervalog/tap`, which the release notes do not say.
   - Change: done. #467 trusts the tap where brew has the command, codes a brew read failure
     NRV-E1167, and adds the step to `docs/INSTALL.md`. `Mac verify` run 43683391666 on `20c3149`
     passed on both Macs at 05:59.

4. **"Held pull requests can merge in any order once each is reviewed."** Under P389, eight held
   PRs merged between 07:29 and 08:36 on 2026-11-15:
   - #338, #430 and #415 at 07:29;
   - then #469, #403, #431, #407 and #412.

   #403, #431, #407 and #412 each merged `main` in again after an earlier merge (one to three times
   each, by their merge commits), and each was reviewed again. *(lead's account: each of these
   merges conflicted.)* #412's review after its merge found a MUST that the merge order caused. #415
   (bundled releases, R6) had merged first, and #412's sender check compared the connection's
   release with `==` against the single running release, not `runs(releases_run, ...)`. It was
   fixed in `3cae76a`, reviewed again, and merged.
   - Cost: about two hours of merge and review cycles, and a MUST that a merge in the other order
     would not have hit.
   - Change (P474 (b)): the held PRs merge one at a time. The brief for each later review names the
     PRs merged since that PR's last review, and the files they share. P389's "review after the
     last push" caught this one. The brief makes the cause visible to the reviewer.

5. **"A worktree's own Zig cache stays out of commits."** #469's first attempt (a cherry-pick of
   #352) committed `.zig-global-cache/`: 1,465 files, 77.4 MB, in `8992b25` on the PR branch.
   `2db2c27` removed it, and the squash merge kept it off `main`.
   - Cost: a review round, and a branch that holds 77 MB of history.
   - Change: `.gitignore` lists `.zig-global-cache/` (#469). P474 (c) puts each agent's
     `ZIG_GLOBAL_CACHE_DIR` in the session scratchpad, outside the worktree. CLAUDE.md said only
     "its own", and the cache ended up inside the worktree.

6. **"A red check that passes on a re-run is noise."** #403's CI (run 43684883408) failed on
   attempt 1 in `test_package_repos.py`. `gpg --quick-generate-key` exited 2, and every later test
   then failed with `FileExistsError` on the same key directory. The run passed on attempt 2 and
   #403 merged. CLAUDE.md says a failing run is a finding, never noise.
   - Cost: none yet. The flake is still in a required check.
   - Change: filed as #472. The rule stays as it is. This time it was not followed.

## Process

- CI watchers reported "no pending checks" before any check run existed for the head, and
  merging waited on a start delay and a manual check of the check-runs API *(lead's account)*.
  Change (P474 (d)): a watcher reports a head as settled only when its check runs exist and have
  all finished.
- A review brief named a stale `main` SHA *(lead's account)*. Change (P474 (e)): a brief takes the
  SHA it names from GitHub when it is written, and the reviewer checks it against the live head
  before starting.
- #412's vendored patches (`src/message_bus.zig`, `src/testing/cluster/message_bus.zig`,
  `src/vsr/replica.zig`) needed the owner's written approval under P389. The approval came in
  session at 06:31 and is quoted on #412.
