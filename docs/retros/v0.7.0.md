# v0.7.0 retro

Release PR #274 (merged at `d61154f`). The first release run, on candidate `a0a6a80`, failed
building for macOS (#276). The release is built from `main` at `b1ea448`, which adds #269 and
#277 to `a0a6a80`; two more reviewers reviewed that delta (#279 to #282).

## Assumptions that were wrong

1. **"A mixed v0.6.1/v0.7.0 cluster is safe in both directions."** The audit and reviewer A's
   hand-run upgrade tested a v0.6.1 gateway against v0.7.0 replicas. Nobody tested a v0.7.0
   gateway against a v0.6.1 replica, which is the case that breaks: P143 (request combining)
   makes ops that #254 and #255 panic a v0.6.1 replica on.
   - Cost: reviewer B's MUST (#272), a decision from the owner, a corrected CHANGELOG (P260),
     and about half a day.
   - Change: a release audit lists every new kind of op since the last tag and tests each
     against the previous release's replicas. The rollback path is stated op by op, not
     assumed.
2. **"The candidate is fixed once both reviewers start."** #254 and #255 (extreme scans counting
   members admission did not count) landed after the first candidate, `a47d9c7`.
   - Cost: a second candidate (`a0a6a80`, with #263 and #267), a Jepsen re-run (68, then 71),
     and the reviewers re-checking it.
   - Change: none. Moving the candidate for a correctness bug was right. Briefs now name the
     candidate SHA, and the reviewers diff against it.
3. **"The container can run the release suites beside other work."** One fixer ran out of
   memory and killed processes it did not start, which cut off reviewer B's `test:release`
   (first by memory, then by disk).
   - Cost: reviewer B's verdict rests on CI's `releases` job, not its own run, and a few
     hours went to working out which failures were findings.
   - Change: at most one heavy build (`test:release`, `test:integration`, `test:unit`) at a
     time in a session. A reviewer that needs a release suite dispatches it on CI. An agent
     never kills a process it did not start.
4. **"The release gate's fleet clause will bind."** R2's fleet was not running yet, so
   "sim-clean" meant VOPR seeds, fuzz smoke and the fixed #254 and #255. #252 was waived by
   the owner.
   - Cost: none measured, but this release had no 24-hour soak.
   - Change: the next release waits for the fleet (#177) unless the owner waives it again in
     writing.

5. **"If the Linux binary passes CI, every release target builds."** CI built and tested only
   Linux. `release.yml` also builds `x86_64-macos` and `aarch64-macos`, and nothing had
   cross-compiled them: #206 used `std.os.linux` and the metrics send used a flag macOS lacks.
   - Cost: a failed release run, a fix (#277), a second candidate (`b1ea448`) and a second
     round of two reviewers, who also found that the notes missed #269's five-line
     `nerva version` (#279, #281).
   - Change: the `release targets` CI job (#277) builds all four targets on every PR. Running
     the macOS binaries on a Mac is still open (#278).

## Smaller things

- The release PR was squash-merged, so the CHANGELOG date and `VERSION` landed in one commit.
  CLAUDE.md only requires `VERSION` (and its worklog) in a commit of its own, and the section
  existed before it. Date the heading in the prep PR next time.
- Botpike's `nerva.pin` feeds both the app's gateway, which deploys on every push, and the
  replicas, which are deployed by hand. A one-step pin bump would break P260's order
  (Botpike/app#159).
