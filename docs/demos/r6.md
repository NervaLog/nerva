# R6 demo: upgrade

**Status: built, not demonstrated.** R6's brief is [docs/briefs/r6.md](../briefs/r6.md). The demo
(`zig build demo-r6`) is slice 7; this document records what each slice ran.

## Slice 2: multiversion `nerva start`

Recorded as the slice ran (2026-11-13, Debug build, one replica, `--addresses=0 --development`,
unbundled binary, so it runs as one release and `MultiversionOS` is not opened):

- RSS at start: 1.75 GiB (`VmRSS` 1839212 kB), of which 1780 MiB is the replica's own init
  allocation (log line `allocated 1780MiB during replica init`).
- A bundled binary adds `MultiversionOS`'s source buffer and memfd, each `multiversion_binary_platform_size_max`
  (64 MiB, doubled outside ReleaseSafe). Measured with a real bundle in slice 3, once a packer exists.

Ran: `test:release` (mixed releases refuse E0718 above and E0701 below), `test:integration`,
`demo-r5`, VOPR seeds 1 to 5 (ReleaseSafe). Not run: a bundled start (no packer yet).

Known limit (P415d): a replica running an unbundled binary (the first R6 release, today every
build) does not poll its file, so replacing the binary in place upgrades nothing until each
replica is restarted. The demo restarts them.

## Slice 3: the packer and `bundle.py`

The brief lists "`nerva_next start` on N's data file logs `release_transition` to N and keeps its PID"
among `bundle.py`'s tests. It was cut here, while `start` had no multiversion (slice 2, #415, was
unmerged). Since P490 (#484) `bundle.py` starts the packed binary on the past release's data file
and reads its statsd gauges: `replica_release` is the past release (the switch happened) and
`replica_releases_offered` is the next. It does not read the log line or the PID; `rolling.py`
(slice 5) runs the cluster upgrade.

Margin: a stripped ReleaseSafe `nerva` is about 5 MiB, so a pair is about 10 MiB against
`multiversion_binary_platform_size_max` (64 MiB), a margin of about 54 MiB. `bundle.py` prints the
exact margin in CI; this figure is the description's rough one, not a recorded run.
