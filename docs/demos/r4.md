# R4 demo: gateway

**Status: built, not demonstrated.** It passed locally (below); `demo_r4` has not yet run in CI on `main`. R4's brief is [docs/briefs/r4.md](../briefs/r4.md). R4 is delivered only
when this demo is green in CI, with the run linked here.

- **The demo:** `zig build demo-r4`, which runs `tests/demo/r4.py` against a ReleaseSafe
  `nerva`, and the `demo_r4` job in `.github/workflows/ci.yml`. Both are in slice 7 (#190).
- **What it shows:** two client processes, each with its own `nerva api` on loopback beside it,
  on one three-replica cluster. A gateway with every slot taken refuses with `503 busy` and
  `"applied": false` and never cuts a request part-way. Its statsd metrics count the refusals.
  Killing one client's gateway stops only that client, and its keyed retries through a restarted
  gateway apply once. A cluster that stops answering turns in-flight writes into
  `"applied": "unknown"` and `/healthz` into `503` within the stated bound. Every error reply
  carries its code. The brief's table, "The demo", lists every step and its expected outcome.

This document grows slice by slice: what each slice ran, the cuts (with the reason), and the
recorded output of the green run.

## Slice 7: the demo

Run on 2026-11-05 in the cloud container, ReleaseSafe, **locally, not CI** (the CI run link is
added here after `demo_r4` is green on `main`). Seven local `zig build -Drelease demo-r4` runs
in all: run 1 failed at step 11, run 4 at step 9, and the three after the fix passed; runs 2 and 3
(before the fix) passed. Both failures were the script's, not Nerva's:

- Run 1, step 11: step 9's keys repeated B's earlier keys with other bodies, so the gateway
  rightly answered `key_reused` (NRV-E0207). Step 9 now uses its own key prefix.
- Run 4, step 9: a commit answered 200 within milliseconds of the SIGSTOP was counted as "in
  flight" and failed the 503 check. A 200 or 409 answered less than 0.5 s after the last signal
  is now accepted; it committed before the stop.

Cuts and choices (P190): clients A and B are caller threads in the script, each group with its own
gateway process, not Python subprocesses. Step 9 asserts "unknown" for at least one in-flight
request and `"applied":false` for those still waiting to be sent. Step 6 compares the sum of
`refused{reason:busy}`, `displaced` and `queue_wait` with the E0602 replies seen (the three
reasons answer alike); in these runs it was all `busy`. Step 11 also checks each account's
balance against the unique keys' effects, so a transfer applied twice cannot hide in a total
that stays zero. Step 5's refused drippers are counted too.
