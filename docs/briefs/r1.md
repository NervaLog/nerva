## Goal

Every night, the histories Botpike produces (keyed commits that are retried after an unknown
outcome, through gateways that are killed, cut off and paused) are checked by Jepsen against the
tip of `main`, and a failure becomes an issue with the seed, the history and the commit.

## Non-goals

- **Workloads beyond `retry` and keyed `bank`:** `claim`, `register` (Elle) and `feed` stay
  planned (N82). Bit flips and rolling upgrades are not R1.
- **Replaying a run.** Jepsen's `--seed` steers its generators but not the timing of real
  processes; N82's rule stands: a failure is reproduced as a VOPR seed or a unit test before it is
  fixed (P215c).
- **A self-hosted GitHub runner.** The repository is public (P147e); the host runs its nightly
  under systemd and reports through the GitHub API, as the fleet does.
- **Merging #106.** Its fuzz half is superseded by R2's fleet (P147h) and P147e's hosted runners;

## Design

### Where each part is verified

Three places, used in this order of preference (P215b):

| Where | What it can run | Who uses it |
| --- | --- | --- |
| A cloud session | Zig (`check`, `test:unit`, VOPR, `test:api`), Python unit tests, `shellcheck`, `actionlint`, `lein check` and `lein test` if its dependencies download | Every slice |
| `jepsen.yml` on a hosted runner | The real suite, 5 nodes in Docker, runs of up to 20 minutes; started by a push to a scratch branch `jepsen/<slice>-<slug>` or by `workflow_dispatch` | Slices 2 to 6, the teeth in CI |
| The host | The nightly (an hour per workload), the 7 nights, LazyFS and clock faults | Slices 7 to 10 |

`jepsen.yml` is the bridge: it lets every workload, nemesis and checker run for real before the
host exists, as Zigbox's `vm/*` branches do. A scratch branch is deleted by the run when it ends;
a run never files an issue.

### The teeth: commit-key deduplication off, in a test build only

`StateMachine.Options` gains `commit_keys_deduplicate: bool = true`. When it is `false`, the three
places above treat a key's row as absent: the transaction commits again, and `commit_key_put`
writes the row again (a put over the existing row, no assertion). Nothing else changes: the
data file, the row and the wire are the same.

Only a test build can pass `false` (owner question 1): `zig build -Drelease
-Dtest-commit-keys=off` builds a `nerva` whose `start` sets it. That build's `start`
- refuses without `--development`: `error[NRV-E0717]: start: this build has commit-key
  deduplication off (-Dtest-commit-keys=off); it runs only with --development`, exit 1;
- logs, before it opens the data file, `warning: NRV-W0701 start: commit-key deduplication is off:
  a resent key commits again`;
- reports `<protocol>+<commit>+keys-off` from `nerva version`.

Every replica of a cluster must run the same build: a mix makes their states differ. That is why
it is a build and not a flag a release binary accepts. A release build cannot reach `false`.

### The reply model follows R4's contract (P215d)

`http.clj`'s `outcome` reads the body: `applied: false` on any status is a definite `:fail`;
`"applied": "unknown"` and a reply with no status line are `:info` for a write; `200` with
`"replayed": true` (`NRV-W0201`) is `:ok` with `:replayed? true` and the original `:op`. A
non-`2xx` reply without `code` or `applied` is a test failure (R4 promises both). The client's
timeout stays above the answer bound unless a workload lowers it on purpose (below).

### Workload `retry`

What Botpike does: keyed commits, resent under the same key until the answer is definite.

- **Data.** One unfloored `source` row and eight `account` rows with an `i64` `balance`, in a
  declared ledger. An operation is a **pay-in**: a fixed amount (1 to 30) from the source to one
  account, as a pair of adds with no `clamp`, so its effect does not depend on state and every
  commit of it moves exactly its amount. A pay-in never fails for funds.
- **Keys.** Each operation draws a fresh 128-bit key from Jepsen's random source (so `--seed`
  steers it); the entries under a key never change.
- **Gateways.** The test runs `--gateways 2`. Each attempt goes to a gateway drawn from every
  node's two (P183d's second gateway now carries traffic).
- **Lost replies on purpose.**
  - The client's timeout is drawn per attempt: 35 s, or with probability 1/4 a short one (50 to
    2,000 ms), below the gateways' `--request-timeout=3000`.
  - With probability `--drop-reply` (default 1/10) the client discards a `200` and resends as if
    it were lost.
  - The gateway nemeses below kill, cut off and pause gateways mid-request (#120's class).
- **Retries.** An attempt that is not definite is resent under the same key to another gateway,
  with backoff, up to `--attempts` (default 8). The operation completes `:ok` with the op of its
  first definite `200`, `:fail` if every attempt was `applied: false`, else `:info`.
- **Final phase.** After healing, every key whose operation ended `:info` is resent through a
  healthy gateway until its answer is definite, then every account is read in one lookup.
- **Checked** (`retry/checker`):
  1. **Once:** every definite `200` for a key, first-time or `replayed`, names the same op. A key
     answered `committed` twice at two ops is the duplicate the teeth must produce.
  2. **At most once in effect:** each account's balance equals the sum of the amounts of the keys
     that committed for it, each counted once, and the source equals minus their total.
  3. **No lie in `applied`:** a key whose every attempt before the final phase was answered
     `applied: false` must answer the final phase first-time, never `replayed`.
  4. **No reuse:** no reply is `key_reused` (the client never changes a key's entries); a
     `key_collision` is reported as invalid with its key (about 10⁻⁹ at a run's size).

### Workload `bank` with keys and records

Today's `bank`, with each transfer as Botpike sends it (`--keys`, the default; `--no-keys` keeps
today's unkeyed run for `test-all`):

- every transfer carries a key and is retried as `retry` retries;
- the same transaction writes a **record** (P123b) in a `transfers` record table: id from the key,
  value `from`, `to`, requested `amount`; a `count` view over that table (P123d) and an index by
  `from` (P123c);
- **checked:** today's bank checker, sum view and refusal rule; every key that committed has
  exactly one record and every record a committed key (read through the index in the final
  phase); the count view equals the number of committed keys; and `retry`'s check 1 (one op per
  key). Conservation alone cannot see a duplicate transfer: it conserves too.

### Gateway nemeses (`--nemesis gateway`, or one of its three faults)

Each gateway runs as its own Unix user on its node (`nerva-gw0`, `nerva-gw1`), so iptables can
match it with `-m owner --uid-owner`.

| Fault | Does | Targets |
| --- | --- | --- |
| `gateway-kill` | SIGKILLs gateways and restarts them on the same port; replicas untouched | one gateway, one node's two, a minority of nodes' |
| `gateway-partition` | Drops the gateway user's packets to the replica port (`OUTPUT -p tcp --dport 3000 -m owner`), while the client still reaches it | its own node's replica, a majority of replicas, all |
| `gateway-pause` | SIGSTOP a gateway, SIGCONT after the fault's interval: a request it held goes out late | one gateway, one node's two |

`--nemesis gateway` composes the three. Healing resumes, restarts and removes the rules. A paused
gateway is the case keys exist for: the client resends elsewhere, the retry commits, and the
original arrives later and must answer `replayed`.

### Failures as issues: `ops/jepsen/`

Modelled on `ops/sim-fleet/` and Python 3, standard library only (P147i):

- `nightly.sh` (systemd `jepsen.service`, started by `jepsen.timer`): stops `sim-fleet.service`,
  fetches `main`, builds `nerva` in ReleaseSafe at the tip, runs the nightly (demo steps 1 and 2,
  P215), archives `store/` (tar.zst, kept 90 days), restarts the fleet, and calls the reporter. It
  holds `flock` and a whole-night deadline of 3 h; a run past it is killed and reported as the
  host's.
- `jepsen_report.py ingest --commit SHA --store DIR [--dry-run]`, for each test:
  - **valid:** a commit status `jepsen/nightly` = `success` on the commit;
  - **invalid or unknown:** one issue labelled `jepsen` per fingerprint (workload, the failing
    checker key, its anomaly class: `duplicate`, `balance`, `applied-lie`, `conservation`,
    `record`, `unknown-result`), never the seed or the commit; a known fingerprint gets a comment
    for a commit not yet reported, at most 4 a day. The issue carries the seed, the commit, the
    exact command, the checker's verdict (`results.edn`, bounded), **the history**: the anomalous
    operations with 50 operations of context on each side, at most 48 KiB, and the archive's path
    on the host. Status `failure`;
  - **the host's** (exit 137, the deadline, a build that failed, Docker down): counted, a status
    `error`, never an issue;
  - one comment a day on a tracker issue, as the fleet's: what ran, on which commit, the verdict.
    A day without one is the alarm.
- Its token is not the fleet's (owner question 3).

## Risks

1. **The host is late.** Slices 1 to 6 do not wait for it, and the hosted runner proves each
   workload; R1 is still not delivered until the host's 7 nights. Botpike's gate waits too.
2. **16 GB is tight on the hosted runner** with two gateways per node: about 7 GiB of replicas,
   1 to 2 GiB of gateways, a 4 GB JVM; `lose-unfsynced-writes` adds 5.4 GiB of LazyFS cache (1.08 GiB
   a node, resident from mount to unmount, P242i), measured headroom in P242i. If it OOMs (exit 137, as #107), the hosted runs drop to
   `-Xmx3g` and one gateway per node for nemeses that do not need two.
3. **Jepsen runs do not replay.** A seed narrows, not reproduces; a failure costs a VOPR seed or a
   unit test to pin down before its fix (N82).
4. **The fleet loses about 2.5 h a night** (about 10% of its seeds).
5. **A test build in the wrong place.** E0717 refuses it without `--development`, W0701 logs every
   start, and `version` names it; release builds cannot produce it.
6. **The issue holds an excerpt, not the whole history.** The whole store stays on the host for
   90 days; a reviewer without host access gets the hosted runner's re-run.
7. **The token** can write issues and statuses: a compromised host can post a false green. The
   statuses are evidence for the release gate (P147b), so the owner reviews the first week by hand.

## Owner questions

1. **The teeth as a build option** `-Dtest-commit-keys=off` (a one-option patch to `build.zig`,
   which UPSTREAM.md lists as rewritten), or as a `nerva start` flag refused without
   `--development` (no vendored change, but a release binary can then switch keys off)? **The
   build option:** a binary that holds money can never skip the key check, and every replica runs
   the same build by construction.
2. **Clock faults need separate kernels:** five KVM guests on the host (slice 10), or cut clock
   faults from R1 and record the cut? **Keep them, as slice 10**, after delivery: Hetzner's
   dedicated servers expose KVM, and VSR's clock synchronisation has never met a skewed clock
   outside the VOPR.
3. **The nightly's token:** a second fine-grained PAT (Issues and Commit statuses), apart from the
   fleet's (Issues only)? **A second token:** the Jepsen user is root-equivalent through Docker,
   and the fleet's token should not be within its reach.
4. **The full history:** a 48 KiB excerpt in the issue and the store on the host (90 days), or also
   the full history as a secret gist (the token gains Gists write)? **The excerpt and the host:**
   the excerpt holds the anomaly, and the token stays at two permissions.
