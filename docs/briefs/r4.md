## Goal

A gateway beside its client answers every request it accepts within a stated bound, saying with
a code whether it was not applied (`false`) or may have been (`"unknown"`), and operators see it
through statsd. The only silence is the gateway's own death, which commit keys make safe.

## Non-goals

- **TLS and callers off the machine:** the gateway serves loopback (owner question 2).
- **More than one cluster request at a time.** One thread, one session (`server.zig:1-6`);
  throughput comes from P143's groups and one gateway per client process. The native client is R8.
- **Jepsen workloads and nemeses** (`retry`, gateway kill and partition) are R1's; R4 only lets
  the suite start gateways as R4 documents them (slice 6).
- **Metrics from `nerva view`:** it gets the `Receiver`'s fixes and the codes, nothing else.
- **Conservation as a replica metric:** cut (owner question 5). **Per-caller limits:** behind
  loopback the caller is the client process.

## What exists today

**One thread, one session, one cluster request at a time.**
- `api_server.serve` (`src/nerva/api/server.zig:38-91`) loops: `receiver.next`, one request or
  one P143 group (`:67-86`), the reply. While a cluster request runs, the gateway reads, accepts
  and answers nothing, `/healthz` included; connections wait in the kernel's backlog (Zig's
  default, 128).
- The cluster client's timeout is 30 s, hard-coded (`src/nerva_main.zig:840`; `:822` for `view`).
  After `error.Timeout` "the request may still commit" (`src/nerva/client.zig:5-6`). Every request
  leaves through `Client.send` (`client.zig:583-601`). Botpike's client gives up after 5 s
  (`NervaConfig.kt:14`): it sees a gateway still waiting on the cluster as "unknown".

**How a request is refused or cut** (`src/nerva/http_connection.zig`).
- 16 slots (`server.zig:23`, `view/server.zig:25`). With every slot busy, a waiting connection
  displaces the oldest one still reading once it is 50 ms old, **closed with no reply**
  (`:357-392`, `displace_grace_ns` `:603`). That is #120: a request cut part-way through its body,
  which OkHttp reports as a bare 503 and the client cannot tell from a lost commit.
- A request not whole within 10 s is **closed with no reply** (`expire`, `:552-561`). A malformed
  head or a body over 4 MiB gets `400`, a shutdown and a drain of what has arrived (`refuse`,
  `:490-503`); a body still arriving can turn the close into a reset that destroys the reply.
- The listener sets `SO_REUSEADDR` and `SO_REUSEPORT` together (`:226`): a second gateway on the
  port binds silently and shares its connections (#112). `take` (`:285-311`, P143) never displaces.

**What a 503 means today.** `{"error":"cluster unavailable"}` is answered both when the session
is broken and the request was **never sent** (`server.zig:193`, `:142-143`) and when it timed out
or was evicted **after it was sent** (`:196-201`, `:147-154`); ERRORS.md files both as NRV-E0601,
"outcome unknown". `views_busy` (`api/api.zig:1097-1101`) was never applied; "index building" and
"view still building" (`:1869`, `:2284`) are reads. A client cannot tell any of them apart.

**`/healthz`** (`server.zig:177-181`, `src/nerva/client_health.zig`). `ClientHealth` breaks only
when a request times out or is evicted (`:41-45`), then retries every 5 s (`:15`, `:68-72`). An
idle gateway whose cluster has gone answers `200` indefinitely.

**Error replies.** `api.error_reply` (`api/api.zig:2423`) writes `{"error": "<text>"}`, commit
results `{"status": …}` (`:1030-1120`); no reply carries a code. A body over 4 MiB answers `400`
(`http_connection.zig:476-478`, NRV-E0102). "Not yet committed" is `400` on `/v1/row`,
`/groups` and documents (`api.zig:1536`, `:1541`, `:2092`) and `504` on `/v1/views/<n>`
(`:2274-2276`, NRV-E0401). An unexpected commit status panics the gateway (`api.zig:1051`,
`:1116`, `documents_routes.zig:319`, NRV-B0002).

**Commit keys** (P123, README `:87-97`) make a resent `/v1/commit` apply at most once. What stays
ambiguous: an unkeyed `/v1/commit` with adds or blind puts; `/v1/documents/commit`, which takes no
key (`documents_routes.zig:1-24`: with reads a resend conflicts, a blind write applies again);
and a replayed commit's adds, answered without amounts (README `:93`; read as of its op).
Declarations are idempotent ("created or exists") and reads change nothing. Botpike's JSON
reader ignores unknown members (`wire/NervaJson.kt:21`).

**Metrics and listening.** Gateways export nothing (N50); replicas use the vendored tracer
(`src/trace/statsd.zig`, events `src/trace/event.zig:568`), and new events patch a vendored file.
`--listen` takes any address (`cli.zig:567`): Jepsen binds `0.0.0.0` (`db.clj:71`), every test
and INF-2 bind loopback.

## Design

### The answer contract

What the slices implement, and README's new "What a reply means":

1. **Every connection the gateway accepts gets a status line before it is closed**, unless the
   process dies. A transport error without one means the gateway died: unknown, resend under the
   key to the restarted gateway.
2. **Every non-`2xx` reply carries `"code"` (ERRORS.md) and `"applied"`**: `false` (nothing
   reached the cluster, or the cluster refused it) or `"unknown"` (a write went out and no reply
   came back), beside today's `error` or `status`, whose spellings stay (P147c). A replayed commit
   gains `"code":"NRV-W0201"`.
3. **The answer bound.** A request that has arrived whole is answered within `queue_wait_max` +
   `--request-timeout` + `reply_margin` (32 s by default). A client whose timeout is longer always
   gets the gateway's answer; INF-2's settings follow from it (owner question 3).

### `applied`, from what was sent

`Client` gains `writes_sent: u64`, counted in `send` for the writes (`commit`, `commit_wide`,
`declare_view`, `declare_ledger`, `declare_index`; `Operation.is_write()` in `src/nerva.zig`, an
exhaustive switch, so a new operation must choose). `serve_request` and `serve_group` snapshot it:
a failure with it unchanged is `false`; after a write went out (`Timeout`, `Evicted`, any error
after a write's reply) it is `"unknown"`, for every member of a failed group request.

| What happened | Status, body (new members in **bold**) | Code |
| --- | --- | --- |
| Every slot is taken by a connection that has sent bytes, and another connection waits | `503 {"error":"busy",`**`"applied":false,"code":"NRV-E0602"`**`}`, sent without reading anything | E0602 |
| A silent connection is displaced (no byte in its 50 ms grace) | the same `503 busy`, written before the close | E0602 |
| A request complete but not sent within `queue_wait_max` | the same `503 busy` | E0602 |
| Not whole within 10 s | `408 {"error":"request not received within 10 s",…false}` | E0116 (new) |
| Malformed head, or body over 4 MiB | `400 …` (unchanged), and **`413`** for the body (owner question 1) | E0101, E0102 |
| The session is broken: not sent | `503 {"error":"cluster unavailable",…false}` | E0605 (new) |
| Sent, and no reply (timeout, eviction) | `503 {"error":"cluster unavailable",`**`"applied":"unknown"`**`,…}` | E0601 |
| `views_busy` | `503 {"status":"views_busy",…false}` | E0211 |
| An op not yet committed, on any route | **`504`** (owner question 1) | E0401 |
| An unexpected commit status (today a panic) | `500 {"error":"internal error",…"unknown"}` | B0002 |
| Any other 4xx (refusals, `409` results) | today's body plus `false` and its code | as registered |

`/healthz` gains `code` on `503` and `"session"`: `"ready"` or `"reconnecting"`.

### The `Receiver` (`http_connection.zig`, shared by `api` and `view`)

- **Its own listening socket:** `socket`, `SO_REUSEADDR` only, `bind`, `listen(listen_backlog)`.
  A second process on the port gets `AddressInUse`, reported as NRV-E0007. Closes #112.
- **No silent close.** `shut(slot, status, body)` writes the reply, shuts down the send side and
  moves the fd to a `lingering` table polled for EOF, discarding what arrives for at most
  `linger_ns` or `linger_bytes_max`, so a reset cannot destroy the reply (table full: closed at
  once, counted). `refuse`, `expire` and displacement go through it.
- **Who is refused.** With every slot taken, the oldest connection that has sent **zero bytes**
  and is past `displace_grace_ns` is displaced (#28's defence, kept); failing that, the waiting
  connection is accepted and answered `503 busy` at once, unread and without a slot (at most
  `refusals_per_wake_max` a wake). A connection that has sent bytes is never displaced: #120.
  `take` (P143) is unchanged.
- **The queue bound.** Before `next` hands out a request, and before `take` adds one to a group,
  every complete request older than `queue_wait_max` is answered `503 busy`, so the answer bound
  holds whatever the round before took.

### The session and `/healthz`

- **`--request-timeout=<ms>`** on `api` and `view`: 1,000 to 60,000, default 30,000 (today's),
  into the client's `Options.timeout`; out of range is NRV-E0002.
- **A probe.** Idle with no cluster reply for `health_probe_interval`, the gateway sends one read
  (`lookup_rows` of one catalog row); a probe that times out breaks the session as a request
  would. `/healthz` then says `503` within `health_probe_interval` + `--request-timeout` of the
  cluster going (a busy gateway, within `--request-timeout`). Cost: one op per idle gateway per
  5 s. A hook on `pong_client` in vendored `vsr/client.zig` would cost no op but is a vendored
  patch (R5's question 6 declined the same hook).

### Metrics (`src/nerva/api/metrics.zig`, Nerva's own)

`nerva api --statsd=<host:port>` (`start`'s parser, `cli.zig:695`) sends UDP every
`statsd_interval` from the main loop, non-blocking, packets of at most `packet_size_max`; a failed
send is counted and dropped. The replicas' format (DogStatsD tags, so the same `statsd_exporter`),
prefix `nerva.api.` (not the vendored tracer's events, so N50's reason for `tb.` does not apply),
tags `cluster` and `listen` on every line. Aggregates are fixed arrays sized by comptime enums
(`Route`, today's routes plus `healthz` and `other`; `RefusalReason`; `Operation`): cardinality is
bounded.

| Name | Type, tags | Counts |
| --- | --- | --- |
| `nerva.api.requests` | counter; `route`, `status` | Every reply written |
| `nerva.api.refused` | counter; `reason`: `busy`, `displaced`, `queue_wait`, `deadline`, `malformed`, `too_large`, `unavailable` | Replies with `applied: false` written by the gateway itself |
| `nerva.api.unknown` | counter; `route` | Replies with `applied: "unknown"`: the one to page on |
| `nerva.api.group_size` | `min`, `max`, `avg`, `sum`, `count` | Requests per cluster request (P143) |
| `nerva.api.cluster_request_us` | timing; `operation` | From `send` to reply or failure |
| `nerva.api.queue_wait_us` | timing | From complete to sent |
| `nerva.api.reconnects` | counter; `result`: `ok`, `failed` | `ClientHealth.ready` attempts |
| `nerva.api.session` | gauge, 1 or 0 | Ready at the end of the window |
| `nerva.api.connections` | gauge | Slots in use, the window's maximum |
| `nerva.api.lingering_dropped`, `nerva.api.statsd_dropped` | counters | Bounds that were hit |

### Loopback by default (owner question 2)

A `--listen` that is not loopback (`127.0.0.0/8`, `::1`; `0.0.0.0` and `[::]` are not) is refused
with NRV-E0009 unless `--listen-remote` is given, which logs a warning about the plain-HTTP key
(README, "Network"). Jepsen's `db.clj` passes it.

### Documents under a key (owner question 4)

`/v1/documents/commit` takes an optional `"key"`, sent as the first entry exactly as `/v1/commit`
sends it (P123), with the same `replayed`, `key_reused` and `key_collision` replies. No state
machine change: a documents commit is already a `commit`.

### The sidecar topology (README, "Running a cluster")

A new subsection, "Gateways beside their clients": one `nerva api --listen=127.0.0.1:<port>` per
client process, with every replica's address; the process starts once `/healthz` answers and
stops taking work on `503`; its timeout above the answer bound; sessions (64 per cluster; every
gateway, `nerva view`, export, recover and Zig client takes one; a 65th evicts the least recent);
ports (client machines reach every replica's port; nothing reaches the gateway's).

**Formats:** the data file, the replica protocol and every persisted identifier are unchanged; no
`Operation` or `tree_id`. The JSON wire gains `code`, `applied`, `/healthz`'s `session` and
documents' `key`, all additive. Two statuses change, a stop unless owner question 1 approves them:
body too large `400` → `413`, not yet committed `400` → `504`.

## Risks

1. **The answer bound needs the client's timeout above it.** Botpike's 5 s against today's 30 s
   leaves "unknown" on the client's side whatever the gateway does: INF-2 sets
   `--request-timeout` below its call timeout (about 3 s for 5 s) or raises the call timeout. A
   view change longer than that answers `"unknown"` and reconnects, safely under keys.
2. **`queue_wait_max` refuses work after a slow op:** one 2 s op makes everything behind it
   `busy`. Clients must back off, or a slow op becomes a retry storm;
   `nerva.api.refused{reason:queue_wait}` shows it.
3. **Lingering is best-effort.** A client still sending a large body after a refusal may see a
   reset: unknown, and safe under a key. The tests use loopback and small bodies.
4. **Unkeyed writes stay ambiguous** after a gateway's death or `"unknown"`: keys are opt-in.
5. **Probes cost ops** (about 13 a second for 64 idle gateways), and a timed-out probe a session.
6. **Sessions.** A fleet of more than about 60 client processes on one cluster evicts sessions in
   turn. Raising `clients_max` changes the data file's client table: a format change, out of
   scope. README says so.
7. **Jepsen does not prove R4 until R1 runs** its `retry` workload with two gateways per node;
   until then `test:api`'s busy and stall cases and the demo are the evidence.
8. **The status changes** break a client that matches `400` for "not yet committed". Botpike maps
   `400` and `413` alike and `504` as unavailable (`NervaError.kt:27`, `NervaView.kt:13`).
   CHANGELOG says so.

## Owner questions

1. **Two status changes:** body too large `400` → `413`, "not yet committed" `400` → `504` on
   every route. PRODUCTION and P147c name them, but they are not additive (stop 1). Approve them
   as named? **Yes**: one cause, one status, and Botpike's client already maps both.
2. **Loopback only unless `--listen-remote`**, or only a warning, or neither? **Refuse**: P147g's
   point is that the key and plain HTTP never cross a network. Jepsen passes the flag; anyone
   binding `0.0.0.0` gets one CHANGELOG upgrade step.
3. **`--request-timeout`** as a flag (default 30 s), with the answer bound documented as the
   client's minimum timeout, or a lower fixed 30 s? **The flag**: the right value follows the
   client's call timeout, which Nerva cannot know.
4. **A key on `/v1/documents/commit`** now (additive, no state machine change), or document
   writes left ambiguous? **Add it**: otherwise "unknown" has no safe resend for documents.
5. **"Conservation as a metric."** Replicas hold no ledger totals: export reads every row to
   compute them (`src/nerva/export.zig:206-220`). A total kept from applied deltas is zero by
   construction and would never show a break; a true one needs a scan or a persisted total (a
   format change) and new tracer events (a vendored patch), and it is replica work. Cut it from
   R4 (PRODUCTION corrected, filed for later), or add replica gauges of each view's `view_hash`
   at checkpoints (divergence, not conservation) as a last, cuttable slice? **Cut it**: Botpike's
   watch reads a `sum` view already, and `nerva view` recomputes it independently (N35).
6. **Metrics over statsd** with Nerva's own emitter, as PRODUCTION says, or a Prometheus
   `/metrics` on the gateway? **Statsd**: one format for every Nerva process; Botpike runs
   `statsd_exporter` already, and now needs one beside the app.
7. **Delivery.** R4 is delivered when `demo_r4` is green; PRODUCTION's "Jepsen R1 runs with two
