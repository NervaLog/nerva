## Goal

Someone who is not us downloads Nerva v0.7.1 for Linux or macOS, installs it the way their
platform expects, follows one page from nothing to a three-replica cluster and a first committed
request, and finds in the docs how to size, back up, upgrade, recover, secure and troubleshoot it,
and what the label promises about their data. The release is the first cut under the full gate:
24 hours of the fleet and a Jepsen night on the candidate, and two adversarial reviews.

## The outside user's story

1. On a Mac: `brew install nervalog/tap/nerva`, then `nerva version`. The binary is universal,
   signed with a Developer ID and notarized; a browser download of the zip runs too.
2. On Linux: the release tarball for their architecture (or a `.deb` or `.rpm`). `sudo ./install.sh` puts `nerva` in `/usr/local/bin`, a `nerva` user, `/var/lib/nerva`
   and a `nerva@.service` systemd template unit in place, and formats nothing.
3. `docs/QUICKSTART.md`: three replicas on one machine with `--development`, a gateway, a table,
   a commit, a lookup, the change feed; then the same three on three machines with a cluster key.
   Under 15 minutes, every output shown is recorded from v0.7.1.
4. `docs/OPERATING.md` says what a replica needs (memory, disk, CPUs, the file system), how to
   back up and restore, how to replace a lost replica, how to upgrade (v0.7.x in place; the next
   protocol release by export and import), and what to watch.
5. A refusal prints `error[NRV-E…]`; `docs/TROUBLESHOOTING.md` finds that code and says what to
   do. `SECURITY.md` says what `NERVA_KEY` and the cluster key protect, what they do not, and how
   to report a vulnerability.
6. `docs/MATURITY.md` says what the label promises: which upgrades keep data, what may change,
   what was tested (the fleet's line, the Jepsen night) and what was not.

## Non-goals

- **No protocol, format or state machine change.** v0.7.1 stays on release `0.0.6` with v0.7.0's
  format digest. P259b moves the string with every `VERSION` only from vR (the first release that
  ships R6) on. A slice that finds it must change the state machine, a wire or data format, or a
  persisted identifier stops (CLAUDE.md, items 1 and 4), and the change moves to a later release.
  The P275 audit (slice 7) proves this release adds no new kind of op.
- **No R3, R6 or R7 work.** Sizing in the docs is what was measured (#127, `perf/`), labelled as
  measured on one host; rolling upgrades and retention are named as not there yet.
- **No signed apt or dnf repositories, and no signed packages.** Zigbox runs them; Nerva may
  follow after 0.7.1 (owner question 2). v0.7.1's `.deb` and `.rpm` are unsigned release assets
  checked by `SHA256SUMS`.
- **No Apple secret outside the `apple-signing` environment.** The Apple secrets are secrets of that
  GitHub environment, which the owner approves for each run; they reach only the keychain step of
  `mac-sign.yml`. The owner's laptop signing remains the fallback.
- **No macOS production support.** macOS is for development and evaluation (owner question 5,
  a supervisor default);
  production is Linux. No VM, so no entitlements.
- **No Homebrew core, no Linux Homebrew, no Windows, no container image for outside users.**
  (`perf/fly/Dockerfile` and Botpike's `fly/nerva/` stay internal.)
- **No rewrite of the README or the tutorial.** Slice 6 adds the missing pages and links to what
  exists; it fixes stale facts in place and moves nothing.
- **No change to the existing asset names or layout.** Botpike's `scripts/nerva.sh` pins the
  sha256 of all four `nerva-<tag>-<target>.tar.gz` and runs `nerva-<tag>-<target>/nerva`;
  slices add files and assets beside them and rename nothing.
- **Botpike's pin bump** (Botpike/app#159, #160) is Botpike's change. The notes say what it must
  do.

## Design

### The soak: where the candidate runs

Both services already take a branch. For the soak the owner points both at **a frozen commit on
`main`**, the candidate (owner answer 3, 2026-11-10). There is no `release/v0.7.1` branch.
Both services fetch `origin <branch>` and check out what they got (`run.sh:227`,
`nightly.sh:133`), so the owner sets `SIM_FLEET_BRANCH` and `JEPSEN_BRANCH` to the candidate's
full 40-character SHA, which GitHub serves to `git fetch`. Slice 1 proves that on the host's
checkout and, if it fails, adds a commit pin to those two scripts (it then also owns
`ops/sim-fleet/run.sh` and `ops/jepsen/nightly.sh`). `main` keeps moving, and the release is cut from the candidate even if `main` has moved on,
which CLAUDE.md allows. A fix found during the soak merges to `main` and the owner moves the pin
to the new commit; the soak restarts there. When the soak ends the pin is removed.

- **24 hours means 24 hours of fleet rounds on the candidate commit**, counted from the rounds'
  own records, not wall time. Jepsen's window stops the fleet for about 2.5 h a night, so the soak
  takes about 27 hours of wall time.
- **The Jepsen clause** is one night on the candidate in which both `retry` and `bank` are
  `:valid? true`: commit status `jepsen/nightly` `success` on the candidate SHA. The owner may
  start the night by hand (`systemctl start jepsen.service`) inside the soak rather than wait for
  01:17.
- **The candidate moves** only for a fix, merged to `main` first. A change to anything but Markdown restarts both clauses
  on the new SHA; a Markdown-only change does not (CI already treats it that way, N68).
- **The release commit** (the `VERSION` bump, its worklog note and the dated CHANGELOG heading) is
  the candidate plus Markdown and `VERSION` only. Slice 7's release-PR check says so from
  `git diff --name-only`.

**Nerva-side work, the only code the gate needs:** the fleet must be able to say "commit X ran
24 hours". `sim_fleet.py` gains, per commit, the fleet-hours and seeds per kind (from the rounds
it already ingests), shown in each daily tracker comment as one line per commit that ran that day,
and a subcommand `sim_fleet.py soak --commit SHA --state FILE` that prints the line the release
PR quotes:

```
soak 1a2b3c4: 24.6 h, vopr-nerva 182,311 seeds, vopr-testing 15,020, fuzz 9,874; 0 failures; open sim-fleet issues against it: none
```

The state file keeps per-commit totals for the last 64 commits (bounded; the oldest is dropped).
"Open issues against it" is every open `sim-fleet` issue whose last reported commit is the
candidate, from the state the reporter keeps (`filed[...]["last_commit"]`).

### macOS: one universal binary, signed by the owner

**A universal binary, not two thin ones.**
- One file to sign, notarize, checksum and put in one Homebrew formula with one `url` and
  `sha256`, as Zigbox's formula has; the user cannot download the wrong architecture.
- The two slices are the two thin binaries `release.yml` already builds, joined with `lipo`. CI
  runs the same join ad hoc (below), so each slice is tested on its own architecture.
- If macOS ever runs multiversion binaries (R6 rules it out for now), upstream's packing on macOS
  needs a universal binary. The Mac release format would not have to change.
- **Cost:** about twice the download, and `lipo`, which comes with the Xcode command line tools
  that `codesign` and `notarytool` already need on the owner's Mac and that GitHub's macOS
  runners carry. It is a release-time program, never run by `nerva` or the Linux CI.

**`zig build mac-release`** (slice 3), mirroring Zigbox's step and run only on a Mac:
1. It refuses unless the tree is clean, `HEAD` is the tag `v<VERSION>`, and (unless
   `-Dsign-identity=-`) the notary profile exists in the keychain. It refuses before signing
   anything.
2. It builds `aarch64-macos` and `x86_64-macos` in ReleaseSafe (`-Drelease`), then `lipo -create`s
   them into a universal binary and checks `lipo -archs` gives `x86_64 arm64`.
3. It signs with `codesign --force --options runtime --timestamp --sign <identity>` and no
   entitlements file. It checks with `codesign --verify --strict` and `codesign -dv`
   (`Authority=Developer ID Application`, `flags=0x10000(runtime)`, a `Timestamp`).
4. It runs the signed binary: `nerva version` (first line `+<tag's short commit>`, and the
   version line `version 0.7.1`, below), then a `nerva format --development` into a temporary
   directory, so the hardened runtime is known not to break it.
5. `ditto -c -k --keepParent` zips `nerva-v<VERSION>-universal-macos/` (the binary, `LICENSE`,
   `NOTICE`) into `nerva-v<VERSION>-universal-macos.zip`. It checks that the unzipped binary's
   CDHash equals the signed one, then writes `<zip>.sha256`.
6. With `-Dnotarize=true`: `xcrun notarytool submit --keychain-profile <profile> --wait`, and it
   fails unless the status is `Accepted`. A bare Mach-O cannot be stapled, so the ticket stays
   with Apple (Zigbox's m4b.md says what that means for Gatekeeper).
7. It fills `packaging/homebrew/nerva.rb`'s `@VERSION@`, `@URL@` and `@SHA256@` into
   `zig-out/mac-release/nerva.rb`. The output directory is emptied first.

Options as Zigbox's: `-Dsign-identity=<name>` (default the owner's Developer ID Application
identity; `-` signs ad hoc), `-Dnotary-profile=<name>` (default `nerva-notary`),
`-Dnotarize=true`. It never reads, prints or logs a secret: the keychain holds them. From an ssh
or sandboxed session `codesign` fails with `errSecInternalComponent`, and the tool says so in one
line. Its failures are tooling messages, not NRV codes: only the owner runs it, as with the
Jepsen suite's messages (P215c).

**The tap** is a new public repository, **`NervaLog/homebrew-tap`**, holding `Formula/nerva.rb`
(`brew install nervalog/tap/nerva`), created by the owner as Zigbox's was. The template lives
here, in `packaging/homebrew/nerva.rb`. The formula installs the prebuilt universal binary pinned
by sha256, with `depends_on :macos` and no `arch` restriction, builds nothing, and needs no
`sudo`. Its `test do` runs `nerva version` and checks `version #{version}`. Homebrew core is not
an option: an alpha with one maintainer does not meet its notability rules.

**No Apple secret outside `apple-signing`** (slice 2, and the release): the `macos` job in `ci.yml`
runs ad hoc and holds none. The release's signing job is `mac-sign.yml`. It runs on a hosted
`macos-15` runner, waits for the owner's approval of the `apple-signing` environment (the owner is
its required reviewer, and `main` its only deployment branch), and gives the five Apple secrets only
to the step that creates a temporary keychain. The repository is public, so GitHub's hosted macOS
runners are free. The owner's laptop path remains the fallback.

### Linux: a tarball that installs, and packages

**Slice 4, no new dependency:** each Linux tarball gains, beside `nerva`, `LICENSE` and
`NOTICE`:
- `install.sh` (POSIX sh). As root it puts `nerva` in `/usr/local/bin` (it refuses to replace
  one of another release unless given `--upgrade`), creates the system user `nerva`,
  `/var/lib/nerva` (0750) and `/etc/nerva/` (0750), installs `nerva@.service` and
  `nerva-api@.service` to `/etc/systemd/system/`, and runs `systemctl daemon-reload`. It never
  formats, starts or enables anything, and prints the next three commands. `--uninstall` removes
  the binary and units and leaves `/var/lib/nerva` and `/etc/nerva`. It is idempotent, and
  `--dry-run` prints what it would do.
- `nerva@.service`: one replica per instance (`nerva@0`), `User=nerva`,
  `EnvironmentFile=/etc/nerva/replica-%i.env` (`NERVA_ADDRESSES`, `NERVA_CLUSTER_KEY`, the data
  file's path, extra flags), `ExecStart=/usr/local/bin/nerva start …`, `Restart=on-failure`,
  `LimitMEMLOCK=infinity`, `LimitNOFILE=…`, a hardening set (`NoNewPrivileges`,
  `ProtectSystem=strict`, `ReadWritePaths=/var/lib/nerva`, `PrivateTmp`). Its
  `RestartPreventExitStatus=` lists the `nerva start` exits that a restart cannot fix (7, 8; the
  slice checks each in ERRORS.md).
- `nerva-api@.service`: a gateway per instance, `EnvironmentFile=/etc/nerva/api-%i.env`
  (`NERVA_KEY`, `--listen`, `--statsd`), loopback by default.
- `replica.env.example` and `api.env.example`, each line commented.

**Packages (slice 5, owner answer 2).** `release.yml` builds a `.deb` and an `.rpm` per
architecture with the standard tools, `dpkg-deb` and `rpmbuild`, beside the tarball. The owner
approved this new tool dependency on 2026-11-10 (recorded in P284b). No Python packager, and
no vendored one.

- **Which runner, how installed.** Both run on `release.yml`'s Ubuntu runner (`ubuntu-24.04`,
  pinned by label as the other jobs are). `dpkg-deb` is part of `dpkg`, already on the image.
  `rpmbuild` comes from `apt-get install -y rpm`, which on `ubuntu-24.04` resolves to rpm
  4.18.x. The job pins the version it installs (`rpm=<version>`, read from the image's apt
  index when the slice is written), prints `rpmbuild --version`, and fails if it differs, so a
  runner image change shows as a failure and not as different bytes. The slice records the
  version in its PR.
- **Both architectures from one x86_64 runner.** The binaries are already built, so nothing is
  compiled: `dpkg-deb --build` takes `Architecture: amd64|arm64` in `control`, and `rpmbuild -bb
  --target x86_64|aarch64` takes the prebuilt binary through the spec's `%install`. The slice
  checks that `rpmbuild` accepts a foreign `--target` with no compiler and no `BuildRequires`.
- **Unsigned.** No GPG key exists for Nerva and none is created for 0.7.1 (recommendation
  accepted as the default). Each package is a release asset covered by `SHA256SUMS`, which
  `release.yml` already writes. `INSTALL.md` says so, and says how to check the sum. Signed
  repositories are a later release's decision.
- **Tests, installed in CI in containers** `ubuntu:24.04`, `debian:12`, `rockylinux:9` and
  `fedora:latest`: four public images pulled by CI only (Jepsen's CI already pulls images).
  One thing to check: rpm 6 (Fedora 43 on) is believed to enforce signatures by default. If
  `fedora:latest` refuses an unsigned rpm, v0.7.1's rpm is documented for RHEL 9 compatibles
  and Fedora 42 and below, and signing waits for a later release. The slice records what it
  found.

Package names: `nerva`, version `0.7.1`, release `1`, arch `amd64`/`arm64` (deb) and
`x86_64`/`aarch64` (rpm). Files: `/usr/bin/nerva` (packages own `/usr/bin`; the tarball's
`install.sh` uses `/usr/local/bin`), the two units in `/usr/lib/systemd/system/` (**the same
unit files slice 4 ships, byte for byte**, not copies that can drift: the packages take them
from `packaging/linux/`), the examples in `/usr/share/doc/nerva/`. The maintainer scripts only
create the user and directories. They never start, enable, format or remove data, and removal
leaves `/var/lib/nerva`. Builds are reproducible: fixed mtimes (`SOURCE_DATE_EPOCH` from the
commit), sorted entries, `root:root`.

### `nerva version` names the release

The last line of `nerva version` becomes `version 0.7.1`, read from `VERSION` at build time
(`-Dversion`, default `VERSION`'s contents). The first line, which Botpike and `release.yml`
parse (`head -n1`, Botpike/app#160), is unchanged. The format digest is unchanged: the version is
not part of it, and two builds of one commit under different `VERSION`s are the same protocol.
Slice 3 does it, because `mac-release` and the formula need it. The patch is to `build.zig` and
to `src/nerva_main.zig`'s version printer. **The owner approved both vendored patches
(2026-11-10, P284b), so this is not a stop under CLAUDE.md item 2.** Each must still be minimal
and recorded in UPSTREAM.md in the same commit as the patch.

### Release mechanics (slice 7)

**Order of operations:**

1. **Prep PR** (docs only): the CHANGELOG section `## v0.7.1 — <date>`, dated in this PR (retro,
   "smaller things"); the P275 audit as `docs/releases/v0.7.1-audit.md`; the candidate SHA. It is
   merged before the soak, so the candidate includes it.
2. **Soak** on the candidate, one frozen `main` commit: the owner pins the host to it (above). In
   parallel, **two reviewers** (Opus, fresh sessions, P147b) review the candidate against
   `v0.7.0`: every change, the packaging and install scripts, the units, `mac-release`, and the
   docs read as an outside user would. Each also runs `zig build -Drelease mac-release -Dsign-identity=-`
   on a hosted Mac (dispatching `ci.yml` is enough) and does an install on a clean container.
   Findings are `release-review` issues.
3. **Blockers fixed** (each merges to `main`, moves the candidate and restarts the soak), or waived by the owner in
   writing.
4. **Release PR:** `VERSION` = `0.7.1` and `worklog/<n>.md` in their own commit, nothing else. Its
   description quotes the `sim_fleet.py soak` line, the `jepsen/nightly` status link on the
   candidate, both verdicts, and the label. Merging it starts `release.yml`.
5. **`release.yml`**: as today, plus the four Linux packages (with `rpm` installed as above and
   their checksums in `SHA256SUMS`) and **a draft release**
   (`gh release create --draft`). Botpike's assets and names are unchanged.
6. **The `mac` job waits for the owner's approval of `apple-signing`.** It signs, notarizes and
   uploads the zip and its `.sha256` to the draft, then `mac-verify` runs on the draft. The owner
   publishes once it is green (`gh release edit v0.7.1 --draft=false`) and commits the
   `homebrew-formula` artifact to `NervaLog/homebrew-tap` as `Formula/nerva.rb`. Fallback: P311's
   laptop block.
7. **`mac-verify.yml`** runs on the draft automatically, after `mac`; dispatching it is for re-runs
   only. On `macos-15` and `macos-15-intel` it downloads the zip, checks its `.sha256`, checks
   `codesign -dv` shows `Authority=Developer ID Application` and the hardened runtime, and runs
   slice 2's smoke test on that binary. On `release: published` it also runs
   `brew install nervalog/tap/nerva && brew test nerva` (brew is skipped on a draft). Its run link
   goes in the retro and on the site.
8. README's status line and the site's `RELEASES` (nervalog.github.io) in the same session; the
   retro within a day.

**Why a draft:** outside users and Homebrew should never see a v0.7.1 without its Mac build, and
the notes should name the zip from the start. A draft has no tag until it is published. So
`release.yml`'s "already released" check also refuses when a draft named `v<VERSION>` exists:
re-running the workflow must not make a second draft.

**`release.yml` also:**
- refuses to publish a binary built with commit-key deduplication off (#271): it runs the built
  Linux x86_64 binary's `nerva version --verbose` and requires the line that names the keys-on
  build. If no such line exists, slice 7 adds it to `--verbose` only.
- checks the `version` line equals `VERSION`.
- puts slice 4's files in each Linux tarball and calls slice 5's script.

**The release notes must say:**
- The label and a link to `docs/MATURITY.md`: what it promises about data and upgrades. In
  short: v0.7.x data files open in place in every v0.7.x; the next protocol release (vR, R6)
  moves by export and import (P259g); the export format v1/v2 is read by at least the next
  release (N80).
- How to install on each platform, with links to `docs/INSTALL.md` and `docs/QUICKSTART.md`.
- What was tested, quoted: the soak line, the Jepsen night, the two reviews (with their issues),
  and that `mac-verify` ran the signed binary on both Mac architectures.
- **Upgrading from v0.7.0:** replace the binary, one replica at a time, then gateways in any order.
  This holds only because the audit shows no new kind of op and no state machine change (P275).
  If the audit finds otherwise, this line is wrong and the release stops.
- **Upgrading from v0.6.1:** P260's order still applies (every replica before any gateway; roll
  back only if no v0.7.x gateway has run). For Botpike, Botpike/app#159 and #160: bump the
  replicas' pin first, and parse `nerva version`'s first line only.
- `nerva version`'s new last line.
- macOS: the universal zip and Homebrew are signed and notarized. The `*-macos.tar.gz` assets
  stay for scripts that pin them and are ad hoc (arm64) or unsigned (x86_64).
- Fixes with their issues (#278, #271, and whatever the soak and the reviews find).

## New error codes

`11xx · Installation and packages` (a new range in `docs/ERRORS.md`), for `install.sh` and the
package maintainer scripts, which an operator runs. Each is one line, `error[NRV-E11xx]: …`, with
exit 1 (the operator's input) or 2 (the environment). Proposed, numbered by slice 4:
- not root;
- no systemd;
- a different `nerva` already installed (pass `--upgrade`);
- an unsupported architecture or a missing `sha256sum`;
- a unit or user that exists but is not ours.

Each gets its test in `tests/packaging/` (slice 4). `mac-release`'s messages are tooling, not
codes (above).

## Risks

- **The host is the critical path.** Every other slice can finish in days; the soak cannot start
  until the host has run a day and passed both canaries. The default (owner question 6) is that the
  release waits.
- **The first soak finds something.** That is the point; it moves the candidate and restarts the
  clock. Budget for at least one restart.
- **macOS runtime breaks beyond #277.** `test:unit` on a Mac may show more vendored assumptions.
  Vendored ones are a stop (slice 2).
- **The hardened runtime.** Nerva needs no entitlement, but nothing has run a hardened Nerva:
  `mac-release` step 4 runs it before it is zipped.
- **An unsigned rpm on rpm 6.** See slice 5.
- **`rpmbuild` on the runner.** A runner image update can change rpm's version; the job pins and
  asserts it. A foreign `--target` build may need more than expected; slice 5 checks first.
- **Docs drift.** Every output in the new pages comes from a v0.7.1 run. A page with an output
  nobody ran says so.
