## Goal

An operator running three replicas, with a gateway beside each client process (R4), moves the
cluster from release N to release N+1 one replica at a time, with the cluster open and writes
going on, and can put any replica back on N until the last one has moved. Releases say, from a
check the release workflow makes, whether they upgrade this way or by export and import.

## The operator's story

1. Release N+1's notes say **"Upgrading from vN: rolling"** (the formats match) and its binary
   bundles N. The cluster runs N; Botpike's gateways run N.
2. The operator restarts replica 0 with N+1's binary. It opens its data file, sees that the
   cluster runs N, and runs N's code from inside its own binary, offering N+1. Nothing else
   changes: same PID, same port, same log, writes go on. `nerva version` on the binary lists
   both releases.
3. Something looks wrong: the operator restarts replica 0 with N's binary. It is back where it
   was; nothing N+1 wrote exists, because N+1's code has not run.
4. Replicas 0, 1 and 2 are restarted with N+1's binary, one at a time, each waiting until it
   commits again. Only when **all three** offer N+1 does the primary write the upgrade into the
   log; at the next checkpoint every replica switches to N+1's code in place, at the same op.
   Clients see one short pause, below `upgrade_stall_max`, and no ambiguous reply.
5. Gateways move to N+1 after the switch (one at a time, each beside its client). An N gateway
   keeps working against the N+1 cluster; an N+1 gateway started before the switch says so with
   NRV-E0609 and waits.
6. After the switch, N's binary refuses the data file with NRV-E0718 and changes nothing. Going
   back means a revert release (N's code, released as N+2, owner question 4), rolled the same way.

Until the first release that ships R6 (call it vR), every upgrade is still an export and import:
v0.7.0's binary cannot be bundled (below, "What exists today"). The first rolling upgrade is vR to
vR+1.

## Non-goals

- **A data format change by rolling upgrade.** After the switch, N+1's code opens a checkpoint
  that N's code wrote: its grid, manifest, trees, client sessions and WAL. A format change would
  need N+1 to carry N's readers and a deterministic migration in the log, which neither upstream
  nor Nerva has, and which every later release would have to keep. Export and import already
  moves a cluster across any format change (N80), so R6 leaves it there and makes the release say
  which path applies. Additive changes (a new `Operation` value, a new tree) are also treated as
  format changes in R6 (owner question 2).
- **Downgrade after the switch.** Upstream never lowers a cluster's release
  (`release_for_next_checkpoint`, `replica.zig:11153-11183`; `execute_op_upgrade` takes only a
  higher one). Rolling back after the switch is a revert release, rolled forward.
- **Skipping a release.** A binary bundles one past release (`releases_bundled_max = 2`). N to
  N+2 is two rolling upgrades, or an export and import.
- **macOS.** Upstream's multiversion on macOS executes from a temporary file and needs a
  universal binary; production is Linux. macOS binaries stay single-release and `start` there
  says rolling upgrades are Linux only (in the README, not a code: nothing fails).
- **Upgrading from v0.7.0 or any release before vR.** Its binary runs one release
  (`.single_release`, `src/nerva_main.zig:751`) and cannot offer a newer one (below).
- **Changing quorums.** The upgrade quorum stays upstream's: every replica
  (`src/vsr.zig:1241-1257`). A cluster with a replica down does not upgrade; it recovers it first
  (R5).
- **Botpike's runbook.** The rolling procedure on Fly (`fly machine update` one replica at a time,
  then the pin) is Botpike's change, in Botpike/app `docs/runbooks/nerva.md`. This brief says what
  it must do.

## What exists today

**The release string.** `build.zig:17-20`: `release = "0.0.6"`, `release_client_min = "0.0.4"`,
`release_test_other = "0.0.200"`. The release string is the protocol release, not `VERSION`
(0.6.1): v0.6.0 and v0.6.1 both run 0.0.6, and so will v0.7.0 if nothing moves it.

**Mixing releases.** N61: with `release_peers_strict` (`nerva start` sets it), a replica handles a
peer's messages only once the peer has announced, in a ping or pong, exactly this replica's
release (`release_peers.zig:42-92`); prepares and blocks are checked by the release they carry.
`tests/release/mixed.py` proves the two sides never count toward each other's quorums and never
panic. Clients are governed by `release_client_min` and by upstream's eviction of a client newer
than the replica (`replica.zig:6233-6262`, `client_release_too_low`/`_too_high`); neither eviction
has a code.

**The hazard already documented.** The v0.6.1 notes tell operators to restart replicas one at a
time onto v0.6.1, mixing v0.6.0 and v0.6.1 binaries under one release string. N61's guard admits
them, because the strings are equal. It was safe only because v0.6.1 left `prefetch`/`commit`
unchanged; nothing checks that, and if a release changed the state machine without moving the
string, the replicas would execute one op with different code and diverge (at best
`checkpoint diverged` at the next checkpoint, as before N61). `git diff v0.6.1 main` changes the
state machine only behind a test-build option (`commit_keys_deduplicate`), so v0.7.0 on 0.0.6 is
safe the same way, and unchecked the same way.

**Upstream's upgrade, vendored and unused.**
- A binary built with past releases packed into it (`MultiversionHeader`,
  `src/multiversion.zig:298-560`) runs as `MultiversionOS` (`:653-960`): at open, if the data
  file's checkpoint release is an older bundled one, the replica re-executes itself as that
  release from a `memfd` (`execveat`, Linux), keeping its PID (`release_transition`,
  `replica.zig:11115-11150`). Every running process reads the binary on disk again on a timer and
  advertises the releases it bundles; what it advertised is copied to the `memfd` first, so it
  stays executable if the file changes again (`:720-724`).
- Pings carry those releases (`replica.zig:3770-3790`); each replica records its peers'
  (`upgrade_targets`, `:1941-1961`). When every replica offers a higher release
  (`quorum_upgrade = replica_count`), the primary prepares `upgrade` requests to itself
  (`on_upgrade_timeout`, `:4169-4236`) until the whole last bar before a checkpoint trigger is
  `upgrade` ops (`:11153-11183`; so no op is ever replayed by a newer release than executed it),
  and checkpoints with the new release. Once that checkpoint is durable each replica executes the
  new release (`:4700-4717`); a replica that state-syncs to it does the same.
- `upgrade` is a VSR operation, executed by the replica (`execute_op_upgrade`, `:5826-5890`),
  never by Nerva's state machine. Pulses pause while an upgrade is pending (`:5112`, `:5137`).
- **Nerva runs none of it.** `nerva start` passes `.single_release` (`nerva_main.zig:751`), whose
  `release_execute` panics (`multiversion.zig:55-80`); `build.zig` has no packing step (UPSTREAM:
  "No clients, multiversion or release fetching"; upstream's `build_multiversion.zig` was
  dropped). The VOPR's `nerva` lane runs one release and no upgrades (`src/vopr.zig:431-443`,
  `:542-546`); the `testing` lane simulates upgrades with upstream's peer rules.
- **Why v0.7.0 cannot be bundled.** A past release runs as its own binary. To let the cluster
  upgrade, that process must advertise the newer release, which it learns by reading the outer
  binary on disk through `MultiversionOS`. A `.single_release` binary advertises only itself, so
  the upgrade quorum is never reached. The older release must already be multiversion-aware.
- **And why N61 must change.** Around the switch, replicas announce different releases: one that
  has switched announces N+1 while a slower one still runs N and must reach the same checkpoint
  from the new primary's prepares, or state-sync from it. N61 drops all of it, and the slower
  replica never catches up.

**Format guards.** `src/nerva/format_test.zig` (N54) snapshots every wire and storage type's
layout and every persisted enum, and pins golden derivations (row keys, document ids, commit-key
ids) and the export file. `config.cluster.checksum()` (`src/config.zig:195`) covers the cluster
constants that shape a data file; replica ids derive from it (`src/vsr.zig:1301-1320`). Nothing
turns these into a value that two releases can compare.

**What `test:release` proves today** (`build.zig:405-460`, `tests/release/`): `mixed.py`, a
cluster of this release and `0.0.200` never mixes quorums (N61); `upgrade.py`, an export by this
build imported by `0.0.200`, every read the same (N80); `origins.py`, replicas imported from
different exports and a client of `release_client_min` (P90); `recover.py` and `restore.py` (R5).
Both sides are always builds of this commit with different release strings; no published binary
is run. Nothing in it runs two releases' code in one cluster on purpose.

## Design

### Release identity and the format digest

- **The release string becomes `VERSION`** from vR on (vR = 0.8.0 runs release `0.8.0`), and
  every published release moves it (owner question 1). Two binaries with one release string then
  hold the same code, and the v0.6.1 hazard ends. `release_client_min` stays `0.0.4`, and a
  release that rolls must keep it at or below the previous release, so that N's gateways stay
  valid after the switch (asserted in `build.zig` against the bundled release).
- **`format_digest`**, `src/nerva/format_digest.zig`: SHA-256, at comptime, of the text that
  `format_test.zig`'s layout snapshot renders (the same list of types, through one shared
  `layout_render`), `config.cluster.checksum()`, the superblock version, and `format_epoch: u32`,
  a constant moved by hand when a format change escapes the layouts (a key derivation, the
  meaning of a stored field, how a view's stored state is read). `format_test.zig` snapshots the
  digest beside the layouts, so a change to either fails the same test; its doc comment says that
  updating the snapshot needs a decision naming whether the epoch moves.
- **`nerva version`** prints `release`, `release_client_min`, `format <hex>` and `bundles <release>`
  (or `bundles none`). Its `--verbose` form is what the release workflow reads.

### Multiversion `nerva start`

- On Linux, `nerva start` opens `MultiversionOS` on its own executable (`exe_path_format = .native`)
  and passes `.multiversion()` to the replica; every other command, macOS and test builds of
  `cluster 0` keep `.single_release`. `open_sync`'s error (a damaged bundle) refuses with
  NRV-E0719 before the data file is opened; upstream's fallback (advertise only itself) is not
  taken, so an operator never runs a binary that silently cannot upgrade.
- **Pre-flight** (R5's `preflight.zig`) changes its release check: the data file's checkpoint
  release must be this binary's or the one it bundles (else NRV-E0701, as today), and a file whose
  release is above every release this binary runs gets NRV-E0718 (the cluster upgraded past it:
  a rollback after the switch). It also reads `/proc/sys/vm/memfd_noexec` and refuses a value of 2
  with NRV-E0720 at start, rather than failing at the switch.
- **Peers** (`release_peers.admits`, Nerva's own file; the call site in `replica.zig` is a named
  patch): a peer is admitted when the release it announces is one this process can run, that is,
  in `self.multiversion.releases_bundled()`, and its origin matches (P90, unchanged). A prepare or
  block is admitted when its release is one this process can run. A replica of an unrelated release
  is still ignored (`mixed.py` passes unchanged), now with NRV-W0702 logged once per peer and
  connection. Safety: which code executes an op is decided by the checkpoint release in the log,
  not by the peer's binary (the upgrade bar rule above); N61's danger, one op executed by two
  codes, needs a replica to run a release its peers' log did not choose, which `release_transition`
  makes impossible.
- **Metrics:** two gauges, `replica_release` (the release running, as a `u32`) and
  `replica_releases_offered` (the highest release it advertises), through the replica's existing
  statsd (a named patch to `src/trace/event.zig`). Botpike's exporter and the demo read them.

### Packing a past release

- `zig build -Dbundle=<path to N's nerva>` makes `nerva` with N packed in (Linux x86_64 and
  aarch64). The packer is upstream's `build_multiversion.zig` brought back from the pinned commit
  unchanged, if it packs with Zig's own toolchain; if it needs `llvm-objcopy` or any download, it
  is replaced by a small Zig packer under `src/nerva/` that writes the same header (owner
  question 3). It refuses (a build error) a past release whose `format_digest` differs, whose
  release is not lower, or whose `release_client_min` accepts fewer clients than this build's.
- `test:release` builds `nerva_next`: this commit under `release_test_next` (this release with its
  patch plus 200), bundling this build's `nerva`.

### Releases say which path applies

- `release.yml`, for a new `VERSION`: fetch the previous release's Linux binaries and
  `SHA256SUMS` from GitHub, verify them, compare `nerva version --verbose`'s format digest with
  this build's. Equal: pack (`-Dbundle`) and require the CHANGELOG section's
  `### Upgrading from v<previous>` to start with `Rolling:`. Different: do not pack, and require
  `Export and import:`. Either mismatch refuses the release. The bill of materials names the
  bundled release and its SHA-256.
- The previous release is not multiversion-aware (anything before vR): never pack, and require
  `Export and import:`.

### How clients are affected, and the skew allowed

| Process | During the roll (cluster runs N) | After the switch (cluster runs N+1) |
| --- | --- | --- |
| Replica, N binary | Runs N; admits peers whose binary bundles N | Refuses the data file at start, NRV-E0718 |
| Replica, N+1 binary | Runs N's code from its bundle, offers N+1 | Runs N+1 |
| `nerva api`, `nerva view`, `export`, `recover`, `backup`, Zig client of N | Works | Works (N ≥ `release_client_min`) |
| The same, of N+1 | Evicted, `client_release_too_high`: NRV-E0609, `/healthz` 503 | Works |
| A client below `release_client_min` | Evicted: NRV-E0610 | Evicted: NRV-E0610 |

- **Order:** replicas first, then gateways. Roll gateways back first, then replicas (before the
  switch only).
- **The JSON API** only grows (REVIEW.md), so a caller of the gateway, Botpike's Kotlin client
  included, is unaffected by the gateway's release.
- **Botpike** (`nerva.pin`, an external client): its replicas (`botpike-nerva`, deployed by hand)
  roll first, one Machine at a time, waiting for each to commit (`replica_release` and the
  replica's commit gauge); once every replica's `replica_release` is N+1, the pin moves and the
  app's gateways roll with the app. `NervaContainer` runs one replica of the pinned release and is
  unaffected. A pin that moves before the switch fails loudly on `/healthz` (NRV-E0609), never
  silently.
- **A gateway evicted as too new** does not loop: it logs NRV-E0609 once a minute and retries its
  registration every `client_release_retry` (5 s), so it comes up by itself after the switch.

**Formats:** the data file, the wire, the export and every persisted identifier are unchanged.
The release string moves, as at every protocol release so far (a data file records its
checkpoint's release; the formatted file's golden checksum moves with it, UPSTREAM's
`replica_format.zig` row). The packed binary's header is upstream's format, used as is.

## Bounds

| Constant | Value | Where | Why |
| --- | --- | --- | --- |
| `releases_bundled_max` | 2 (this release and one past) | the packer, asserted at `start` | Skipping a release is two steps |
| `multiversion_binary_platform_size_max` | 64 MiB (upstream's) | `src/config.zig` | Measured against a ReleaseSafe pair in slice 3; the buffer and the `memfd` are allocated at start |

Each gets a test at the bound and one past it: a pack of three releases refused; a bundle one byte
over the size limit refused with NRV-E0719; the stall measured in every rolling run.

## New error codes

To register in `docs/ERRORS.md` in slice 1, as "not yet emitted". The numbers are proposed; the

| Code | Summary |
| --- | --- |
| NRV-E0609 | The client (a gateway, `nerva view`, a command) is of a newer release than the cluster runs; it was evicted (`client_release_too_high`) |
| NRV-E0610 | The client's release is below the cluster's `release_client_min`; it was evicted (`client_release_too_low`) |

## The demo: `zig build demo-r6`

`tests/demo/r6.py <nerva> <nerva_next>`, both built by the step from this commit: N is `nerva`, N+1
is `nerva_next` (this code under `release_test_next`, bundling N; slice 3). It needs no network and
no published binary, so it runs on GitHub's runners whatever the state of the Hetzner host the owner
is provisioning for R1 and R2; the cross-release run against a published binary is
`test:release`'s, once vR exists (owner question 5). Three replicas on loopback, each with
`--statsd` to the script's listener, a real `NERVA_CLUSTER_KEY`, two gateways (A and B, each beside
its own writer, R4) and one `nerva view`. Every step asserts.

| Step | Action | Expected |
| --- | --- | --- |
| 1 | Format and start three replicas on N; declare a layout, a ledger and two views; start writers A and B: keyed commits moving the ledger by pairs and writing records, without pause until step 11 | Every commit answers `committed`, or a 503 with `"applied": false` resent under its key |
| 2 | Commit past op 1,100 (past the first checkpoint); record every view hash and the ledger total through `nerva api` and `nerva view` | They agree |
| 3 | Restart replica 0 with N+1's binary | Its log shows `release_transition` to N; `replica_release` = N on all three; `replica_releases_offered` = N+1 on replica 0 only; writes go on |
| 4 | Rollback: restart replica 0 with N's binary | Commits again; every replica offers N only; no checkpoint names N+1 |
| 5 | Restart replica 0, then 1, with N+1, each after the previous commits again | Still N everywhere; no `upgrade` op prepared (two of three offer N+1) |
| 6 | Start gateway C on N+1 | `/healthz` 503 with NRV-E0609; logged once a minute, not per retry |
| 7 | Restart replica 2 with N+1 | Within 60 s every replica's `replica_release` = N+1; the three logs name the same checkpoint op for the switch; the longest gap between acknowledged commits is below `upgrade_stall_max` |
| 8 | Wait for gateway C | `/healthz` 200 within `client_release_retry` + 5 s; its commits apply |
| 9 | Restart gateway B on N+1; gateway A stays on N | Both writers go on |
| 10 | SIGKILL the primary; restart it with N+1's binary | It runs N+1 and catches up; writes go on |
| 11 | Stop the writers. Read every view, the ledger and its total through `nerva api` (A and B) and `nerva view` | Every hash equals `nerva view`'s; the total is conserved; every acknowledged key, resent, answers `replayed` with its original op: none lost, none doubled. No reply in the whole run said `"applied": "unknown"` |
| 12 | Stop replica 1; `nerva start` it with N's binary | `error[NRV-E0718]`, exit 1; the data file's SHA-256 unchanged; started again with N+1 it rejoins |

The script prints one line per step and ends `demo-r6: PASS` or `demo-r6: FAIL step N: …`. A
failure is a finding (CLAUDE.md), never re-run until it passes. Gateways run with
`--request-timeout=60s`, above `upgrade_stall_max`, so a pause at the switch is a wait, not an
unknown outcome.

## Risks

1. **The switch is a short whole-cluster pause.** Every replica re-executes at the same checkpoint
   and the last bar before it holds only `upgrade` ops. Unmeasured; the demo bounds it at 30 s on a
   CI runner, and R3's topology may differ (larger caches allocate longer at start).
2. **Memory at start.** `MultiversionOS` holds the binary in a buffer and a `memfd`
   (`multiversion.zig:720-760`): tens of MiB on a replica that already takes about 3.0 GB (#127)
   on Botpike's 4 GB Machines. Measured in slice 2; R3's sizing table includes it.
3. **The binary on disk is watched.** Replacing the file on every replica, with no restart (a
   package manager, an image update), upgrades the cluster by itself: upstream's behaviour, kept
   and written in the README.
4. **A new `start` flag.** N+1's binary runs N's code with N+1's command line until the switch; a
   flag N does not know is refused by N (NRV-E0001), confusingly. The release notes say new
   `start` flags are used only after the switch, in a later restart.
5. **Same-string mixing before vR.** v0.7.0 (and any release on 0.0.6) still relies on an
   unchanged state machine for the v0.6.1-style restart. Until vR, its notes should say export and
   import, or name the review that checked `prefetch`/`commit` unchanged.
6. **The VOPR runs one code in both releases.** It checks the protocol of the switch, not two
   state machines; that one op runs under one release is upstream's argument and the bar rule's
   assertion. Real two-code runs are only `rolling.py` against a published release, from vR+1.
7. **Hardened kernels.** `vm.memfd_noexec = 2` breaks the switch; pre-flight catches it at start
   (E0720), not containers that forbid `execveat` by seccomp, which fail at the switch with the
   replica's exit and E0720.

## Owner questions

1. **The release string becomes `VERSION` from vR on**, every release moving it, so that one
   string always means one code. Or keep a protocol release that moves only when the protocol or
   state machine does? **I'd move it every release**: the second option is the v0.6.1 hazard, and
   multiversion needs distinct, increasing releases anyway.
2. **Strict formats in R6:** any change to the digest (a new `Operation` value, a new tree, a new
   field) means export and import. Or allow additive changes now? **Strict**: an additive rule
   needs its own proof that N+1 opens N's checkpoint; file it as a decision after R6.
3. **The packer.** Upstream's `build_multiversion.zig` if it needs nothing but Zig, else a Zig
   packer of Nerva's own; never a downloaded `llvm-objcopy` (a new dependency, stop item 5).
   **Agreed as written**; the implementer checks upstream's file first and stops if neither works.
4. **Rollback after the switch** is a revert release: N's tree with the next release string,
   rolled as usual. May a revert release skip the 24-hour fleet soak of the release gate (P147b),
   keeping both reviews? **Yes, with one review and the fleet's tracker line from N**: its code is
   N's, which passed the gate.
5. **The demo's two releases** are both built from the commit (N and N+1 = N's code, release +200),
   so the demo runs anywhere without network. The run with a real published N lives in
   `test:release` from vR+1. Or make the demo fetch the published release? **Built from the
   commit**: the demo must be green on every PR, and a fetched binary depends on GitHub's release
   assets and on the formats still matching.
6. **v0.7.0 to vR** is an export and import. Or keep vR on 0.0.6 so that v0.7.0 restarts into it
   (no rolling switch, the same-string hazard once more)? **Export and import**, said in vR's notes.
