## Goal

A JVM process (Botpike's app) holds one Nerva client in its own memory, connected to every
replica. Its threads call `commit`, `lookup` and the reads they need as Java methods; the library
puts the calls that wait together into one cluster request, as many as one message holds, and
hands each caller its own result with the same `code` and `applied` the gateway's reply would
carry. No gateway, no HTTP and no JSON are in the path.

## Non-goals

- **A new wire format between client and replica.** The library sends what `src/nerva/client.zig`
  sends today: the operations' extern structs in a multi-batch body (`vsr/multi_batch.zig`). The
  "binary encoding" PRODUCTION names is these structs, documented and pinned by test vectors; it
  adds no `Operation` value, no `EntryKind`, no status and no field. A slice that finds it needs one
  stops (CLAUDE.md, item 1), because under P259c any such change also ends rolling upgrades for
  that release.
- **Retiring the gateway.** `nerva api` stays the language-neutral API (N39, P147g), and the way
  to declare layouts, views, ledgers and indexes, and to read and write documents (owner
  question 5).
- **Declarations and documents through the library.** `declare_view`, `declare_ledger`,
  `declare_index`, the catalog's layout writes and `/v1/documents` stay with the gateway and the
  `nerva` commands. A native client declaring a view with no catalog entry is the hole #353 names.
- **Client authentication itself.** That is #353, in v0.8. R8 carries its key (below) and does
  not design it again.
- **TLS.** As for replicas (P102): the client key proves who connected; traffic is not encrypted.
  Hosting is generic VMs (P359b), so the README says client-to-replica traffic needs a private
  network, as replica-to-replica traffic does.
- **Other languages.** Only the C ABI and the JVM binding. Go, Python and Node bindings can follow
  over the same ABI, each its own decision.
- **macOS and Windows libraries.** Linux x86_64 and aarch64 only, as PRODUCTION says. Developers on
  macOS keep the gateway (owner question 4).
- **Maven Central.** The jar is a release asset (owner question 4).
- **Botpike's switch.** Its Kotlin client (`Botpike/app`, `:external:nerva`) gaining an
  implementation over the jar is Botpike's change; this brief says what that change can rely on.

## What exists today

**The Zig client** (`src/nerva/client.zig`). One VSR session, one request in flight, every
message allocated in `init`, and a blocking call per operation that drives the client's own event
loop until its reply, an eviction or `Options.timeout` (`:1-6`, `:114-240`). After a timeout the
client must be replaced (`Client.reconnect`, `:172`; N70; `client_health.zig`). `writes_sent`
(`:106-109`) counts the write requests sent, so a gateway can say `applied: false` or `"unknown"`
(P173c). Multi-batch calls take at most `batches_max = 16` batches (`:47-48`); `batches_fit`
(`:292-314`) checks that a set of batches and their replies fit one message.

**The operations.** `Operation` (`src/nerva.zig:1339-1361`) has 16 values, `vsr_operations_reserved
+ 0` to `+ 15`. Four are multi-batch (`is_multi_batch`, `:1455-1472`): `lookup_rows`, `commit`,
`commit_wide`, `lookup_records`. A `commit` batch is one transaction (N4, `:189`); the replica
accepts up to `maxInt(u16)` batches in one request (`state_machine.zig:598-599`), so a request is
bounded by the message (`message_size_max` 1 MiB, `src/config.zig:156`): about 8,190 128-byte
`Entry`s or 2,040 512-byte `WideEntry`s. The other twelve take one event per request.

**The gateway's batching** (P143, `src/nerva/api/server.zig`, `api.zig:358-450`). Up to 16
complete requests waiting for the same route become one multi-batch cluster request, one batch per
caller. A transaction refused `views_busy` (the op's budget of view-group writes,
`StateMachine.groups_per_op_max`, was spent by the transactions before it) is sent again alone,
once. A timeout, a lost session or an eviction fails every member. P143 measured about 340 submits
a second at 24 callers before, about 1,700 after; P136 explains why the primary's commit stall
dominates once several ops wait.

**Sessions.** A cluster holds 64 client sessions (`src/config.zig:222`; README `:246`). Each
gateway, `nerva view`, `export` and Zig client takes one; a 65th evicts the least recent (NRV-E0603).
Under R4 Botpike runs one gateway beside each app process, so one session per process already.
R8 keeps that count only once the gateway is gone from a process: while both paths run side by
side, each process holds two (below, "How R8 serves Botpike").

**Who may reach a replica.** Today no one but its peers and the gateways beside clients should:
a process that reaches a replica's port can register and read and write with no key
(`SECURITY.md:54-62`). The gateway's `X-Nerva-Key` is the only client credential (N33, P96), and a
native client goes around it. #353 (Option A, owner-approved for v0.8) adds `NERVA_CLIENT_KEY`
and `NERVA_CLIENT_KEY_NEXT`, a handshake on every client connection (new header-only commands
after ordinal 27), vendored patches to `message_bus.zig`, `replica.zig`, `vsr/client.zig`,
`message_header.zig` and `vsr.zig`, and its own codes. The dial side lives in the vendored
`vsr/client.zig` and message bus, which R8's library is built on, so R8 inherits it.

**TigerBeetle's clients, not vendored.** At the pinned commit, `tb_client`
(`src/clients/c/tb_client/`) runs the VSR client on its own thread, takes packets from any thread
through a queue and a signal, puts packets of one operation into the next request while one is in
flight, and completes each packet through a callback. Its Java client calls that library through
**JNI** (`src/clients/java/src/jni.zig`), not the foreign-function API: P147g's "as TigerBeetle's
Java client does" is mistaken on this point. `tb_client` is written against the accounting state
machine's operations and results, so it cannot be vendored as is.

**Java.** The foreign-function API (`java.lang.foreign`) is a preview in Java 21 (JEP 442) and
final in Java 22 (JEP 454): on 21 it needs `--enable-preview` at compile time and at run time.
GitHub's `ubuntu-24.04` runners carry Temurin 21 (`jepsen.yml:120-126` uses it). Nerva's build
and CI need no JDK today except Jepsen's.

**Releases.** A release has exactly twelve assets (P361; `publish-ready` refuses others,
NRV-E1131), its SBOM covers TigerBeetle, Zig and nothing else (N63), and the release check pins
`src/`, `build.zig`, `build.zig.zon`, `zig/`, `.gitmodules` and `.gitattributes` to the candidate
(P374). A jar is none of these.

## Design

### Layers

```
JVM threads ──▶ nerva.jar (Java: NervaClient, Transaction, results, NervaException)
                 │  JNI (owner question 1)
                 ▼
             libnerva.so  ── C ABI: src/nerva/native/c_abi.zig, include/nerva_client.h
                 │
                 ▼
             src/nerva/native/client.zig: its own thread, IO loop, packet queue, batching
                 │  the vendored vsr.Client and message bus (with #353's handshake)
                 ▼
             replicas
```

Everything below the JVM is Nerva's own Zig under `src/nerva/native/`, beside (not inside)
`src/nerva/client.zig`, which the gateway keeps using unchanged. Shared pieces (building a
multi-batch body, `batches_fit`, `writes_sent`) move to a small module both use, with no change of
behaviour for the gateway; the gateway's tests prove it. One change reaches the state machine:
`batch_valid` becomes a `pub` function that the replica's `input_valid` and the library both call
(below, "Shape check"). That is a change to `src/nerva/state_machine.zig`'s admission path, so
slice 2 runs a VOPR seed and pins `input_valid`'s answers at the bounds before and after the move.

### The native client (`src/nerva/native/client.zig`)

- **One thread per client,** started by `init`, running the IO loop (`IO.run_once`, N51) and
  ticking the VSR client. All memory (messages, the packet ring, reply buffers) is allocated in
  `init`; nothing after.
- **Packets.** A caller's call is a packet: an operation, its events, a result buffer and
  `user_data`. `submit` puts it on a bounded queue (`packets_max`) and wakes the thread; a full
  queue completes the packet at once with NRV-E1204, `applied: false`. The packet is completed by
  the callback exactly once.
- **Shape check, before anything is queued.** The replica's `input_valid`
  (`src/nerva/state_machine.zig:1160-1206`) judges a whole request: one malformed batch fails it,
  `replica.zig` evicts the session with `invalid_request_body`, and every caller of the process
  gets NRV-E0603. The vendored `vsr/client.zig` also asserts on body sizes, so a bad size that
  reached it would panic the library and the JVM with it. So `submit` checks each packet on the
  caller's thread, in this order, and completes a packet that fails at once, `applied: false`,
  nothing queued or sent:
  1. the operation is offered (NRV-E1205);
  2. the shape (NRV-E1209): `events` is not null when `events_size` is not zero, nor `results`
     when `results_size` is not zero; the packet's own reserved fields are zero (an entry's are the
     cluster's to judge, E1210 below); `events_size` is not zero and
     not above the limit; and the events pass `batch_valid` (`state_machine.zig:1192`): for a
     one-event operation `events_size` equals `operation.event_size()`; for a batchable one it is
     a whole multiple of it and the count is at most `operation.event_max(batch_size_limit)`.
     Zero events is refused by the library's own rule, beside `batch_valid`: the replica admits an
     empty batch (`maybe(batch.len == 0)`), but `batches_fit` refuses a count of zero
     (`client.zig:298`), and an empty transaction or lookup is never a caller's intent (the
     gateway refuses it as E0110). The size is checked before `batch_valid` is called, so its
     `assert(batch.len <= limit)` holds for both callers. `batch_valid` becomes a `pub` function
     of the operation, the batch and the limit; the replica's `input_valid` passes its own
     `self.batch_size_limit`, unchanged, and the library passes the limit below, so the two
     cannot drift. Before the session is registered, `submit` checks against
     `constants.message_body_size_max`; the thread checks each packet again against the session's
     `batch_size_limit` (from the register reply) as it takes it into a request, and completes one
     that fails with E1209 there;
  3. the size: events and results fit one request (NRV-E1203), and `results_size` holds the
     largest reply its events can get (NRV-E1207).

  The thread asserts `input_valid`'s whole-request check (the trailer and the reply's size) on
  every body it builds, before handing it to `vsr.Client`: by construction it holds, so a failure
  is the library's bug, not the caller's. One caller's malformed packet therefore never reaches
  the cluster and never fails another caller's packet.
- **Batching.** While one request is in flight (VSR allows one per session), packets wait. When the
  reply comes, the thread takes the oldest packet and every later waiting packet of the **same
  operation** that still fits (`batches_fit`: request and reply in one message, at most
  `batches_per_request_max` batches) into one multi-batch request, one batch per packet. For
  `commit` and `commit_wide`, one batch is one transaction (N4), so each caller's transaction
  commits or not on its own; a keyed transaction carries its key as its first entry (P123). The
  first packet in the queue is always taken, so no operation starves another; a packet of a
  one-event operation is a request of its own. Order: packets of one client are sent in the order
  submitted.
- **`views_busy`.** A transaction refused `views_busy` is sent again alone, once, as the gateway
  does (P143); a second refusal is its result.
- **Deadline.** `request_timeout` (an `init` option, default 30 s as the gateway's, P168d). A
  request in flight past it abandons the session, as the gateway's client does
  (`client_health.zig`, N64): each packet in that request completes with NRV-E0601 and
  `applied: "unknown"` if it is a write (`Operation.is_write`), NRV-E0601 and `false` for a read;
  each waiting packet completes with NRV-E0605, `applied: false`; the thread registers a new
  session no sooner than `reconnect_interval_ns`. A caller resends a write under its key (P123):
  `committed_before` names the op it took.
- **Eviction** (N70): the same as the deadline, with NRV-E0603 for the packets that were sent, and
  R6's NRV-E0609 and NRV-E0610 when the reason is the release.
- **`deinit`** stops taking packets, completes waiting ones with NRV-E1206 (`applied: false`),
  waits up to `request_timeout` for the one in flight, then completes it as above and joins the
  thread.

### The C ABI (`src/nerva/native/c_abi.zig`, `include/nerva_client.h`)

```c
uint32_t nerva_abi_version(void);           // 1; moves when any declaration below changes
const char *nerva_release(void);            // the release string (P259b), e.g. "0.9.0"

nerva_init_status nerva_init(nerva_client *client, const nerva_init_options *options,
                             nerva_completion callback, uintptr_t context);
nerva_submit_status nerva_submit(nerva_client *client, nerva_packet *packet);
void nerva_deinit(nerva_client *client);

typedef struct {
    uint64_t user_data;        // the caller's, returned untouched
    uint8_t  operation;        // a Nerva Operation value, unchanged (src/nerva.zig)
    uint8_t  status;           // nerva_packet_status: 0 ok, 1 error, 2 bug; never an NRV number
    uint8_t  applied;          // 0 false, 1 true, 2 unknown
    uint8_t  reserved[5];
    uint16_t code;             // the NRV code's four digits when status != ok, else 0
    uint16_t reserved_b[3];
    const void *events;        // events of `operation`'s EventType, little-endian extern structs
    uint32_t events_size;
    uint32_t results_size;     // capacity of `results`
    void    *results;          // results of ResultType, as the reply carries them
    uint32_t results_written;
    uint32_t reserved_c;
    uint64_t op;               // the op the reply reflects (G2)
} nerva_packet;
```

- **`status` and `code`.** `status` is the ABI's own `nerva_packet_status` enum and says only
  whether the packet succeeded and, if not, the kind of its code: `error` for an `NRV-E` code,
  `bug` for an `NRV-B` code (NRV-B0002). `code` alone carries the code's number: `status = error,
  code = 601` is NRV-E0601, `status = bug, code = 2` is NRV-B0002. A transaction the cluster
  refused carries the same `02xx` code the gateway's reply would (`conflict` E0202,
  `out_of_bounds` E0203, `write_duplicate` E0210, …), `applied: false`, and its entries'
  statuses are in `results`. Both enums' values are frozen once released (below, "Identifiers").
- **Malformed entries are the caller's.** The gateway builds each `Entry` from JSON, so it calls
  the entry statuses its own checks rule out impossible (NRV-B0002, `applied: "unknown"`,
  `api.zig:1199-1212`). A native caller writes raw `Entry` and `WideEntry` bytes, and
  `batch_valid` checks only a batch's shape ("entry contents are validated at commit",
  `state_machine.zig:1191`). So the statuses a caller's encoding can cause, `kind_invalid` (3),
  `table_invalid` (4), `reserved_not_zero` (5), `value_not_zero` (6), `op_seen_not_zero` (7),
  `field_invalid` (11), `delta_from_invalid` (12), `key_misplaced` (21), `key_invalid` (22) and
  `id_invalid` (23) (`src/nerva.zig:256-311`), complete the packet with **NRV-E1210**, blame
  client, `applied: false` (the transaction was refused whole, N4), and the failing entry's index
  and status in `results`. A resend fails the same way, so the binding marks it not retryable.
  Here the native path does not mirror the gateway. NRV-B0002 stays only for what is impossible
  from the library too: a status value the library does not know (from a newer replica), a
  key status (`committed_before`, `key_reused`, `key_collision`) on an entry that is not the
  key, or a refused transaction with no failing entry (every entry `aborted`).
- `nerva_init_options` carries the cluster id, the addresses, `request_timeout`, `packets_max`,
  and `client_key` and `client_key_next` (#353's keys; empty until #353 merges, refused as
  NRV-E1208 when set before then, so no one believes a key is in use).
- **The encoding is the cluster's own.** `events` and `results` are exactly the arrays the Zig
  client sends and receives for one batch: `Entry`, `WideEntry`, `RowKey`, `RecordKey`, the
  filters and queries, and their results, as `src/nerva.zig` declares them (`extern struct`,
  little-endian, sizes asserted). The library adds the multi-batch trailer and strips it; a binding
  never sees it. `docs/WIRE.md` (new, slice 1) documents every offered operation's event and result layout, the
  enums (`Operation`, `EntryKind`, `EntryStatus` and the other statuses) by value, and what each
  result field means. `format_test.zig` (N54) already snapshots these layouts; R8 adds golden
  vectors (below) so that the JVM side is checked against the same bytes.
- **Operations offered:** `commit`, `commit_wide`, `lookup_rows`, `lookup_records`, `get_changes`,
  `get_history`, `get_record_changes`, `get_record_history`, `get_view`, `get_ledger`,
  `scan_index`, `get_index`. Any other value, `pulse` (N67) and the declarations included, is
  refused at `submit` with NRV-E1205, never sent.
- **Identifiers.** The ABI's own enums (`nerva_init_status`, `nerva_submit_status`,
  `nerva_packet_status`) are new public identifiers. They are not persisted, but bindings compile
  against them: once released they are never renumbered, as `Operation` (a decision to file).
- **Layouts.** `nerva_layout_read(client, table, out)` reads a table's layout from the catalog
  (the same documents the gateway reads, `catalog.zig` and `documents.zig`, over `lookup_rows`) and
  returns its fields as fixed-size records: name, type, offset, size. Field packing then happens in
  Java by those offsets, the rule `catalog.zig:1-10` states. It is the one multi-call function, run
  on the library's thread as a sequence of packets (owner question 5).
- **Callbacks** run on the library's thread and must not block; the binding copies the results
  and completes a future on its own executor.

### The JVM binding (`clients/jvm/`)

- Java 21 source, no third-party library, built with `javac` and `jar` by `zig build jvm` (which
  also cross-builds `libnerva.so` for `x86_64-linux-gnu` and `aarch64-linux-gnu` with Zig and puts
  both in the jar). Tests are plain `main` programs, run by `zig build test:native` (owner question
  2).
- The JNI shim is Zig (`src/nerva/native/jni.zig`): upstream's `src/clients/java/src/jni.zig`
  brought back unchanged as a vendored file for the JNI types (owner question 3), and Nerva's own
  entry points over it. No JDK header is needed to build it.
- API, kept small and Kotlin-friendly:
  - `NervaClient.open(cluster, addresses, Options)`, `close()`. One per process (a session).
  - `CompletableFuture<CommitResult> commit(Transaction)` and `commitWide`; a `Transaction` builder
    for reads, puts, deletes, adds (pairs, floors, `delta_from`) and the key.
  - `lookupRows`, `lookupRecords`, `changes`, `history`, `view`, `ledger`, `scanIndex`, `index`,
    `layout`; each also as a blocking call.
  - `CompletableFuture<RawResult> submitRaw(int operation, ByteBuffer events, int resultsSize)`:
    the packet as the C ABI takes it, for bindings over the jar and for tests (slice 4's
    malformed packet, the demo's step 7). The library's shape check runs on it as on any packet;
    its Javadoc says the caller owns the encoding (`docs/WIRE.md`).
  - Results keep the wire identifiers (`conflict`, `out_of_bounds`, `unpaired`, `key_reused`, …)
    as an enum beside each entry's status; failures are `NervaException` with `code()`
    (`"NRV-E0601"`), `applied()` (`FALSE`, `TRUE`, `UNKNOWN`) and `retryable()` (blame `retry`).
- The jar's loader checks `nerva_abi_version()` against the one it was built for and refuses a
  mismatch with NRV-E1201; an unsupported platform is NRV-E1202.

### How R8 serves Botpike

Botpike's Kotlin client (`:external:nerva`, D4, P96, Botpike/app P99b) talks to the gateway
beside it. Its submit is a lookup, then a keyed commit with records (P132). With R8:

- **What Botpike changes** (in Botpike/app): a second implementation of its client interface over
  `nerva.jar`, chosen by configuration, so both paths can run side by side and be compared; the
  layouts it encodes by name come from `NervaClient.layout`. Declarations at deploy time, and
  documents if its request path uses them, stay on a gateway or `nerva` commands.
- **What it can rely on:** every outcome carries the same `code` and `applied` the gateway would
  give for the same cause, except a malformed entry, which the gateway never sends and the
  library answers NRV-E1210 `applied: false` (above); a write whose outcome is unknown is resent
  under its key.
- **Sessions.** A `NervaClient` takes one of the cluster's 64 sessions, as a gateway does. While
  both paths run side by side, each app process holds two (its gateway's and its client's), and
  a process that keeps a gateway for documents on its request path keeps two after the switch
  too. `nerva view`, exports and probes take theirs from the same 64. A 65th registration evicts
  the least recent session (NRV-E0603), which in the middle of the comparison fails every call of
  that process.
- **What it needs first:** the replicas' client port reachable from the app Machines over a private
  network, and #353's client key in v0.8 (below). Its replicas are upgraded before the app, as for
  gateways (P260; R6's order). And a session budget: with 2 sessions per app process and 4 kept
  for `nerva view`, an export and probes, Botpike runs at most 30 app processes while both paths
  run (60 + 4 = 64), and at most 60 once each process holds only its client; past that it needs a
  larger `clients_max`, which is a format question (`src/config.zig:222`), not R8's.

### #353 and v0.8

R8 moves the client's credential from the gateway's door to the replica's. Without #353, a native
client is exactly the unauthenticated caller `SECURITY.md` warns about, so:
- R8's library takes `client_key` and `client_key_next` from slice 3 on, and the handshake is
  #353's code in the vendored bus and `vsr/client.zig`, not R8's.
- R8's slices 1 to 5 may merge before #353 (tests on loopback, keyless replicas). The demo
  (slice 7) runs with a client key, so it waits for #353; **R8 is delivered only after #353 has
  merged, and ships in v0.8 or later** (owner question 7).
- #353 changes the wire (new commands); R8 changes none. Neither renumbers anything.

### Formats and identifiers

- **Data file, export, wire between client and replica:** unchanged. No `Operation` value, enum
  value or struct changes; the format digest (P269b) does not move; rolling upgrades (R6) are
  unaffected.
- **New, public, not persisted:** the C ABI (`nerva_client.h`, `nerva_abi_version` = 1) and the
  Java API. Rules to file: the ABI's enums are never renumbered; the ABI version moves on any
  change; the Java API only grows within a major version.
- **Releases:** the library's release is the binary's (`nerva_release()`), checked by the cluster
  against `release_client_min` like any client (R6's NRV-E0609 and NRV-E0610).

| `packets_max` | 4,096 (option, 1 to 65,536) | `native/client.zig` | Waiting calls per client; a full queue refuses with E1204 instead of growing |
| `batches_per_request_max` | 1,024 | `native/client.zig` | 64 times the gateway's 16; far below the replica's `maxInt(u16)`; the message's 1 MiB still bounds it first for full transactions |

## Risks

1. **Bigger requests change the primary's work per op.** 1,024 transactions in one op is new; view
   group budgets (`groups_per_op_max`) will refuse more `views_busy`, and one op's commit takes
   longer. Measured in slice 2 and the demo; `batches_per_request_max` is a constant to lower.
2. **One request in flight per session.** A slow op delays every caller in the process, as one
   gateway does today. Throughput grows by batching, not by concurrency; a process that needs more
   opens a second client (and a second session).
3. **A deadline abandons a whole session.** One stuck request answers `unknown` to every write in
   it. Keys make the resends safe; Botpike must resend under the same key, which it already does
   behind the gateway.
4. **Callbacks on the library's thread.** A binding that blocks in the callback stops the client;
   the Java side only hands off to an executor, and a test checks the thread never waits on Java.
5. **The JVM's native memory.** About two messages of 1 MiB per packet slot in flight plus
   `packets_max` packets: tens of MiB beside Botpike's app. Measured and stated in the README.
6. **Replica ports opened to clients.** Until #353, a deployment that tries R8 in production
   exposes the cluster to anyone on the network. The README and the library's E1208 say so; no
   release ships R8 before #353.
