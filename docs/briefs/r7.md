## Goal

An operator declares how long Nerva keeps three kinds of past state: commit keys, row and record
history, and view and group versions. The cluster trims each kind below its horizon,
deterministically, as part of the log, with a bounded amount of work per op. A cluster under
steady load then holds a steady amount of data: the data file's live blocks, the export and its
time, and `nerva view`'s memory stay flat. What was trimmed is refused by name:
- a resent key older than its horizon answers `key_expired`, never `committed`;
- a read of the past below a horizon answers `before_horizon`, never a wrong answer.

## The operator's story

1. Today a cluster grows without bound:
   - each keyed transaction leaves an 80-byte key row and a change, forever (P123);
   - each write leaves a 128-byte change (512 for a record);
   - each view or group write leaves a version.

   An export of a year-old cluster replays a year.
2. The operator runs `nerva api` and sends:

   ```
   PUT /v1/retention {"keys": "7d", "history": "30d", "versions": "30d"}
   ```

   The declaration commits like any other op; `GET /v1/retention` shows it with each kind's
   horizon (the oldest timestamp still kept) and how far trimming has caught up.
3. From then on the primary's pulses trim, a bounded slice per pulse, until each kind is caught
   up, and then keep up. Writes go on; a pulse is one op among them.
4. A client resends a key from 8 days ago: `409 key_expired` (NRV-E0213). It does not apply. The
   client knows the outcome is unknowable from Nerva and goes to its own records.
5. A client asks for a row as of 40 days ago, or for changes after a cursor from 40 days ago:
   `410 before_horizon` (NRV-E0411), naming the horizon. `nerva view` and `nerva export` read the
   compacted prefix instead (see "The feed below the horizon").
6. Loosening a horizon keeps what is still there: trimmed data does not come back. Tightening it
   trims more, at the same bounded pace.

## Non-goals

- **Shrinking the data file.** Trimmed blocks return to the free set and are reused; the file
  never shrinks (upstream's grid has no truncation). "Flat" is measured as blocks acquired, not
  file size.
- **Reclaiming tombstones** (N3): a deleted row's tombstone, and a row's current value, are kept
  whatever the horizon. So are the catalog, layouts, ledgers, views' and groups' current state,
  members, indexes and their entries.
- **Per-table or per-view horizons.** One horizon per kind, cluster-wide. A later milestone may add
  them; the declaration's layout keeps reserved bytes for it.
- **Horizons by op count** or by size. Time only, from prepare timestamps.
- **Object storage, tiering, archiving** what is trimmed. An operator who must keep everything
  exports before trimming, or does not declare a horizon.
- **Trimming at compaction time.** It would never fire: append-only, timestamp-keyed tables reach
  the last level by `move_table` and are never rewritten there (`compaction.zig`). See "Design".
- **A rolling upgrade into R7's release.** Its formats move the digest; P259c says export and
  import (see "Formats and R6").

## What exists today

- **Nothing is ever removed.**
  - Rows are deleted by tombstone (N3).
  - Changes (`tree_ids` 3, 4), group versions (12, 13), view versions (14, 15) and record
    changes (20, 21) are append-only grooves with `objects_cache = false`.
  - Commit keys are rows of reserved table `0xFFFF_0003`, written once at `commit_key_id(key)`
    (the first 8 bytes of SHA-256 of `"nerva.commit_key.v1"` and the key). The value is
    `CommitKey {key, checksum, entry_count, reserved[44]}`, 80 bytes, and it is also a change
    in the feed (P123).
- **Removal in the vendored groove is unfinished.**
  - `Groove.remove(key)` (`src/lsm/groove.zig:1879`) asserts `constants.verify`, requires an
    objects cache, and carries upstream's "TODO: Nothing currently calls or tests this method".
  - Cacheless grooves cannot remove at all.
  - UPSTREAM.md records that `forest_fuzz` was dropped "until Nerva's forest has real grooves".
- **Tombstones are dropped by compaction** at the last level, or when no lower level can hold the
  key (`compaction.zig:706-719`). So a removal that writes a tombstone per object is reclaimed by
  ordinary compaction, and the space returns to the free set.
- **Pulses exist.**
  - The primary prepares `pulse` every `pulse_timeout` (100 ms, `replica.zig:1481`), and after
    a commit when `pulse_needed` is true (`replica.zig:5110`).
  - `pulse_needed` (`state_machine.zig:1155`) is true while a view or an index is building
    (N52).
  - Backfill already shows the pattern R7 needs: a cursor in a singleton groove, a bounded batch
    per pulse, all reads in `prefetch`.
- **The format digest** (R6 slice 1, `src/nerva/format_digest.zig`) hashes layouts, `tree_ids`,
  the cluster config, the vendored layouts and the derivations, with `format_epoch = 1`.
  - R6's later slices are not merged: `nerva_main.zig:750` is `.single_release`, and
    `build.zig:25` has `release_bundled = null`.
- **The export file** is version 2 at most (`export_file.zig:29`). It replays every op from 1
  (N80); import refuses a delete of a row that is not live (N81). Backups record the export
  version in their manifest (`backup.zig:206`).
- **Statuses.** `EntryStatus` runs to `id_collision = 24` (`format_test.zig:105`); new values are
  appended from 25. `ChangesFilter` (`nerva.zig:937`) has 52 reserved bytes.
- **The free-set gauge.** `grid_blocks_acquired` exists (`src/trace/event.zig:591`), which is
  the demo's measure.

## Design

### Declared in the log

- **Operations.** A new `Operation.declare_retention` (the next free reserved value, appended)
  carries:

  ```
  Retention {keys_s, history_s, versions_s: u64, reserved}
  ```

  Each value is a horizon in seconds; 0 means forever. A new `get_retention` reads it.
- **Declaring is changeable.** Unlike a view, retention may be declared again, and the latest
  declaration holds.
- **Bounds on a declaration.** A horizon is 0 or between `retention_min` and `retention_max`;
  otherwise NRV-E0310.
- **The default is forever.** A cluster that never declares trims nothing and behaves exactly as
  today, bit for bit, apart from the new trees, which stay empty.
- **The retention state is a singleton groove** (new `tree_ids` 27 and 28, following the
  backfill cursor's pattern), not a reserved-table row, which would add a change to the feed on
  every pulse. For each kind it holds:
  - the declared horizon;
  - the trim cursor (a timestamp in that kind's tree);
  - `trimmed_ts`, the newest timestamp trimmed;
  - `horizon_op`, the op of the newest change trimmed.

### Trimming by pulses

- **`pulse_needed`** is also true while some kind's cursor is behind `now − horizon`. `now` is
  the prepare timestamp; there is no clock.
- **Each pulse trims at most `trim_per_pulse_max` objects across the kinds:**
  - `prefetch` scans forward from the cursor and reads what it needs to decide;
  - `commit` removes, writing one tombstone per object, then advances the cursor.

  The removal is deterministic because it is a function of the log and the forest.
- **Compaction reclaims the space.** Tombstones on append-only, timestamp-keyed tables meet their
  object at the next compaction of that range and are dropped at the last level. Trimming adds
  ordinary compaction work, about one tombstone per removed object, which the existing pacing
  absorbs.
- **The vendored patch.** Removal needs a minimal patch to `groove.zig`:
  - a `remove_object(object)` for cacheless grooves, which removes from each index tree by the
    object's own fields, since there is no cache to look the object up in;
  - `remove` enabled outside `verify` builds.

  It is recorded in UPSTREAM.md, with a groove fuzzer standing in for the dropped `forest_fuzz`
  (slice 2).

### History: the keep-last rule

- **The rule.** A change C of row R is trimmed only if a newer change of R exists whose timestamp
  is below `now − history_s`.
  - So every row keeps the change that was current at the horizon.
  - As-of reads at any op ≥ `horizon_op` stay exact, because the current row and the latest
    change at or below the horizon are kept.
- **How it is applied.** `prefetch` checks the rule on the `row_key` index (tree 4), or tree 21
  for records. Rows, records and their tombstones are never touched.
- **What is refused.** An as-of read below `horizon_op` answers `before_horizon`: an end record
  with a new flag bit, then HTTP 410 at the gateway with NRV-E0411 and the horizon's op and time.

### The feed below the horizon

- **What it holds.** Below the horizon, the change feed is a compacted prefix: the latest change
  of each row as of the horizon, in timestamp order, much like log compaction in a message log.
- **The default read.** `get_changes` with a cursor below the horizon answers `before_horizon`.
- **The opt-in.** A new `ChangesFilter` flag, carved from its reserved bytes, opts in to reading
  the compacted prefix.
  - `nerva view` (N35) and `nerva export` set it. Their consumers rebuild current state, which
    the prefix gives them exactly.
  - A consumer that needs every change does not set it, and is told.
  - Owner question 3.

### View and group versions

- **The same keep-last rule**, applied per group in GroupVersion (trees 12 and 13) and per view
  in ViewVersion (trees 14 and 15) with `versions_s`. Groups' and members' current state is
  untouched.
- **Reads.** A view read as of an op below that kind's `horizon_op` answers `before_horizon` (a
  flag bit in the view record).

### Commit keys: `key_expired`

- **What expires.** A key's row and its one change are trimmed once their commit timestamp is
  below `now − keys_s`.
- **The danger.** A resend of a trimmed key would find no row and commit again: the double apply
  P123 exists to prevent.
- **The key's age.** To refuse such a resend, the state machine must know the key's age without
  its row. Once a key horizon is declared, keys must be UUIDv7, and the state machine reads the
  key's 48-bit millisecond time (owner question 2).
- **The acceptance check.** A keyed transaction is accepted only if its key time is at least the
  later of these two:
  - `now − (keys_s − skew_max)`;
  - `keys trimmed_ts + skew_max`.

  If it is not:
  - an older key answers `key_expired` (EntryStatus 25, NRV-E0213, wire `key_expired`);
  - a key that is not v7, or is more than `skew_max` in the future, answers `key_time_invalid`
    (26, NRV-E0214).
- **Why it is safe.** Every key accepted, with time t, has a row committed at or after t −
  `skew_max`. Every key whose row may be trimmed has a time below `trimmed_ts + skew_max`. So a
  resend that passes the check finds its row, and answers `committed_before` as today.
- **Determinism.** The check uses only the prepare timestamp and the retention groove.
- **Who is affected.** Documents' keys (P180) follow the same rule, through `api.key_reply`. The
  Jepsen bank's checkers (P239c and P239d) must count `key_expired` as a definite refusal of a
  resend whose original outcome is known from the history, never as a loss.
- **Without a key horizon** (`keys_s = 0`), keys may be any 16 bytes, as today.

### Export, import and backup

- **Export version 3.** The header carries the retention declaration and each kind's
  `horizon_op` and `trimmed_ts`. The body is the compacted prefix followed by the ops above the
  horizon.
- **Import.** It accepts a first op above 1, and a row whose first change below the horizon is
  its latest, including a tombstone, without N81's "delete of a non-live row" refusal for that
  prefix. Ops above the horizon are replayed under every rule, as today.
- **What import refuses.** A v3 file whose prefix is not in timestamp order, or which carries a
  change above its own declared horizon in the prefix (NRV-E0811).
- **Old files.** Export v1 and v2 files import unchanged.
- **Backups.** The manifest's version moves with export v3 (P149d).

### Formats and R6

**Formats:** R7 changes these, each named, and nothing else:
- new `tree_ids` 27 and 28 (retention);
- new `Operation` values `declare_retention` and `get_retention`, appended;
- new `EntryStatus` values 25 `key_expired` and 26 `key_time_invalid`, appended;
- the `Retention` event and result layouts;
- a flag bit in the changes end record and in the view record (`before_horizon`);
- a flag in `ChangesFilter`, carved from its reserved bytes;
- export file version 3, and the backup manifest's version;
- `format_epoch` 1 → 2, because the meaning of stored bytes changes outside the layouts. A
  change may now be missing below the horizon, and a key's bytes carry a time once a key horizon
  is declared. P269b says such changes move the epoch by hand.

No existing identifier is renumbered. A data file written by the last release opens. Its
retention groove is empty, so it means "forever", and the file behaves exactly as before.

Every item above moves the format digest. Under P259c (strict formats), the release that ships
R7 is reached by **export and import**, never a rolling upgrade, and its release notes say so.
- The data file itself needs no conversion. Only the multiversion admission refuses to roll
  across a digest change.
- Rolling upgrades resume from that release to the next one with the same digest.
- Slice 1 lands every layout and identifier change at once, so the digest moves once in R7, not
  once per slice.

## Bounds

| Constant | Value | Where | Why |
| --- | --- | --- | --- |
| `trim_per_pulse_max` | 1,024 objects | `src/nerva/retention.zig` | Bounds a pulse's prefetch and its tombstones, and so the compaction it adds; measured in slice 3 against the bar's budget |
| `trim_scan_per_pulse_max` | 4,096 index entries | same | Bounds the keep-last scan when nothing is trimmable (long-lived rows) |
| `retention_min` | 60 s | same | Below it a key horizon is shorter than a client's retry window plus `skew_max` |
| `retention_max` | 100 years | same | A bound, asserted, not a meaning |
| `skew_max` | 10 s | same | A client's clock may run ahead of the cluster's by this much before its keys are refused as from the future |
| `pulse_trim_interval` | every pulse while behind | `state_machine.zig` | Catches up from a fresh declaration at `trim_per_pulse_max` per pulse; measured in the demo |

Each gets a test at the bound and one past it:
- a declaration at 59 s is refused with NRV-E0310;
- a pulse with 1,025 trimmable objects trims 1,024 and is pulsed again;
- a key `skew_max` + 1 ms in the future is refused with NRV-E0214.

## The demo: `zig build demo-r7`

`tests/demo/r7.py <nerva>`. A day cannot pass in CI, so the demo scales time (owner question 4):
a 60 s horizon, run for 30 horizons (about 35 minutes), which stands in for "a 1-day horizon over
30 days". The cut is recorded in `docs/demos/r7.md`.
- **The cluster.** Three replicas on loopback, each with `--statsd` to the script's listener and
  a real `NERVA_CLUSTER_KEY`, one gateway and one `nerva view`.
- **The load.** A writer sends keyed commits at a steady rate: a fixed set of rows updated,
  records written, a ledger moved by pairs, and two views over them.

Every step asserts.

| Step | Action | Expected |
| --- | --- | --- |
| 1 | Format, start, declare a layout, a ledger, two views; start the writer (UUIDv7 keys) | Every commit `committed`, or retried under its key |
| 2 | Run 2 horizons with no retention; record `grid_blocks_acquired`, export size and time, `nerva view` RSS | They grow (the baseline: unbounded) |
| 3 | `PUT /v1/retention {"keys":"60s","history":"60s","versions":"60s"}` | `GET` shows it; within 2 horizons every kind is caught up (no W0703) |
| 4 | Run 30 horizons; sample the three measures once per horizon | Over the last 20 samples, each measure's spread is under 10% of its mean, and no trend is above 1% per horizon |
| 5 | SIGKILL the primary at horizon 15; restart it | It catches up; trimming resumes; step 4's bounds hold |
| 6 | Resend a key acknowledged 2 horizons ago | `409 key_expired`, NRV-E0213; the ledger total is unchanged |
| 7 | Resend a key acknowledged 10 s ago | `committed_before` with its original op |
| 8 | Read a row as of an op from horizon 2; `get_changes` from that op | `410 before_horizon`, NRV-E0411, naming the horizon |
| 9 | Stop the writer. Export, import into a new cluster, read every view and the ledger | Every hash equals the source's and `nerva view`'s; the total is conserved |
| 10 | Redeclare `history` as forever; run 2 horizons | Trimming of history stops; nothing trimmed reappears; keys still expire |

The script prints one line per step and ends `demo-r7: PASS` or `demo-r7: FAIL step N: …`. The
`demo_r7` job in `ci.yml` is copied from `demo_r5`'s, with a 60-minute timeout. A failure is a
finding (CLAUDE.md), never re-run until it passes.

## Risks

1. **The vendored removal path is untested upstream.** Upstream's own comment says nothing calls
   `remove`. A bug there loses or resurrects objects silently. Slice 2's fuzzer is the guard, and
   it comes before any trimming.
2. **The keep-last scan on long-lived, rarely written rows** reads index entries that are not
   trimmable. `trim_scan_per_pulse_max` bounds a pulse, but the cursor may move slowly through a
   table of cold rows. It is measured in slice 3; the fix is a cursor per row range, not more
   work per pulse.
3. **Import trusts the prefix.** Below the horizon, import replays without the ledger's pair rule
   (the pairs are gone). A forged v3 file can import an unbalanced ledger. The export's checksum
   and E0811 cover damage, not forgery, as today for v2.
4. **UUIDv7 is a new client obligation** once a key horizon is declared. Nothing in `src/nerva/`
   names UUIDv7 at `c886c9f`: clients choose their keys today. Slice 5 audits every key Nerva's
   own tools and tests make (the gateway's retries, `tests/jepsen`, the demos) and makes them v7.
5. **Clock skew between the client and the cluster** beyond `skew_max` turns into refusals
   (E0214), not into wrong answers. The README says so.
6. **Compaction load.** Trimming writes one tombstone per removed object, which roughly doubles
   compaction input on the trimmed trees in steady state. The demo's flat measures include it; R3's
   sizing table should be redone after R7.
7. **The digest moves for one release**, so v0.8 to v0.9 is an export and import. It happens
   while rolling upgrades are new, and the release notes must say it plainly.

## Owner questions

1. **R7 waits for R6 to be delivered** (`demo_r6` green on `main`), or starts slice 1 and 2 beside
   it as P269 did for R6 beside R1? **I'd wait**: slice 1 moves the digest that R6's admission
   reads, and slice 2 patches a vendored file R6 does not touch, but both are easier to review once
   R6's rules have run in CI. Slice 2 alone could run early if R6 stalls.
2. **A key's age comes from UUIDv7**, required only once a key horizon is declared, or from an
   explicit `sent_at` field in the keyed entry (a wire change for every client, but no rule on the
   key's bytes)? **UUIDv7**: no new field, and v7 is a standard any client library can make;
   `sent_at` is the fallback if one cannot.
3. **The feed below the horizon** is refused by default (`before_horizon`), with an opt-in to the
   compacted prefix for `nerva view` and export; or is it served compacted to everyone, silently?
   **Refused by default**: a consumer that counts changes would otherwise be wrong without knowing.
4. **The demo's time scale.** A 60 s horizon over 30 horizons (about 35 minutes, real cluster), or
   a VOPR-only demo at 1 simulated day × 30 (fast, but not a real cluster)? **60 s × 30 on a real
   cluster**, with the VOPR drawing horizons per seed beside it; the PRODUCTION.md wording "at
   simulated time" is amended in `docs/demos/r7.md`.
5. **The default horizon is forever** (nothing trimmed unless declared), or a default such as 30
   days for keys? **Forever**: a new default would drop data from clusters that never asked, and
   would change behaviour across the export and import into R7's release.
6. **`retention_min` 60 s and `skew_max` 10 s**, or larger (for example 1 hour and 60 s) for
   production safety? **60 s and 10 s**: the demo needs 60 s, and a larger minimum belongs in the
   operator's declaration, not the bound. The README recommends days.
