## Goal

An operator declares how long Nerva keeps three kinds of past state: commit keys, row and record
history, and view and group versions. The cluster trims each kind below its horizon,
deterministically, as part of the log, with a bounded amount of work per op. What the cluster
holds is then bounded by its **live set** plus one horizon of the past:
- **Kept whatever the horizon:** every row's and record's current value, every tombstone, and
  each row's, record's, group's and view's last change or version at the horizon (keep-last).
  This part grows with the number of rows and records ever created: a 128-byte row and its
  128-byte change each, or a 512-byte record and its 512-byte record change, with their index
  entries. R7 does not bound it.
- **Bounded by the horizons:** every older change and version, and every commit key, which go
  once they are below their horizon. This part is at most one horizon's worth of writes.

So a load that rewrites a fixed set of rows and records holds a flat amount of data: the data
file's live blocks, the export and its time, and `nerva view`'s memory stay flat. A load that
creates new rows or records grows by those rows and their last changes, linearly, and R7 says so
rather than hiding it. The first client's facts (executions, receipts, runs: P123b) are new
records per operation, so **R7 as designed does not bound their growth** (owner question 8).
What was trimmed is refused by name:
- a resent key older than its horizon answers `key_expired`, never `committed`;
- a read of the past below a horizon answers `before_horizon`, never a wrong answer.

## The operator's story

1. Today a cluster grows without bound:
   - each keyed transaction leaves an 80-byte key row and a change, forever (P123);
   - each write leaves a 128-byte change (512 for a record);
   - each view or group write leaves a version.

   An export of a year-old cluster replays a year.
2. The operator runs `nerva api` and sends:

   ```
   PUT /v1/retention {"keys": "7d", "history": "30d", "versions": "30d"}
   ```

   The declaration commits like any other op; `GET /v1/retention` shows it with each kind's
   horizon (the oldest timestamp still kept) and how far trimming has caught up.
3. From then on the primary's pulses trim, a bounded slice per pulse, until each kind is caught
   up, and then keep up. Writes go on; a pulse is one op among them.
4. A client resends a key from 8 days ago: `409 key_expired` (NRV-E0213). It does not apply. The
   client knows the outcome is unknowable from Nerva and goes to its own records.
5. A client asks for a row as of 40 days ago, or for changes after a cursor from 40 days ago:
   `410 before_horizon` (NRV-E0411), naming the horizon. `nerva view` and `nerva export` read the
   compacted prefix instead (see "The feed below the horizon").
6. Loosening a horizon keeps what is still there: trimmed data does not come back, and a key
   once trimmed stays refused, even with `keys` redeclared as forever. Tightening it trims more,
   at the same bounded pace.

## Non-goals

- **Shrinking the data file.** Trimmed blocks return to the free set and are reused; the file
  never shrinks (upstream's grid has no truncation). "Flat" is measured as blocks acquired, not
  file size.
- **Reclaiming tombstones** (N3): a deleted row's tombstone, and a row's current value, are kept
  whatever the horizon. So are the catalog, layouts, ledgers, views' and groups' current state,
  members, indexes and their entries.
- **Per-table or per-view horizons.** One horizon per kind, cluster-wide. A later milestone may add
  them; the declaration's layout keeps reserved bytes for it.
- **Horizons by op count** or by size. Time only, from prepare timestamps.
- **Object storage, tiering, archiving** what is trimmed. An operator who must keep everything
  exports before trimming, or does not declare a horizon.
- **Trimming at compaction time.** It would never fire: append-only, timestamp-keyed tables reach
  the last level by `move_table` and are never rewritten there (`compaction.zig`). See "Design".
  This departs from R7's scope in `docs/PRODUCTION.md` ("Compaction drops what is older,
  deterministically"): here pulses write tombstones and compaction only reclaims them. The brief
  does not edit that line; it is owner question 7, and the answer's pull request amends it.
- **Expiring rows or records themselves.** A row or record that is never deleted is kept, with
  its last change, however old. Bounding a load that only creates (owner question 8) needs the
  application to delete, or a later milestone.
- **A rolling upgrade into R7's release.** Its formats move the digest; P259c says export and
  import (see "Formats and R6").

## Design

### Declared in the log

- **Operations.** A new `Operation.declare_retention` (the next free reserved value, appended)
  carries:

  ```
  Retention {keys_s, history_s, versions_s: u64, reserved}
  ```

  Each value is a horizon in seconds; 0 means forever. A new `get_retention` reads it.
- **Declaring is changeable.** Unlike a view, retention may be declared again, and the latest
  declaration holds.
- **Bounds on a declaration.** A horizon is 0 or between `retention_min` and `retention_max`;
  otherwise NRV-E0310.
- **The default is forever.** A cluster that never declares trims nothing and behaves exactly as
  today, bit for bit, apart from the new trees, which stay empty.
- **The retention state is a singleton groove** (new `tree_ids` 27 and 28, following the
  backfill cursor's pattern), not a reserved-table row, which would add a change to the feed on
  every pulse. For each kind it holds:
  - the declared horizon;
  - the trim cursor (a timestamp in that kind's tree);
  - `trimmed_ts`, the newest timestamp trimmed;
  - `horizon_op`, the op of the newest change trimmed.

### Trimming by pulses

- **`pulse_needed`** is also true while some kind's cursor is behind `now − horizon`. `now` is
  the prepare timestamp; there is no clock.
- **Each pulse examines at most `trim_per_pulse_max` objects across the kinds:**
  - `prefetch` scans forward from the cursor, in timestamp order, and reads what it needs to
    decide (for history and versions, each examined object's predecessor: see the keep-last
    rule);
  - `commit` removes, writing one tombstone per removed object, then advances the cursor past
    what it examined.

  Each examined object removes at most one object, so a pulse removes at most
  `trim_per_pulse_max`. The removal is deterministic because it is a function of the log and the
  forest.
- **The lag is bounded.** One client op creates at most `created_per_op_max` changes, record
  changes, versions and key rows. It is derived at comptime from `state_machine.zig`'s per-op
  limits (`commit_entries_max` entries, `commit_wide_entries_max` record changes, the groups and
  views an op touches), and asserted. `trim_per_pulse_max` is `2 × created_per_op_max`. So a pulse
  writes at most twice what the largest client op writes, and it trims faster than any writer
  creates, as long as a pulse commits at least once per client op while trimming is behind.
  - Today the primary sends itself a pulse after every commit while `pulse_needed` is true
    (`replica.zig:5110`). Slice 3 checks, by reading `send_request_pulse_to_self` and by a test
    under a saturated pipeline of max-size batches, that this gives at least one pulse per client
    op. If the request queue can starve the pulse, it is a stop: the fix touches a vendored file.
  - Given that, once caught up, a kind's cursor stays within one client op and one
    `pulse_timeout` of its horizon. While catching up from a fresh declaration, the backlog
    falls by at least `created_per_op_max` per client op and pulse pair, and by
    `trim_per_pulse_max` per idle pulse.
  - W0704 is the alarm if this bound is broken, never the mechanism.
- **Compaction reclaims the space.** Tombstones on append-only, timestamp-keyed tables meet their
  object at the next compaction of that range and are dropped at the last level. Trimming adds
  ordinary compaction work, about one tombstone per removed object, which the existing pacing
  absorbs.
- **The vendored patch.** Removal needs a minimal patch to `groove.zig`:
  - a `remove_object(object)` for cacheless grooves, which removes from each index tree by the
    object's own fields, since there is no cache to look the object up in;
  - `remove` enabled outside `verify` builds.

  It is recorded in UPSTREAM.md, with a groove fuzzer standing in for the dropped `forest_fuzz`
  (slice 2).

### History: the keep-last rule

- **The rule.** Every row keeps its newest change at or below `now − history_s`, and every
  change above it. A change is trimmed only once a newer change of the same row is itself at or
  below the horizon.
- **How a forward cursor applies it: trim the predecessor.** The history cursor walks changes
  (tree 3, and tree 20 for records) in timestamp order, up to `now − history_s`. When it reaches
  a change C' of row R at time t', `prefetch` reads R's newest change older than t' in the
  `row_key` index (tree 4, or tree 21 for records), one bounded range read, newest first, limit
  1. If there is one, C, `commit` removes it. Then the cursor moves past t'.
  - Checking C itself ("is a newer change of R below the horizon?") would not work with a forward
    cursor: when the cursor reaches C, R's next change is usually still above the horizon, and
    the cursor never comes back to C. Trimming the predecessor gives the same result and never
    looks back.
  - A row's first change has no predecessor and removes nothing. A deleted row's tombstone change
    is its last change, and the row itself is never touched, so it keeps both.
- **The invariant.** Let c be the history cursor (every change at or below c has been examined).
  For every row R:
  - exactly one of R's changes at or below c is kept, the newest; every change of R above c is
    kept.

  By induction on the changes the cursor examines: before R's first change, R has none at or
  below c. When the cursor examines C' of R, R's only kept change at or below the old cursor is,
  by the hypothesis, the newest one older than C', which is what the range read finds; removing
  it leaves C' as R's only kept change at or below the new cursor. Changes of other rows are
  untouched. Since c ≤ `now − history_s`, every row keeps the change that was current at the
  horizon.
- **What stays exact.** As-of reads at any op ≥ `horizon_op` (the op of the newest change
  trimmed) stay exact: for any such op, each row's change current at that op is either above the
  cursor or is the newest at or below it, and both are kept. Rows, records and their tombstones
  are never touched.
- **What is refused.** An as-of read below `horizon_op` answers `before_horizon`: an end record
  with a new flag bit, then HTTP 410 at the gateway with NRV-E0411 and the horizon's op and time.

### The feed below the horizon

- **What it holds.** Below the horizon, the change feed is a compacted prefix: the latest change
  of each row as of the horizon, in timestamp order, much like log compaction in a message log.
  A commit key's row and its change are removed whole (see "Commit keys"), so the prefix holds no
  change of a key whose row was trimmed. That is the one exception to keep-last, and it is right
  for the prefix's purpose: the prefix rebuilds current state, where a trimmed key no longer
  exists.
- **Where the feed's horizon is.** Changes leave the feed under two horizons: history's and
  keys'. So the feed's refusal point is `feed_horizon_op = max(history horizon_op, keys
  horizon_op)`, never history's alone. With `keys: 7d` and `history: forever`, a reader of
  `get_changes` from op 1 is told `before_horizon` once any key has been trimmed; it is never
  served a feed with key changes silently missing.
- **The default read.** `get_changes` with a cursor below `feed_horizon_op` answers
  `before_horizon`.
- **The opt-in.** A new `ChangesFilter` flag, carved from its reserved bytes, opts in to reading
  the compacted prefix.
  - `nerva view` (N35) and `nerva export` set it. Their consumers rebuild current state, which
    the prefix gives them exactly.
  - A consumer that needs every change does not set it, and is told.
  - Owner question 3.

### View and group versions

- **The same keep-last rule, by predecessor**, applied per group in GroupVersion (trees 12 and
  13) and per view in ViewVersion (trees 14 and 15) with `versions_s`: the versions cursor walks
  versions in timestamp order, and on reaching a version V' below the horizon it removes the
  same group's or view's newest version older than V', read from the per-group or per-view index.
  The invariant and its proof are history's, with "group" or "view" for "row". Groups' and
  members' current state is untouched.
- **Reads.** A view read as of an op below that kind's `horizon_op` answers `before_horizon` (a
  flag bit in the view record).

### Commit keys: `key_expired`

- **What expires.** A key's row and its one change are removed together once the row's
  timestamp is at or below `now − keys_s`. The keys cursor walks the key rows' changes in
  timestamp order.
- **The danger.** A resend of a trimmed key would find no row and commit again: the double apply
  P123 exists to prevent.
- **The key's age.** To refuse such a resend, the state machine must know the key's age without
  its row. Keys must be UUIDv7 once a key horizon is declared, and the state machine reads the
  key's 48-bit millisecond time (owner question 2, which also weighs this against the first
  client's derived keys). With `sent_at` instead, `k` is read from that field and nothing else in
  the check below changes.
- **Units.** Everything below is in nanoseconds, as timestamps are. A key's time is
  `k = key_ms × 1,000,000`, the floor of its real time; both checks below use the same `k`, so the
  floor costs nothing.
- **Row timestamps sit below the prepare timestamp.** A key row is written with its entry's own
  timestamp (`commit_key_put(op, entry_timestamp, …)`), which counts up to the op's prepare
  timestamp P: `P − span_max ≤ T ≤ P`. `span_max` is the most timestamps one op reserves
  (`prepare_delta` plus `versions_reserve`, `state_machine.zig:1236`: at most
  `commit_entries_max × entry_timestamps` plus the versions reserve), a comptime constant.
  Slice 5 derives it, and asserts the bound in `commit_key_put`.
- **The order, as P123 has it.** The key's row is looked up first, before every other rule. A row
  found answers as today: `committed_before`, `key_reused` or `key_collision` (and the gateway's
  `200 {"status": "committed", "op", "replayed": true}` for the first). Only when **no row** is
  found does the age check run.
- **The age check.** Let `m = skew_max + span_max`. A keyed transaction with no row is accepted
  only if all of these hold (`now` is P):
  - `k ≤ now + skew_max` (not from the future);
  - if a key horizon is declared (`keys_s ≠ 0`): `k > now − keys_s + m`;
  - if any key was ever trimmed (keys `trimmed_ts ≠ 0`): `k > trimmed_ts + m`, strictly.

  If it is not:
  - a key that fails the second or third bound answers `key_expired` (EntryStatus 25,
    NRV-E0213, wire `key_expired`);
  - a key that is not v7 while v7 is required, or fails the first bound, answers
    `key_time_invalid` (26, NRV-E0214).
- **Why it is safe.** A key accepted with time k, at prepare timestamp P, has `k ≤ P + skew_max`,
  and its row has `T ≥ P − span_max ≥ k − m`. Every key row trimmed has `T ≤ trimmed_ts`. A
  resend with no row that passes the third bound has `k > trimmed_ts + m`, so if it had ever been
  accepted, its row would have `T ≥ k − m > trimmed_ts` and could not have been trimmed. So no row
  means it never committed, and committing it now is its first commit. The bound is strict
  because `trimmed_ts` is itself a trimmed row's timestamp: with `≥`, a resend of the row at
  exactly `trimmed_ts` would pass and commit twice.
- **The check outlives the horizon.** The third bound, and the v7 requirement, hold whenever keys
  `trimmed_ts ≠ 0`, whatever the current declaration. Redeclaring `keys` as forever after keys
  were trimmed stops trimming, but a resend of a trimmed key still answers `key_expired`. Only a
  cluster that has never trimmed a key accepts any 16 bytes, as today. `trimmed_ts` travels in
  export v3's header, so an imported cluster keeps the check.
- **Determinism.** The check uses only the prepare timestamp, the key's bytes and the retention
  groove.
- **Who is affected.** Documents' keys (P180) follow the same rule, through `api.key_reply`. The
  Jepsen bank's checkers (P239c and P239d) must count `key_expired` as a definite refusal of a
  resend whose original outcome is known from the history, never as a loss.

### Export, import and backup

- **Export version 3.** The header carries the retention declaration and each kind's
  `horizon_op` and `trimmed_ts`. The body is the compacted prefix followed by the ops above the
  horizon.
- **Import.** It accepts a first op above 1, and a row whose first change below the horizon is
  its latest, including a tombstone, without N81's "delete of a non-live row" refusal for that
  prefix. Ops above the horizon are replayed under every rule, as today.
- **The key check survives import.** Import sets each kind's `trimmed_ts` and `horizon_op` from
  the header before it replays anything, so a resend of a key trimmed before the export still
  answers `key_expired` on the new cluster.
- **What import refuses.** A v3 file whose prefix is not in timestamp order, which carries a
  change above its own declared horizon in the prefix, or which carries a change of the key table
  (`0xFFFF0003`) at or below its own keys `trimmed_ts` (NRV-E0811).
- **Old files.** Export v1 and v2 files import unchanged.
- **Backups.** The manifest's version moves with export v3 (P149d).

### Formats and R6

**Formats:** R7 changes these, each named, and nothing else:
- new `tree_ids` 27 and 28 (retention);
- new `Operation` values `declare_retention` and `get_retention`, appended;
- new `EntryStatus` values 25 `key_expired` and 26 `key_time_invalid`, appended;
- the `Retention` event and result layouts;
- a flag bit in the changes end record and in the view record (`before_horizon`);
- a flag in `ChangesFilter`, carved from its reserved bytes;
- export file version 3, and the backup manifest's version;
- `format_epoch` 1 → 2, because the meaning of stored bytes changes outside the layouts. A
  change may now be missing below the horizon, and a key's bytes carry a time once a key horizon
  is declared. P269b says such changes move the epoch by hand.

No existing identifier is renumbered. A data file written by the last release opens. Its
retention groove is empty, so it means "forever", and the file behaves exactly as before.

Every item above moves the format digest. Under P259c (strict formats), the release that ships
R7 is reached by **export and import**, never a rolling upgrade, and its release notes say so.
- The data file itself needs no conversion. Only the multiversion admission refuses to roll
  across a digest change.
- Rolling upgrades resume from that release to the next one with the same digest.
- Slice 1 lands every layout and identifier change at once, so the digest moves once in R7, not
  once per slice.

## Bounds

| Constant | Value | Where | Why |
| --- | --- | --- | --- |
| `created_per_op_max` | derived | `src/nerva/retention.zig` | The most changes, record changes, versions and key rows one client op creates, from `state_machine.zig`'s per-op limits; asserted at comptime |
| `trim_per_pulse_max` | `2 × created_per_op_max` objects examined | same | Each examined object removes at most one, so a pulse writes at most twice the largest client op, and trimming outruns any writer while a pulse commits once per client op ("Trimming by pulses"); its compaction cost is measured in slice 3 |
| `span_max` | derived | same | The most timestamps one op reserves; a key row's timestamp is within it below its prepare timestamp ("Commit keys") |
| `retention_min` | 60 s | same | Below it a key horizon is shorter than a client's retry window plus `skew_max` |
| `retention_max` | 100 years | same | A bound, asserted, not a meaning |
| `skew_max` | 10 s | same | A client's clock may run ahead of the cluster's by this much before its keys are refused as from the future |
| `pulse_trim_interval` | every pulse while behind | `state_machine.zig` | At least one pulse per client op while behind (checked in slice 3); catches up from a fresh declaration at `trim_per_pulse_max` per idle pulse; measured in the demo |

Each gets a test at the bound and one past it:
- a declaration at 59 s is refused with NRV-E0310;
- a pulse with `trim_per_pulse_max + 1` objects to examine examines `trim_per_pulse_max` and is
  pulsed again;
- a saturated pipeline of max-size batches, each creating `created_per_op_max` objects, does not
  make the trimming backlog grow;
- a key `skew_max` + 1 ms in the future is refused with NRV-E0214.

## The demo: `zig build demo-r7`

`tests/demo/r7.py <nerva>`. A day cannot pass in CI, so the demo scales time (owner question 4):
a 60 s horizon, run for 30 horizons (about 35 minutes), which stands in for "a 1-day horizon over
30 days". The cut is recorded in `docs/demos/r7.md`.
- **The cluster.** Three replicas on loopback, each with `--statsd` to the script's listener and
  a real `NERVA_CLUSTER_KEY`, one gateway and one `nerva view`.
- **The load.** A writer sends keyed commits (UUIDv7 keys) at a steady rate. It **rewrites a
  fixed set** of rows and records, created in step 1, moves a ledger by pairs among them, and two
  views read them. After step 1 it creates nothing but commit keys, which expire. Once per horizon
  it sends a burst of commits at the batch limit (`commit_entries_max` entries each) for 5 s.
  This is the load whose data R7 holds flat ("Goal"). A load that creates rows grows, and step 7
  measures that growth rather than hiding it.

Every step asserts.

| Step | Action | Expected |
| --- | --- | --- |
| 1 | Format, start, declare a layout, a ledger, two views; create the fixed rows and records; start the writer | Every commit `committed`, or retried under its key |
| 2 | Run 2 horizons with no retention; record `grid_blocks_acquired`, export size and time, `nerva view` RSS | They grow (the baseline: unbounded) |
| 3 | `PUT /v1/retention {"keys":"60s","history":"60s","versions":"60s"}` | `GET` shows it; within 2 horizons every kind is caught up (no W0704) |
| 4 | Run 30 horizons, bursts included; sample the three measures once per horizon | Over the last 20 samples, each measure's spread is under 10% of its mean, and no trend is above 1% per horizon; no W0704 during the bursts |
| 5 | SIGKILL the primary at horizon 15; restart it | It catches up; trimming resumes; step 4's bounds hold |
| 6 | Resend a key acknowledged 2 horizons ago | `409 key_expired`, NRV-E0213; the ledger total is unchanged |
| 7 | Start a second writer that creates new records at a fixed rate r for 3 horizons; then stop it | `grid_blocks_acquired` grows per horizon by r × 60 s × (a record, its record change and their index entries), within 25%, and by no more: the rewritten set's history stays trimmed. The script prints the growth per record. |
| 8 | Resend a key acknowledged 10 s ago | `200 {"status": "committed", "op": <its original op>, "replayed": true}` (P123's wire answer for `committed_before`) |
| 9 | Read a row as of an op from horizon 2; `get_changes` from that op | `410 before_horizon`, NRV-E0411, naming the horizon |
| 10 | Stop the writer. Export, import into a new cluster, read every view and the ledger; resend on the new cluster a key trimmed before the export | Every hash equals the source's and `nerva view`'s; the total is conserved; the resend answers `409 key_expired` |
| 11 | On the source, redeclare `history` as forever; run 2 horizons | Trimming of history stops; nothing trimmed reappears; keys still expire |
| 12 | Redeclare `keys` as forever; resend a key trimmed in step 4; send a commit under a non-v7 key | `409 key_expired`, NRV-E0213, and `key_time_invalid`, NRV-E0214: the check outlives the horizon; nothing commits twice |

The script prints one line per step and ends `demo-r7: PASS` or `demo-r7: FAIL step N: …`. The
`demo_r7` job in `ci.yml` is copied from `demo_r5`'s, with a 60-minute timeout. A failure is a
finding (CLAUDE.md), never re-run until it passes.

## Risks

1. **The vendored removal path is untested upstream.** Upstream's own comment says nothing calls
   `remove`. A bug there loses or resurrects objects silently. Slice 2's fuzzer is the guard, and
   it comes before any trimming.
2. **The predecessor read costs one range read per examined change.** The cursor walks changes
   in timestamp order, so its work follows what was written, not how many rows exist: cold rows
   cost nothing. But each examined change is one `row_key` range read in `prefetch`, up to
   `trim_per_pulse_max` per pulse. Slice 3 measures a pulse's prefetch against a max-size client
   op's; if it is slower, the fix is a smaller multiple in `trim_per_pulse_max` with the lag
   bound restated, never an unbounded pulse.
3. **Import trusts the prefix.** Below the horizon, import replays without the ledger's pair rule
   (the pairs are gone). A forged v3 file can import an unbalanced ledger. The export's checksum
   and E0811 cover damage, not forgery, as today for v2.
4. **UUIDv7 is a new client obligation** once a key horizon is declared, and stays one once a key
   was trimmed. Nothing in `src/nerva/` names UUIDv7 at `c886c9f`: clients choose their keys
   today. Slice 5 audits every key Nerva's own tools and tests make (the gateway's retries,
   `tests/jepsen`, the demos) and makes them v7. The first client is not audited here, and it is
   the harder case (owner question 2): Botpike derives its ledger IDs deterministically from
   their inputs, and a key derived the same way is not v7.
5. **Clock skew between the client and the cluster** beyond `skew_max` turns into refusals
   (E0214), not into wrong answers. The README says so.
6. **Compaction load.** Trimming writes one tombstone per removed object, which roughly doubles
   compaction input on the trimmed trees in steady state. The demo's flat measures include it; R3's
   sizing table should be redone after R7.
7. **The digest moves for one release**, so v0.8 to v0.9 is an export and import. It happens
   while rolling upgrades are new, and the release notes must say it plainly.
8. **Growth is bounded by the live set, not absolutely.** A load that creates rows or records
   still grows, by each one and its last change ("Goal"). The first client's facts are such a
   load, so R7 slows its growth (no history, no keys past the horizons) without bounding it
   (owner question 8).

## Owner questions

1. **R7 waits for R6 to be delivered** (`demo_r6` green on `main`), or starts slice 1 and 2 beside
   it as P269 did for R6 beside R1? **I'd wait**: slice 1 moves the digest that R6's admission
   reads, and slice 2 patches a vendored file R6 does not touch, but both are easier to review once
   R6's rules have run in CI. Slice 2 alone could run early if R6 stalls.
2. **A key's age comes from UUIDv7**, required once a key horizon is declared (and for ever
   after any key was trimmed), or from an explicit `sent_at` field in the keyed entry? This
   changes P123 in substance: P123 says "clients choose keys; a key names one logical
   operation", and v7 takes that choice away.
   - **The first client's case.** Botpike's invariant is "the same inputs produce the same IDs".
     A key derived from a hash of the operation is not v7. A v7 key must carry the time of the
     operation's **first** attempt, so Botpike would have to store each key before its first
     send and read it back on every retry. A retry that re-derives the key after a restart gets
     a new time, and with it a new key: at-most-once is lost, silently.
   - **`sent_at`** is the first attempt's time, sent beside the key. It fits in the key entry's
     value, whose bytes after the key must be zero today (P123), so it changes a meaning, not a
     layout; an older cluster answers `key_invalid` to it. It has the same cost as v7: a
     re-derived `sent_at` is a new time, so the client must store it too. What it saves is that
     the key itself stays the client's choice, derived or random.
   - **Neither** works for a client that cannot store anything before its first send. A key
     horizon is then unsafe for it, and it should not be declared.

   **`sent_at`**, now that the first client's keys are counted: Botpike keeps its derived keys
   and adds one stored time per operation, which it needs either way. UUIDv7 is the fallback if
   the wire change is refused. Either way the key horizon is opt-in (question 5), and the README
   says what a client must store.
3. **The feed below the horizon** is refused by default (`before_horizon`), with an opt-in to the
   compacted prefix for `nerva view` and export; or is it served compacted to everyone, silently?
   **Refused by default**: a consumer that counts changes would otherwise be wrong without knowing.
4. **The demo's time scale.** A 60 s horizon over 30 horizons (about 35 minutes, real cluster), or
   a VOPR-only demo at 1 simulated day × 30 (fast, but not a real cluster)? **60 s × 30 on a real
   cluster**, with the VOPR drawing horizons per seed beside it; the PRODUCTION.md wording "at
   simulated time" is amended in `docs/demos/r7.md`.
5. **The default horizon is forever** (nothing trimmed unless declared), or a default such as 30
   days for keys? **Forever**: a new default would drop data from clusters that never asked, and
   would change behaviour across the export and import into R7's release.
6. **`retention_min` 60 s and `skew_max` 10 s**, or larger (for example 1 hour and 60 s) for
   production safety? **60 s and 10 s**: the demo needs 60 s, and a larger minimum belongs in the
   operator's declaration, not the bound. The README recommends days.
7. **Trimming by pulses instead of compaction.** `docs/PRODUCTION.md` scopes R7 as "Compaction
   drops what is older, deterministically". This brief has pulses write tombstones and leaves
   compaction only to reclaim them, because compaction never rewrites the append-only trees
   ("Non-goals"). Accept the change, and amend PRODUCTION.md's scope line in the answer's pull
   request? **Yes**: the goal (bounded, deterministic, in the log) is kept; only the mechanism
   moves. This brief does not edit that line.
8. **Bounded by the live set.** PRODUCTION.md's goal is "disk use, export and import stay
   bounded". As designed, they stay bounded only for a load that rewrites a fixed set; a load
   that creates rows or records, like the first client's facts (executions, receipts, runs:
   P123b), still grows by each one and its last change. Options:
   - (a) accept "bounded by the live set plus one horizon" as R7's goal, and amend PRODUCTION.md;
   - (b) add expiry of rows or records by age to R7, a new kind with its own reads and refusals;
   - (c) leave it to the application, which deletes what it no longer needs.

   **(a), with (c) as the first client's path**: deleting is already the application's choice,
   and expiring live facts by age is a semantic change no client has asked for. The demo's
   step 7 measures the growth, so the answer can be checked against numbers.
