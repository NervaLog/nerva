## Goal

An operator declares how long Nerva keeps two kinds of past state: row and record history, and
view and group versions. The cluster trims each kind below its horizon, deterministically, as
part of the log, with a bounded amount of work per op. What the cluster holds is then bounded by
its **live set** plus one horizon of the past and the trimming backlog (owner question 8):
- **Kept whatever the horizon:** every row's and record's current value, every tombstone, each
  row's, record's, group's and view's last change or version at the horizon (keep-last), and
  every commit key's row and change (key retention is cut). This part grows with the number of
  rows, records and keys ever created: a 128-byte row and its 128-byte change each, a 512-byte
  record and its 512-byte record change, or an 80-byte key row and its change, with their index
  entries. R7 does not bound it.
- **Bounded by the horizons:** every older change and version, which go once they are below
  their horizon. This part is one horizon's worth of writes, plus what trimming has not yet
  reached.

So a load that rewrites a fixed set of rows and records, without commit keys, holds a flat
amount of data: the data file's live blocks, the export and its time, and `nerva view`'s memory
stay flat. A load that creates rows, records or keys grows by each one and its last change,
linearly, and R7 says so rather than hiding it.

What was trimmed is refused by name: a read of the past below a horizon answers
`before_horizon`, never a wrong answer and never a short one.

## Cuts

This brief proposes two cuts from R7's scope as `docs/PRODUCTION.md` and the README table state
it ("Commit keys, history and view versions trimmed below a horizon"). Both wait for the owner
(question 7); the pull request that records the answer amends those lines and GOALS-1.0's.
`docs/demos/r7.md` records them.

- **Retention of commit keys.** Three review rounds found that a trimmed key cannot be refused
  soundly without new mechanism. A resend of a trimmed key finds no row and commits again, the
  double apply P123 exists to prevent, unless the state machine can tell the key's age without
  its row. Every design tried so far has a hole:
  - a key's time read from UUIDv7 bits fails for keys accepted before the check existed (rows
    written before the declaration, or while `keys` was forever), and for derived keys that
    happen to carry v7 bits with an arbitrary time (P123's first client derives its keys);
  - an explicit `sent_at` is a wire change, and a client that recomputes it on retry commits
    twice once the row is gone;
  - both need an exact bound on a key row's timestamp below its prepare timestamp.

  Open questions for the later milestone: where a key's age comes from (UUIDv7, `sent_at`, or a
  server-assigned epoch the client must store); how keys accepted before the rule are handled
  (never trimmed, or trimmed only from an op recorded as the first that enforced it); documents'
  keys (P180); and the Jepsen bank's treatment of the new refusal (P239c, P239d). Until then, R7
  never removes a key row or its change, and P123 stands.
- **Retention of facts.** The first client's facts (executions, receipts, runs: P123b) are new
  records per operation, so R7 does not bound their growth either.

## The operator's story

1. Today a cluster grows without bound:
   - each write leaves a 128-byte change (512 for a record);
   - each view or group write leaves a version;
   - each keyed transaction leaves an 80-byte key row and a change (P123), which R7 keeps.

   An export of a year-old cluster replays a year.
2. The operator runs `nerva api` and sends:

   ```
   PUT /v1/retention {"history": "30d", "versions": "30d"}
   ```

   The declaration commits like any other op; `GET /v1/retention` shows it with each kind's
   `horizon_op`, the feed's trimmed timestamp, and how far trimming has caught up. A `keys` field
   is refused (NRV-E0310): key retention is not in R7.
3. From then on the primary's pulses trim, a bounded slice per pulse, until each kind is caught
   up, and then keep up. Writes go on; a pulse is one op among them.
4. A client asks for a row as of 40 days ago, pages a row's history past the horizon, or asks for
   changes after a cursor from 40 days ago: `410 before_horizon` (NRV-E0411), naming the horizon.
   `nerva view` and `nerva export` read the compacted prefix instead (see "The feed below the
   horizon").
5. Loosening a horizon keeps what is still there: trimmed data does not come back. Tightening it
   trims more, at the same bounded pace.

## Non-goals

- **Shrinking the data file.** Trimmed blocks return to the free set and are reused; the file
  never shrinks (upstream's grid has no truncation). "Flat" is measured as blocks acquired, not
  file size.
- **Reclaiming tombstones** (N3): a deleted row's tombstone, and a row's current value, are kept
  whatever the horizon. So are the catalog, layouts, ledgers, views' and groups' current state,
  members, indexes and their entries.
- **Retention of commit keys, and of facts** (rows or records themselves, by age or otherwise):
  proposed cuts (see "Cuts", owner question 7). A row, record or key that is never deleted is
  kept, with its last change.
- **Per-table or per-view horizons.** One horizon per kind, cluster-wide. A later milestone may add
  them; the declaration's layout keeps reserved bytes for it.
- **Horizons by op count** or by size. Time only, from prepare timestamps.
- **Object storage, tiering, archiving** what is trimmed. An operator who must keep everything
  exports before trimming, or does not declare a horizon.
- **Trimming at compaction time.** It would never fire: append-only, timestamp-keyed tables reach
  the last level by `move_table` and are never rewritten there (`compaction.zig`). See "Design".
  This departs from R7's scope in `docs/PRODUCTION.md` ("Compaction drops what is older,
  deterministically"): here pulses write tombstones and compaction only reclaims them. The brief
  does not edit that line; it is owner question 6, and the answer's pull request amends it.
- **Trimming inside client ops.** Each tree's tables hold `lsm_compaction_ops` times its runtime
  per-op limit (`tree.zig:116`); a client op that also trimmed could exceed it. Only pulses trim.
- **A rolling upgrade into R7's release.** Its formats move the digest; P259c says export and
  import (see "Formats and R6").

## Design

### Declared in the log

- **Operations.** A new `Operation.declare_retention` (the next free reserved value, appended)
  carries:

  ```
  Retention {history_s, versions_s: u64, reserved}
  ```

  Each value is a horizon in seconds; 0 means forever. A new `get_retention` reads it.
- **Declaring is changeable.** Unlike a view, retention may be declared again, and the latest
  declaration holds.
- **Bounds on a declaration.** A horizon is 0 or between `retention_min` and `retention_max`, and
  the reserved bytes are zero; otherwise NRV-E0310.
- **The default is forever.** A cluster that never declares trims nothing and behaves exactly as
  today, apart from the new trees, which stay empty, and the predecessor links ("Predecessor
  links"), which every write now sets and no reply shows.
- **The retention state is a singleton groove** (new `tree_ids` 27 and 28, following the
  backfill cursor's pattern), not a reserved-table row, which would add a change to the feed on
  every pulse.

### Tracks and the horizon

Trimming walks four **tracks**, one per trimmed tree pair, each in timestamp order:

| Track | Kind | Walks | Removes |
| --- | --- | --- | --- |
| changes | history | tree 3 (changes) | a change's predecessor (trees 3, 4) |
| record changes | history | tree 20 | a record change's predecessor (trees 20, 21) |
| group versions | versions | tree 12 | a version's predecessor (trees 12, 13) |
| view versions | versions | tree 14 | a version's predecessor (trees 14, 15) |

No two tracks write the same tree.

The retention groove holds the declared horizons and, per track:
- `cursor_ts`: the timestamp of the newest object examined (every object at or below it has
  been examined);
- `cursor_op`: that object's op;
- `trimmed_ts`: the **largest** timestamp removed so far (0: nothing yet). Removals do not happen
  in timestamp order (examining B@150 removes B@100, then examining A@200 removes A@50), so
  `commit` sets it to `max(trimmed_ts, removed)` and asserts that it never decreases;
- `next_ts`: a lower bound on the oldest object not yet examined.

**The horizon of a kind is an op:** `horizon_op` is the largest `cursor_op` of the kind's
tracks, 0 before anything was examined. It moves whenever the cursor does, even where an
examination removed nothing, so it is conservative but never wrong:
- **every as-of read at an op ≥ `horizon_op` is exact** ("What stays exact", below);
- **every as-of read at an op < `horizon_op` answers `before_horizon`**, whether or not the
  answer it would have given was removed.

History pages and the feed are refused by timestamp ("History pages", "The feed below the
horizon").

### Trimming by pulses

- **When a pulse is needed.** `pulse_needed` is also true when, for some track of a kind with a
  horizon, `next_ts ≤ now − horizon`. `now` is the prepare timestamp; there is no clock.
  - A pulse's scan that reaches the end of its tree sets `next_ts` to the pulse's prepare
    timestamp + 1: anything written later is newer.
  - A scan that stops at an object above the horizon sets `next_ts` to that object's timestamp.
  - A scan that stops at its budget sets `next_ts` to `cursor_ts + 1`, still due.

  So a caught-up, idle cluster pulses for retention at most once per horizon per track, and
  `pulse_needed` is false between those times. It is never true forever once a horizon is
  declared.
- **One scan per track per pulse.** `prefetch` runs at most one forward range scan per track,
  from `cursor_ts + 1` up to `now − horizon`, limited to the track's budget. The scans run one
  after another, as backfill's do, so they need one scan at a time, within `lsm_scans_max`.
  What a scan returns is kept in a buffer per track, allocated at startup and sized to the
  largest budget any `batch_size_limit` gives it, for `commit`. Nothing else is read: removal
  needs no predecessor read ("Predecessor links").
- **`commit` removes** by writing tombstones from the scanned objects' own fields, then moves the
  cursor fields past what it examined. The removal is deterministic because it is a function of
  the log and the forest.
- **The budget is the tree's runtime limit.** A track examines at most `trim_budget`, its object
  tree's runtime `batch_value_count_limit`, the value the tree's tables, stash and scope were
  sized from at startup (`tree.zig:116`, `groove.zig:776`): `commit_entries_limit` for changes,
  `record_writes_limit` for record changes, `groups_limit` for group versions and `views_max`
  for view versions. Each examined object removes at most one object from each of its two trees,
  whose index tree has the same limit (`state_machine.zig:837-924`). So a pulse's tombstones in
  a tree never exceed what one client op may write there, at whatever `batch_size_limit` the
  cluster runs, and no table layout changes.
  - **A smaller `batch_size_limit`**, as the VOPR draws on half its seeds, gives a smaller budget,
    and a pulse trims less. The per-seed draw (slice 6) covers both halves, and slice 3 tests a
    pulse at the budget under the smallest `batch_size_limit` the VOPR draws.
  - The budget depends on `batch_size_limit` exactly as a backfill pulse's `group_writes_limit`
    does today: every replica of a cluster runs with the same limit, or backfill would already
    diverge.
  - A pulse that backfills (N52) does not trim a tree that backfill writes. Trimming of that tree
    waits until the backfill is done.
- **The lag.** See "The lag bound" below; it is owner question 8.
- **Compaction reclaims the space.** Tombstones on append-only, timestamp-keyed tables meet their
  object at the next compaction of that range and are dropped at the last level. Trimming adds
  ordinary compaction work, about one tombstone per removed object, which the existing pacing
  absorbs.
- **The vendored patch.** Removal needs one minimal addition to `groove.zig`: `remove_by_key`, for
  cacheless grooves, which tombstones the objects tree by timestamp (`tombstone_from_key`) and
  each index tree by a key the caller gives, since there is no cache to look the object up in.
  Every trimmed groove is cacheless, so the cached `remove` stays as it is, unused. The patch is
  recorded in UPSTREAM.md, with a groove fuzzer standing in for the dropped `forest_fuzz`
  (slice 2).

### The lag bound

How many client ops commit between two pulses decides whether trimming keeps up. Today, by the
code above:
- at most one pulse is in flight, and it is queued at the tail, behind every client request
  already queued or prepared;
- each client has at most one request in flight, so at most `clients_max` (64) client ops sit
  ahead of it;
- so between two pulses, at most q client ops commit, where q ≤ 64 is the number of clients with
  a request outstanding.

Let L be a tree's runtime `batch_value_count_limit` (the cluster's, from its `batch_size_limit`).
A client op writes at most L objects in that tree, and a pulse removes at most L. So **trimming
keeps pace when the client ops between two pulses write, on average, at most L/q objects per
tree that will later be trimmed.** With one writer (q = 1) it always keeps pace, batches at the
limit included. Under sustained overload by many writers at the batch limit, the backlog
(objects below the horizon not yet examined) grows by up to (q − 1) × L per pulse, on disk, and
drains at up to L per pulse once the load falls. Nothing in memory grows: the backlog is data on
disk, and every queue and buffer keeps its asserted limit.

A hard bound needs one of three changes, and the choice is owner question 8:
- **(a) No change** (recommended): ship the bound above as stated, with W0704 as the alarm when
  a caught-up track falls more than a minute behind, and a demo step that overloads with many
  writers and asserts the backlog drains.
- **(b) Deterministic backpressure:** while any track's `next_ts` is more than `lag_max` behind
  its horizon, client ops that write to a trimmed tree are refused with a new status
  `retention_behind` (EntryStatus 25, its code taken when the answer lands). The backlog is
  then at most `lag_max` of writes plus `clients_max` × L. It costs a wire change, added to
  slice 1's formats, and refusals under load.
- **(c) A vendored patch to `src/vsr/replica.zig`** that pushes the pulse at the head of the
  request queue. That is a stop item (CLAUDE.md, item 2) unless the owner names the patch. It
  still lets the pipeline's `pipeline_prepare_queue_max` (8) client ops commit between two
  pulses, so the bound is (a)'s with q ≤ 8, not a hard one. Not recommended alone.

Raising each tree's per-op limit instead would change the table layout, a format stop, and is not
offered.

### History: the keep-last rule

- **The rule.** Every row keeps its newest change at or below the cursor, and every change above
  it. Since the cursor is at most `now − history_s`, every row keeps the change that was current
  at the horizon.
- **How a forward cursor applies it: trim the predecessor.** When the changes track examines a
  change C' of row R, it removes C, R's previous change, if there is one.
  - Checking C itself ("is a newer change of R below the horizon?") would not work with a forward
    cursor: when the cursor reaches C, R's next change is usually still above the horizon, and
    the cursor never comes back to C. Trimming the predecessor gives the same result and never
    looks back.
  - A row's first change has no predecessor and removes nothing. A deleted row's tombstone change
    is its last change, and the row itself is never touched, so it keeps both.
  - Commit keys' rows are rows of table `0xFFFF0003`, and the rule treats them like any other:
    the key row itself is never touched. A key row has one change, its first, which is never
    removed. In the `-Dtest-commit-keys=off` build (`state_machine.zig:150-153`), where a resend
    puts the key row again, the older of its changes is trimmed like any row's; the key check
    reads the row, never the change, so nothing changes for it.
- **The invariant.** Let c be the changes track's `cursor_ts`. For every row R:
  - exactly one of R's changes at or below c is kept, the newest; every change of R above c is
    kept.

  By induction on the changes the cursor examines: before R's first change, R has none at or
  below c. When the cursor examines C' of R, R's only kept change at or below the old cursor is,
  by the hypothesis, the newest one older than C', which is C' 's predecessor; removing it leaves
  C' as R's only kept change at or below the new cursor. Changes of other rows are untouched.
  Each change is removed at most once: only its successor's examination removes it.
- **What stays exact.** Let o ≥ `horizon_op`, and let D be R's newest change with op ≤ o (the
  answer to an as-of read of R at o). If D is above the cursor, it is kept. If D is at or below
  it, every change of R between D and the cursor has an op ≤ `cursor_op` ≤ o, so there is none
  (D is the newest with op ≤ o): D is R's newest change at or below the cursor, and is kept. And
  if R has no change with op ≤ o, none was removed that could have answered. So the read is
  exact. Rows, records and their tombstones are never touched.
- **What is refused.** An as-of read (`get_history` with `op_max`, `row?as_of=`) at an op below
  `horizon_op` answers `before_horizon`: an end record with a new flag bit, then HTTP 410 at the
  gateway with NRV-E0411 and the horizon's op. For example, with R's changes C1 at op 5, C2 at op
  10 and C3 at op 20, once the cursor has examined C3 (`horizon_op` 20), C1 and C2 are gone: a
  read as of op 7 is refused, never answered with nothing, and a read as of op 20 answers C3.
- **Records** are the same, with the record changes track, `Record` for `Row` and
  `RecordChange` for `Change`.

### History pages

A history read returns a row's whole history, newest first, a page at a time. Below the cursor
only the row's newest change is kept, so a read that pages past it would see that change, then
nothing, and today's end record would say "exhausted": the brief's own example would answer `[C3]`
and look like a row created at op 20. So `get_history`, `get_record_history` and
`GET /v1/history` are refused below the horizon, by these rules, applied with the track that
holds the read's changes (changes, or record changes) at the read's op:
- **As of an op below `horizon_op`** (`op_max < horizon_op`): refused, as above.
- **A page that starts at or below the cursor** (`timestamp_max ≠ 0` and
  `timestamp_max ≤ cursor_ts`): refused with `before_horizon` (end record flag, then 410 and
  NRV-E0411 at the gateway).
- **A page that reaches the cursor** returns the first change it finds at or below `cursor_ts`
  (with `op_max ≥ horizon_op`, its op is at most `op_max`, so it is returned) and ends there, as if
  its limit were reached: the end record has `more` set and the cursor that change's timestamp
  − 1, never 0. The next page starts at or below the cursor and is refused.

**Why it is complete.** A page returns every change of R with a timestamp in
(`cursor_ts`, `timestamp_max`] and `op ≤ op_max`, all kept by the invariant, then R's newest
change at or below the cursor, which is kept. Nothing between them was removed. A history that
ends with cursor 0 never reached the cursor, so R has no change at or below it, none was
removed, and "exhausted" is true.

**What it costs.** A row whose oldest kept change is at or below the cursor never reads as
exhausted, even when that change was its first: the next page is refused. That is conservative,
never wrong (Risk 5). No new format: the flag bit is the as-of refusal's, and the cursor is the
end record's existing field.

### Predecessor links

The predecessor is found from links written with each object, not by a read at trim time:
- `Row.change_timestamp` and `Record.change_timestamp`: the timestamp of the row's (record's)
  latest change;
- `Change.prev_timestamp` and `RecordChange.prev_timestamp`: the previous change's timestamp, 0
  for a first change;
- `Group.version_timestamp`, and `View.version_op` and `View.version_timestamp`: the latest
  version's (`Group.op` already holds its op);
- `GroupVersion` and `ViewVersion` gain `prev_op` and `prev_timestamp`.

**Layout.** All are carved from reserved bytes, so no layout grows; each is an on-disk format
change, listed under "Formats". Every struct has the room, and every one defaults its reserved
bytes to zero, so a file from the last release decodes with links of 0. Two placements are fixed
by alignment: `Row.reserved` is `[12]u8` at offset 116, so `change_timestamp` goes at offset 120
and `[4]u8` stays reserved; `Record`'s `change_timestamp` takes its last 8 reserved bytes.
**Each link field is added to its groove's `.ignored` list** (Row, Change, Record, RecordChange,
Group, View, GroupVersion and ViewVersion): `GrooveType` makes an index tree for every field not
named there (`groove.zig:307-316`), and a new index tree would need new `tree_ids`, which this
brief does not list. Slice 1's test asserts that every groove's tree count is unchanged.

**Replies never show a link.** `get_changes`, `get_history` and the record feeds copy each stored
`Change` and `RecordChange` into the reply as it is (`state_machine.zig:1540`, `:2410`). They
now zero `prev_timestamp` as they copy it, so every reply's reserved bytes stay zero and no reply
format changes. Rows, records, groups and views reach replies only through `RowValue`,
`RecordValue` and `ViewRecord`, which carry no link. Export reads through the same replies, and
import sets the links itself. Slice 1 tests that a reply's reserved bytes are zero after a row
is written twice.

- **The writer** sets a link from the current object, which `prefetch` already read for the
  write (the row for `row_put`, the group or view for its version). A row written twice in one
  op is updated in the cache each time, so the second change links to the first. Every write
  now updates its row, even one that leaves the same value, because `change_timestamp` moves.
- **The trim** removes the predecessor with no read: its objects-tree key is `prev_timestamp`,
  and its index key comes from the examined object's own fields (the same row's `row_key`, or
  `group_version_key(key, prev_op)` and `view_version_key(view_id, prev_op)`) with that
  timestamp.
- **Unlinked data.** An object written before R7's release has `prev_timestamp` 0 and removes
  nothing. R7's release is reached by export and import ("Formats and R6"), which rewrites every
  object with its links, so after the upgrade 0 means only a first change. A file opened in
  place keeps its unlinked history: more kept, never a wrong answer. The "What stays exact"
  proof does not need the links: D's only remover is its successor, whose op is above o ≥
  `cursor_op`, so it has not been examined.

### The feed below the horizon

- **What it holds.** Below the horizon, the change feed is a compacted prefix: the latest change
  of each row as of the horizon, in timestamp order, much like log compaction in a message log.
  Commit keys' changes are first changes, so they are all in it.
- **Where the feed's horizon is.** `get_changes` reads from `timestamp_min`, not from an op, so
  it is refused by timestamp, against the changes track's `trimmed_ts`. A read is refused with
  `before_horizon` when `trimmed_ts` is not 0 and `timestamp_min` is at or below it
  (`timestamp_min` 0, the beginning, included). Above it, no change at or after `timestamp_min`
  was removed, because `trimmed_ts` is the largest timestamp ever removed, so the feed is
  complete.
- **The opt-in.** A `ChangesFilter` flag, `compacted`, carved from its reserved bytes, serves the
  compacted prefix instead of refusing. Old servers refuse a nonzero reserved byte
  (`state_machine.zig:1518`), so a client that sets it against an older server is refused, not
  misserved.
  - `nerva view` (N35) and `nerva export` set it. Their consumers rebuild current state, which
    the prefix gives them exactly.
  - A consumer that needs every change does not set it, and is told.
  - Owner question 2.
- **The record feed**, where one is read, follows the same rule with the record changes track.

### View and group versions

- **The same keep-last rule, by predecessor link**, applied per group in GroupVersion (trees 12
  and 13) and per view in ViewVersion (trees 14 and 15) with `versions_s`: on examining a version
  V', the track removes V' 's predecessor through its `prev_op` and `prev_timestamp`. The
  invariant and its proofs are history's, with "group" or "view" for "row". Groups' and members'
  current state is untouched.
- **Reads.** A view read as of an op below the versions kind's `horizon_op` answers
  `before_horizon` (a flag bit in the view record); at or above it, it is exact. View reads page
  by group hash, each page as of one op (`ViewQuery.as_of`); no read pages through a group's or a
  view's versions, so "History pages" has no counterpart here.

### Export, import and backup

- **Export version 3.** The header carries the retention declaration and each track's cursor
  fields and `trimmed_ts`. The body is the compacted prefix followed by the ops above the
  horizon.
- **Import.** It accepts a first op above 1, and a row whose first change below the horizon is
  its latest, including a tombstone, without N81's "delete of a non-live row" refusal for that
  prefix. Ops above the horizon are replayed under every rule, as today. Import sets each track's
  fields from the header before it replays anything, so reads on the new cluster are refused
  where they were on the old. Every object it writes gets its predecessor links.
- **What import refuses.** A v3 file whose prefix is not in timestamp order, or which carries a
  change above its own declared horizon in the prefix (NRV-E0811).
- **Old files.** Export v1 and v2 files import unchanged.
- **Backups.** The manifest's version moves with export v3 (P149d).

## Risks

1. **The vendored removal path is untested upstream.** Upstream's own comment says nothing calls
   `remove`. A bug there loses or resurrects objects silently. Slice 2's fuzzer is the guard, and
   it comes before any trimming.
2. **A wrong link removes the wrong object.** Trimming trusts the predecessor links instead of
   reading, so a writer that sets a stale link (a row written twice in one op, a group created
   and changed in the same op, an import) removes a change that is still the latest, silently.
   The guards: slice 1 tests every writer's link; slice 3's model checks keep-last after every
   pulse; the VOPR's model (slice 6) predicts every as-of read and history page; and a removal
   asserts that the predecessor's timestamp is below the examined object's and not 0. The links
   cost no reads and keep a pulse's prefetch to one scan per track.
3. **Import trusts the prefix.** Below the horizon, import replays without the ledger's pair rule
   (the pairs are gone). A forged v3 file can import an unbalanced ledger. The export's checksum
   and E0811 cover damage, not forgery, as today for v2.
4. **Compaction load.** Trimming writes one tombstone per removed object, which roughly doubles
   compaction input on the trimmed trees in steady state. The demo's flat measures include it;
   R3's sizing table should be redone after R7.
5. **History pages end early.** A row whose oldest kept change is at or below the cursor never
   pages to "exhausted"; its last page is refused (`before_horizon`). A reader that pages to the
   end must treat that as "older history was trimmed", which the README says. It is conservative:
   it never answers short.
6. **The digest moves for one release**, so v0.8 to v0.9 is an export and import. It happens
   while rolling upgrades are new, and the release notes must say it plainly.
7. **Growth is bounded by the live set, not absolutely**, and under overload by the backlog
   too. A load that creates rows, records or commit keys still grows, by each one and its last
   change ("Goal"); many writers at the batch limit outrun trimming until the load falls (owner
   question 8).
