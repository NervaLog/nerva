## Goal

A replica whose disk is gone rejoins a running cluster without closing it, and a backup restores
to the same view hashes, with every refusal one coded line.

## Non-goals

- **A replacement at a new address.** A replica dials only the replicas after it
  (`README.md:208`, P102), so a new address needs the lower replicas and every gateway restarted
  with new `--addresses`. R5 recovers at the lost replica's address. The procedure for a new
  address is written down in R5's README text but not automated or tested (owner question 4).
- **Recovering several replicas at once.** One at a time, each caught up before the next, as
  upstream requires. More lost replicas than the cluster's quorum allows is a restore.
- **Clusters of one or two replicas.** Upstream's reformat needs three (`replica_reformat.zig:62`).
  They restore from a backup.
- **Changing the replica's runtime exits** (no space, storage limit, `origin_mismatch`). They get
  codes, not new statuses (owner question 1).
- **Scheduled backups, retention of backups, object storage.** `nerva backup` writes two files;
  where they go is the operator's (Botpike's runbook).
- **Incremental backups.** A backup is a whole export (about 121 bytes a change, README).
- **Codes in `nerva api` replies.** That is R4.

## What exists today

**The protocol can rejoin a reformatted replica.**
- `src/vsr/replica_reformat.zig` is upstream's recovery, vendored and unchanged, never reachable
  from the `nerva` binary. A client registers, commits `pipeline_prepare_queue_max` `noop`
  requests (`:107-178`), then formats a data file whose `vsr_state.view` is the client's view
  plus 2 (`:173`, `:91-105`), so the new replica never nacks an op its predecessor may have
  acknowledged and never sends a second, different view-change message in a view it joined. The
  replica then starts as usual and catches up, by repair inside the first checkpoint and by state
  sync after it (`replica_test.zig:329-354`).
- **Trap:** `ReplicaReformat.done()` (`:76-79`) returns a field, `result`, that the struct does not
  have. It compiles only because nothing calls it. Never call it; use `pending()` and `format()`.
- `noop` is a VSR operation: the replica answers it with an empty reply and never passes it to
  Nerva's state machine (`src/vsr/replica.zig:5637`, `:7579`).
- **The VOPR exercises it.** In swarm mode a crashed replica is reformatted with probability
  30/100 per restart, up to `replica_count + 2` times (`src/vopr.zig:436`, `:514`,
  `:1555-1585`), driven by `ReplicaReformatType` (`src/testing/cluster.zig:640-653`, `:878-911`).
  On the `nerva` lane every replica's origin, reformatted ones' included, is none or a random
  32 bytes by seed (`src/vopr.zig:419-435`, P90).
- **What the VOPR does not do:** start from an imported state. A "random origin" seed formats
  every replica empty at op 0 and only labels it; no seed starts from a checkpoint written by
  `import.zig`.

**Replacing a replica in production.**
- There is no command. README says to export the cluster and import every replica, with the
  cluster closed (`README.md:267-270`). P90 says why one replica imported alone is unsafe.
- A formatted replica cannot join an imported cluster: `nerva format` writes origin zero
  (`src/nerva_main.zig:234-251`), and its peers ignore it (P90).
- A replica of the wrong origin exits with status 8, `origin_mismatch`, and a message naming both
  exports (`src/vsr/replica.zig:3735-3750`). **That exit has no code in `docs/ERRORS.md`**; this
  brief registers it as NRV-E0711.
- Recover can learn a replica's view and release only by observing `pong_client`
  (`src/vsr/replica.zig:1988-2002`), which the vendored client does not pass up
  (`src/vsr/client.zig:490-505`).

**Backups.**
- `nerva export` (`src/nerva_main.zig:317-358`, `src/nerva/export.zig`) writes a versioned,
  CRC-framed, SHA-256-closed file with each view's state, hash and group count, each ledger's
  total and a hash of each table's rows as of its op (N80). `nerva import`
  (`src/nerva_main.zig:112-165`, `:262-315`) checks all of it before it creates a file, restores,
  compares the restored state with the checks, and names the file only once they pass (N81).
- Nothing records an export's identity apart from the export itself, so a backup that was
  swapped, truncated and re-closed, or taken of another cluster, imports cleanly. There is no
  "backup" or "restore" command and no test of a restore of a live cluster's export.

**Diagnostics.**
- Every command failure is `vsr.fatal(.cli, …)`, a log line and exit 1 (`src/vsr.zig:703-734`;
  21 call sites: 8 in `src/nerva/cli.zig`, 13 in `src/nerva_main.zig`). Several end in a raw
  `@errorName` (`nerva_main.zig:108`, `:141`, `:151`, `:158-164`).
- Operator input that panics in vendored code, before Nerva's code sees it: a missing data file
  (`src/io/linux.zig:1475`), a held lock (`:1622`), another release's file
  (`src/multiversion.zig:64`, #95), no superblock (`src/vsr/superblock.zig:1421-1422`).
- The storage-limit exits (4, 5) name a flag Nerva does not have, `--limit-storage`
  (`src/vsr/grid.zig:660`, `src/vsr/superblock.zig:1395`).
- `docs/ERRORS.md` registers the codes and says R5 makes commands print them; nothing does yet.

## Design

### `nerva recover`

```
nerva recover --cluster=<id> --replica=<index> --replica-count=<n> --addresses=<every replica,
              in order> --origin=<export sha256 | none> [--development] [--log-debug] <path>
```

It formats `<path>` as replica `<index>` of a running cluster, then exits. The operator then
runs `nerva start` on it as on any data file; it catches up by repair or state sync.

1. **Flags.** `--replica-count` at least 3 (NRV-E0714). `--replica` below it, and exactly
   `--replica-count` addresses (NRV-E0002, NRV-E0710). `--origin` is required, with no default:
   64 hex digits (the export's SHA-256, which `export` prints and `import` and `start` log), or
   `none` for a cluster that was formatted (NRV-E0001 if malformed). An operator who passes the
   wrong one gets a replica that exits with NRV-E0711 naming the right one, and nothing from it is
   handled by its peers (P90).
2. **No file there.** `<path>` must not exist (NRV-E0005); `<path>.recovering`, left by a killed
   recover, must not exist (NRV-E0715). Both checked before any connection.
3. **The replica is gone.** A TCP connect to the replica's own address, bounded by
   `recover_probe_timeout`: if anything accepts, it refuses (NRV-E0713). Then a connect to each
   other address: if fewer than the replication quorum (`vsr.quorums`, `src/vsr.zig:1198`)
   accept, it refuses at once (NRV-E0712) rather than wait out the timeout. This cannot see a
   replica alive behind a partition from the recovering host; the README says the operator must
   destroy the lost replica's data file or machine first, as upstream does (risk 2).
4. **Reformat's precautions, unchanged.** `src/nerva/recover.zig` instantiates the vendored
   `ReplicaReformatType(StateMachine, MessageBus, Storage)` with the real bus and storage, so the
   code the VOPR checks is the code that runs. It owns an `IO`, a `MessagePool` and a VSR client,
   as `Client.init` does (`src/nerva/client.zig:89-140`) but without registering: reformat's
   `start()` registers. It ticks the client and IO until `pending()` is false, the eviction
   callback fires (NRV-E0716), or `recover_timeout` passes (NRV-E0712). Recover's session takes
   one of the cluster's 64 (`README.md:617-619`).
5. **Write, then name.** `Storage.init` with `.purpose = .format` on `<path>.recovering`, before
   step 4 (reformat holds the storage from `init`). After `format()`: flush, `linkat` to `<path>`,
   remove the temporary name, sync the directory, as import does (`nerva_main.zig:154-165`, N81).
   Any failure removes `<path>.recovering`. The origin goes in through `FormatOptions.origin`,
   the release is this build's.
6. **Output.** One line: `recover: replica 2 of cluster 0 formatted at view 14 (the cluster was
   at view 12), export none (formatted); start it with nerva start`, and a warning that the lost
   replica's old data file must never start again.

**What the state machine does:** nothing new. `noop` never reaches it. Recover adds no
`Operation`, no `tree_id` and no message. **It must never** be given a way to write a data file
that holds state (that is import's, and unsafe alone, P90): recover writes only what `format`
writes, with a view and an origin.

### `nerva backup` and `nerva restore`

```
nerva backup --cluster=<id> --addresses=<…> [--as-of=<op>|latest] --output=<path>
nerva restore --cluster=<id> --replica=<i> --replica-count=<n> --input=<path>
              --manifest=<path>.manifest.json [--development] [--log-debug] <data file>
```

- **`backup`** runs `export` into `<path>` (its refusals and codes unchanged), then reads its own
  file back through import's pass 1 (`import_.plan`: every CRC, the SHA-256, every view
  definition rebuilt), so a backup that `restore` would refuse is refused now (NRV-E0803 or
  NRV-E0804). Last it writes `<path>.manifest.json` with `createFile(.exclusive)` and an fsync,
  and prints the SHA-256 and the manifest's path. Neither file is ever overwritten (NRV-E0004).
- **The manifest** is a new file, version 1, JSON, at most `manifest_size_max`, kept apart from
  the backup so that a damaged or swapped backup is caught by a record it did not carry:
  ```json
  {"format":"nerva-backup","version":1,"release":"0.0.6","cluster":"0","op":"1234",
   "export_sha256":"…","export_size":"128838400","export_version":2,
   "views":[{"name":"revenue","id":1,"state":"ready","view_hash":"…","groups":"12"}],
   "ledgers":[{"id":1,"total":"0"}]}
  ```
  Every value is the export's own check, which came from the cluster (N80). Decimal strings for
  64-bit numbers, as the JSON API. At most `views_max` (64, `src/nerva.zig:563`) views and
  `ledgers_max` (64, `src/nerva.zig:1237`) ledgers; table hashes stay in the export (up to 2^16
  tables) and import checks them.
- **`restore`** is import with the manifest checked first. It parses the manifest (NRV-E0808),
  runs pass 1, and before any file exists compares the export's size, SHA-256, op, version and
  every view's and ledger's check with the manifest (NRV-E0809, naming the first that differs).
  Then pass 2 as import, with import's refusals. `--cluster` may differ from the manifest's: a
  restore drill into a second cluster beside the first is the point (Botpike's monthly drill). It
  prints `restored replica 0 from backup <sha256> at op 1234: 3 views and 1 ledger match the
  manifest`, and import's warning that a replica of a running cluster is never restored alone.

**Formats:** the data file, the export file, the wire and every persisted identifier are
unchanged. The manifest is a new file of its own; it changes no existing format. **No stop
applies**, unless the owner rejects owner question 2 or 5.

### Coded diagnostics

- `src/nerva/diagnostic.zig`: a comptime table of the codes commands emit (code, summary, blame),
  and `fail(code, comptime cause, args, comptime fix, args) noreturn`, which prints and exits:
  ```
  error[NRV-E0713]: replica 2 still answers at 127.0.0.1:3003
    cause  nerva recover replaces a replica that is gone; this address accepts connections
    fix    stop replica 2 and destroy its data file, then run nerva recover again
  ```
  `bug[NRV-B0004]` for an error a command did not expect, never its name in the first line; the
  error name goes on a `detail` line under `--log-debug` only.
- **Exit statuses for commands:** 1 operator, 2 environment (disk, kernel, file system), 70
  internal. `nerva start`'s runtime exits keep their statuses (2 to 8: `src/vsr.zig:703-713`,
  documented by P90 and README) and gain their codes in the message (owner question 1).
- **Pre-flight in Nerva's code**, before the vendored open, so that operator input never reaches a
  vendored panic: `format` refuses an existing path (NRV-E0005); `start` refuses a missing file
  (NRV-E0006), a lock another process holds (NRV-E0703, a non-blocking `flock` taken and released
  just before `Storage.init`), a file of another release (NRV-E0701, from its superblock copies,
  read and checked with the vendored header types, unmodified), a file with no valid superblock
  quorum (NRV-E0702), a file system without direct IO when it is required (NRV-E0704), and a
  kernel below `kernel_version_min` (NRV-E0705). The vendored panics stay as a backstop for a race
  between pre-flight and open.
- A test asserts that the codes in `diagnostic.zig` and `docs/ERRORS.md` agree, and a check fails
  any command output in the tests that holds a stack trace or `error.` followed by a name.

## Bounds

| Constant | Value | Where | Why |
| --- | --- | --- | --- |
| `recover_timeout` | 60 s | `recover.zig` | Registration and every `noop`; a healthy cluster commits them in well under a second |
| `recover_probe_timeout` | 1 s per address | `recover.zig` | A loopback or 6PN connect answers in milliseconds |
| `recover_requests` | `constants.pipeline_prepare_queue_max` | asserted equal in `recover.zig` | Upstream's count; never changed |
| `recover_view_skip` | 2 | asserted in a test against `replica_reformat.zig:173` | Upstream's rationale (`:14-20`) |
| `manifest_version` | 1 | `backup.zig` | A new version is a new format |
| `manifest_size_max` | 64 KiB | `backup.zig`, comptime-checked against `views_max` and `ledgers_max` lines | A manifest is read whole |
| `kernel_version_min` | 5.11 | `preflight.zig` | ERRORS.md NRV-E0705 |
| `exit_operator`, `exit_environment`, `exit_internal` | 1, 2, 70 | `diagnostic.zig` | Zigbox's statuses (ERRORS.md) |

Each gets a test at the bound and one past it (REVIEW.md): `recover_timeout` with a test-only
override flag (`--timeout-test-ms`, refused outside test builds), the manifest at 64 views and
64 ledgers and with one byte more than `manifest_size_max`.

## The demo: `zig build demo-r5`

`tests/demo/r5.py <nerva>`: three replicas on loopback, each with `--statsd` to the script's UDP
listener, a real `NERVA_CLUSTER_KEY`, one `nerva api` and one `nerva view`. Every step asserts.

| Step | Action | Expected |
| --- | --- | --- |
| 1 | Format and start three replicas; declare a layout, a ledger and two views; start a writer: keyed commits that move the ledger by pairs and write records, without pause until step 8 | Every commit answers `committed`, or a 503 resent under its key that then answers `committed` or `replayed` |
| 2 | Commit until past op 1,100 (past the first checkpoint) | — |
| 3 | SIGKILL replica 2; delete its data file | The writer goes on; no commit fails other than as in step 1 |
| 4 | `nerva recover --replica=1 …` | `error[NRV-E0713]`, exit 1, no file written |
| 5 | `nerva recover --replica=2 --origin=none … 0_2.nerva` | Exit 0; one `recover:` line naming the view; `0_2.nerva` exists, `0_2.nerva.recovering` does not |
| 6 | `nerva start` replica 2 | Within 180 s its log shows `sync: done`, and its `replica_commit_min` gauge (`replica.zig:4094`) reaches the others' |
| 7 | Restart replica 0, then replica 1, one at a time, waiting for each to commit again, until the `replica_view` gauge says replica 2 is primary (view mod 3 = 2), at most 6 restarts | With replica 2 in every quorum the writer goes on; replica 2 leads a view |
| 8 | Stop the writer. With replica 2 the primary, read every view, the ledger and its total through `nerva api` | Every `view_hash` and `hash` equals `nerva view`'s; the ledger total is conserved; every acknowledged key, resent, answers `replayed` with its original op: none lost, none doubled |
| 9 | `nerva backup --output=b.nerva-backup` | Exit 0; prints the SHA-256; the manifest's view hashes equal step 8's |
| 10 | Restore into a one-replica drill cluster (cluster 1) while cluster 0 runs | Every view hash and the ledger total equal the manifest's |
| 11 | Stop cluster 0; delete its three data files; `nerva restore` each; start them | Exit 0 each; every view hash and the ledger total equal the manifest's, through `nerva api` and `nerva view` |
| 12 | `nerva restore` from the backup with one byte changed | `error[NRV-E0809]` (or E0804 if the CRC breaks first), exit 1, no data file |

The script prints one line per step and ends `demo-r5: PASS` or `demo-r5: FAIL step N: …`. A
failure is a finding (CLAUDE.md), never re-run until it passes.

## Risks

1. **Imported clusters are not simulated** until slice 5 lands. P90 found two failures that only
   imported clusters showed. Slice 4's real-process test is the only evidence until then.
2. **A lost replica that is not really gone.** If the old process or its data file comes back
   beside the recovered one, two replicas share an index, and the protocol's guarantees are void.
   The probe sees only a listener reachable from the recovering host. The README and the
   message say to destroy the old data file first.
3. **State sync time on real data is unmeasured.** A replica's grid crosses the network; R3 has
   not measured the topology. The demo's data is small. Until R3, the runbook says how long one
   recovery took in CI.
4. **Recover takes a client session** and may evict the least recent of 64. A gateway reconnects
