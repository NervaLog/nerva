# One approval ships a release: CI signs, publishes, bumps the tap and opens the site's pull request

**Decision.** The owner's decisions of 2026-11-12, modelled on Zigbox's release automation
(Zigbox/zigbox#118). The spec, bill of materials and setup guide are
[docs/releases/automation.md](../releases/automation.md).

1. **One human act.** The owner's approval of the `mac` job in the environment `apple-signing` is
   the only human act in a release. Everything after it runs without anyone, in a new reusable
   workflow `release-finish.yml` that `release.yml` calls on `main` after its draft exists:
   `mac` (mac-sign.yml, unchanged) → `mac-verify` (on the draft) → `publish` (environment
   `release-publish`: `main` only, no reviewers; publishes the draft, which creates the tag;
   commits the formula to the tap; opens the site's pull request) → `verify` (`brew install` from
   the tap on both Mac architectures). `apple-signing` is the only environment with a reviewer,
   so one approval covers signing and publishing. The approval therefore means "ship this
   release", and the draft it ships already exists when the prompt appears.
2. **P343 is amended on one point.** The Developer ID certificate and the notary key go into
   `apple-signing` now, before the machine account exists. Sessions act as the owner's account
   `topwombat`, the environment's reviewer, so a session could in principle approve a deployment,
   and now that approval publishes. The owner accepts this risk. What keeps it in check: sessions
   have no tool that approves a deployment; CLAUDE.md says a session never does; workflow changes
   are reviewed before they merge. The machine account, with "Prevent self-review" on
   `apple-signing`, stays the later fix. Everything else in P343 holds: secrets only in the
   keychain step, `mac-draft` before any secret, `main`'s code with the keychain unlocked, the
   owner's Mac as the fallback.
3. **A GitHub App, "Nerva Release",** holds the writes to other repositories. It has Contents and
   Pull requests (read and write) and Metadata (read), and it is installed only on
   `NervaLog/homebrew-tap` and `NervaLog/nervalog.github.io`. Its id and key live only in
   `release-publish`. Writes to `NervaLog/nerva` use the run's `GITHUB_TOKEN`.
4. **The site is updated by a pull request the App opens and auto-merges** once the site's new
   required check `site-check` passes. It touches only the new `RELEASES` entry and
   `SITE.version`, `SITE.released` and `SITE.updated`. The prose (`SITE.stage`, `NEXT`,
   `PRODUCTION`) stays with the supervisor's status PR. The entry's sentence comes from a new
   first line of the version's CHANGELOG section, `<!-- site: ... -->`, which `release_notes.sh`
   drops from the release notes. A release without one is refused before CI runs.
5. **The tap's formula is committed straight to the tap's `main`,** as Zigbox does, not by a pull
   request. The formula is generated by reviewed code (`mac-release`). Its hash comes from the
   job that built and checked the zip, and `publish` refuses a formula whose `url`, `version` or
   `sha256` does not match the draft, or a diff that changes any other line. The tap has no
   checks a pull request could wait for, and `verify` installs from it at once. A pull request
   would add a merge and no review.
6. **A prerelease never reaches users.** Its formula goes to the tap branch `rc/v<V>`, and its
   site PR is opened without auto-merge. `verify` installs from that branch.
7. **Every existing guard stays:** `release_check.sh` (`ref`, `unreleased`, `binary`, `assets`,
   `mac-draft`, `mac-same`, `mac-upload`), main only for a suffix-less version, the refusal of a
   second draft, the required CHANGELOG section, and P343's rehearsal path. A prerelease drafted
   from a branch is finished by dispatching `release-finish.yml` from `main`. `publish` adds
   `publish-ready`: a draft, the same commit, exactly eleven assets.
8. **Timing.** The automation is used for v0.7.1 only if the rehearsal on `v0.7.1-rc.2` passes the
   whole graph before the v0.7.1 soak ends (about 27 hours from its start on 2026-11-12).
   Otherwise v0.7.1 ships the way it does today, and this lands first thing after the tag. The
   change touches no `src/` or `build.zig`, so the release freeze does not cover it, but it
   changes how v0.7.1 ships, so the rehearsal is the gate.
9. **apt and dnf repositories (v0.7.2)** join later as one more job after `publish`, in an
   environment of their own. Only that hook is reserved here, not the job's design.

**Reason.** The owner should decide once whether a release ships, and not then be needed four
more times to carry it out. Each manual step after the draft (read the run, publish, commit the
formula, ask for the site) was a chance to ship a half-finished release or to leave the tap
behind. Putting the cross-repository writes in an App, rather than a personal token, limits them
to two repositories and two permissions, behind an environment only `main` can deploy.

**Cost.** Apple's keys sit in GitHub before the machine account, and the account that holds the
approval is the account sessions use. The approval can no longer be followed by a second look
before publishing: once `mac-verify` is green, the release is out, and a mistake is corrected by
the next version. A CHANGELOG section needs one more line. The site repository gains a workflow,
a ruleset and auto-merge. The rehearsal cannot exercise the push-triggered path, a commit to the
tap's `main` or the site's auto-merge, so the first real release is their first run, with
today's manual steps as the fallback for each.
