# A 0.0.4 replica dialed by a 0.0.5 one crashes; it does not close the connection

P102 says that a 0.0.4 replica and a 0.0.5 replica "cannot talk at all: 0.0.4 closes on an
unknown command, and 0.0.5 on a replica message before the handshake". The second half holds; the
first does not (#111, from the 0.5.0 release review).
- **What happens:** the replica that dials sends `peer_hello`, command 25. v0.4.0's `Command`
  ends at `view = 24`, and its `message_buffer.zig` answers a command byte it cannot name with
  `vsr.fatal(.unknown_vsr_command, ...)`: the 0.0.4 replica exits with status 7. So a 0.0.5
  replica of a lower index than a 0.0.4 one, which dials it, stops it with its first message. The
  other way round, a 0.0.4 replica dialing a 0.0.5 one sends a ping, and the 0.0.5 replica closes
  the connection, as P102 says.
- **What we do about it:** nothing in the code. A released v0.4.0 cannot change, and mixing the
  two releases is already unsupported: the README says never to run them in one cluster, and an
  upgrade is an export and an import with the cluster stopped (N80). The README now names the
  crash, so that a botched upgrade or rollback is recognised for what it is. It is the same class
  as #95, where a v0.4.0 replica given a newer data file stops on a panic rather than a message:
  an older release meeting a newer one stops loudly, never silently, but without saying why.
- **What it costs:** an operator who mixes the releases anyway sees 0.0.4 replicas exit with
  `unknown VSR command, crashing for safety (command=25 ...)` instead of a refusal naming the
  release. Nothing is written to either data file.
