# 493 — `scenario_cluster` no longer loses the client round-trip metric (#482)

2026-11-18

- Cause, from #482's log: replicas entered their tick loops at 16:45:30.687 (r2), 31.182 (r1, the
  primary) and 31.184 (r0). `expect_metrics` ran from 32.9 to 48.4, so no replica had emitted
  anything when it started, and the window held one emit per replica (the first, at about 10 s).
  r0 and r1 started 2 ms apart, so their first emits coincide: 53 to 55 packets each (about
  72 KiB), over 100 together, against the 93 or so the default receive buffer (`rmem_default`
  212992) holds. A reader that is off the CPU at that moment loses the tail of the primary's
  burst, where `client_request_round_trip` is (second to last packet). Metrics reset at each emit
  and the scenario sends no more requests, so the next emit has no round trips.
- This is reasoned from the log, not seen in CI. Shown on the same code with a temporary,
  uncommitted patch (the reader waits for the first packet, then stalls 1.5 s) and the default
  buffer: 93 packets received, the kernel dropped 68, and `never received
  tb.client_request_round_trip_us.count:`. With `SO_RCVBUF` 212992 and the same stall, the
  scenario passes.
- Fix (test only, `src/integration_tests.zig`): `SO_RCVBUF` raised to 212992 (Linux doubles it;
  the listener fails at start if it is below three replicas' emits at once); a thread drains
  the socket from before the first replica starts into a bounded buffer (8 MiB); `SO_RXQ_OVFL`
  makes a missing needle print the kernel's drop count; a receive error fails
  `expect_metrics` at once. `expect_metrics` still waits 15 s for all five needles, and scans
  only new bytes, outside the lock. It sends no requests while waiting (P493).
