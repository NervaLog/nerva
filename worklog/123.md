# 123 — Commit keys (P123); a design for Phase B storage

2026-10-16, https://github.com/Botpike/nerva-ledger/pull/123

- Commit keys (P123, amends N4): a transaction may start with a `key` entry. When it commits,
  the state machine writes the key's row (table `0xFFFF0003`) in the same op; a later
  transaction under the key commits nothing and reports `committed_before` (same entries, with
  the original op), `key_reused` or `key_collision`. `nerva api` takes `"key"` on `/v1/commit`
  and answers a resend `200 … "replayed": true`. Import refuses key rows no commit writes.
  Release string `0.0.6`.
- Tests: state machine (resends alone and twice in one request, stale reads and views do not
  hide a resend, reuse, misplaced and invalid keys, a collision restored by import, keys kept by
  export and import, invalid key rows refused by import); `api.zig` (JSON, indices, bad keys);
  `tests/api/commit_keys.py` in `test:api` (resends through both gateways, 30 concurrent
  resends, 20 lost replies, reserved table); the VOPR workload sends keyed transactions and
  resends them, as sent or with other entries, against its model; format guards (`EntryKind`,
  `EntryStatus`, `CommitKey`, `commit_key_id` from Python's hashlib).
- `docs/design/phase-b-storage.md`: a proposal, not a decision, for what Phase B needs from
  Nerva's storage (128-bit ids, wider records, declared indexes, key retention), from an
  inventory of the Postgres tables Phase B moves. For the owner to decide.
- Verified: `check`, `test:fmt`, `test:unit` (all but the environmental `benchmark.perf`),
  `test:api` (ipv6 skipped: no IPv6 here), `test:release`; VOPR seeds 42, 7, 1234 (Debug) and
  1, 2, 5 (ReleaseSafe), and `fuzz_loop.sh vopr nerva 15`: 202 random seeds, none failed (3
  stopped at "repair requires reachable primary", as upstream does), 863 keyed commits, 953
  resends, 439 `committed_before`, 90 `key_reused`. Not run: `test:integration`, `test:views`,
  `test:demo`, Jepsen, the fuzzers.
- Then, the owner answered the design note's questions (records as proposed; indexes without
  `as_of`; facts move to Nerva too) and asked for all of it, tested, and release 0.6.0:
  - Records (P123b): `commit_wide`, `lookup_records`, `get_record_changes`,
    `get_record_history`; `WideEntry` everywhere inside the state machine; tree ids 18 to 21;
    a one-line vendored patch to `ScanTree` (UPSTREAM.md).
  - Declared indexes (P123c): `declare_index`, `scan_index`, `get_index`; tree ids 22 to 26;
    backfill by pulses; ties ordered by the record's own timestamp, so scans and cursors are
    the same after export and import.
  - Views over records (P123d): `count` and `sum`.
  - Export format version 2 (records' changes, indexes, record checks); version 1 still read
    and still written for a cluster without records or indexes.
  - `nerva api`: record ids, the merged feed, `/v1/indexes`; the Zig client.
  - Tests: state machine (records, indexes, ties, record views, restore, a batch too small for
    a wide entry); `api.zig`; `tests/api/records.py` against a model; `test:release` runs the
    upgrade again with records (`--records`); the VOPR workload models records, a fact
    committed with each ledger pair, and four indexes (scans, cursors, counts).
  - Found by the VOPR and fixed here: record trees with a zero batch limit, index scratch
    smaller than a pulse's backfill, and `event_max` asserting, all at a batch too small for a
    512-byte entry (seed 1546770305681610083).
  - Measured: a replica takes 3.0 GB resident at startup at the default settings, from 2.5 GB
    (with `--development`, 1.83 from 1.33); 2.5 GB with `--cache-grid=512MiB` (CHANGELOG
    upgrade steps). What could not be tested here is in `docs/test-plan-0.6.0.md`.
  - The adversarial release review (a separate agent) found, and this pull request fixes: a
    scan cursor past every timestamp crashed every replica, again on restart (#124); the merged
    `/v1/changes` skipped row changes under concurrent writes (#125); a v0.5.0 export with rows
    in the record range crashed import (#126); the memory figures were `--development` ones
    (#127); a narrow `commit` naming a record table read an unprefetched record during view
    admission (#128); thin VOPR coverage of scan pages (#129).
