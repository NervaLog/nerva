# 123 — Commit keys (P123); a design for Phase B storage

2026-10-16, https://github.com/Botpike/nerva-ledger/pull/123

- Commit keys (P123, amends N4): a transaction may start with a `key` entry. When it commits,
  the state machine writes the key's row (table `0xFFFF0003`) in the same op; a later
  transaction under the key commits nothing and reports `committed_before` (same entries, with
  the original op), `key_reused` or `key_collision`. `nerva api` takes `"key"` on `/v1/commit`
  and answers a resend `200 … "replayed": true`. Import refuses key rows no commit writes.
  Release string `0.0.6`.
- Tests: state machine (resends alone and twice in one request, stale reads and views do not
  hide a resend, reuse, misplaced and invalid keys, a collision restored by import, keys kept by
  export and import, invalid key rows refused by import); `api.zig` (JSON, indices, bad keys);
  `tests/api/commit_keys.py` in `test:api` (resends through both gateways, 30 concurrent
  resends, 20 lost replies, reserved table); the VOPR workload sends keyed transactions and
  resends them, as sent or with other entries, against its model; format guards (`EntryKind`,
  `EntryStatus`, `CommitKey`, `commit_key_id` from Python's hashlib).
- `docs/design/phase-b-storage.md`: a proposal, not a decision, for what Phase B needs from
  Nerva's storage (128-bit ids, wider records, declared indexes, key retention), from an
  inventory of the Postgres tables Phase B moves. For the owner to decide.
